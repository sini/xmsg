## 1. Problem & Threat Model

### 1.1 Hole 1: Caller-Asserted Reply Identity on HTTP

In U2 through U4, `POST /v1/messages/{id}/replies` accepted a JSON payload containing `sessionRef`. The server resolved `sessionRef` and checked whether it matched the message's `session_id`. However, because TCP peers cannot be authenticated by PID or credentials on local loopback, any process capable of connecting to `http://127.0.0.1:7787` could supply the genuine recipient's `session_id` as `sessionRef` and post spoofed replies. The HTTP 403 `not_recipient` check provided zero protection against local untrusted processes.

### 1.2 Hole 2: Insecure `/tmp/xmsg-$UID` Fallback

In U4, fallback paths in `src/agy.rs` and `extensions/pi/index.ts` targeted `/tmp/xmsg-$UID/register.sock`. Because `/tmp` is world-writable with the sticky bit, an unprivileged attacker on a multi-user system could pre-create `/tmp/xmsg-$UID` before the victim agent started, place a rogue socket, and intercept or inject malicious messages.

## 2. Architecture & Mechanisms

### 2.1 Two Dedicated Unix Domain Sockets in `$XDG_RUNTIME_DIR/xmsg/`

The server creates and manages two distinct Unix domain sockets located in `$XDG_RUNTIME_DIR/xmsg/`:

1. `register.sock` (`mode 0700` parent directory):
   - Used for harness-level lifecycle: Antigravity credentials registration and Pi long-poll message delivery.
2. `agent.sock` (`mode 0700` parent directory):
   - Used for identity-attested agent operations: `reply` and `send`.
   - Uses line-delimited JSON framing.
   - Uses `SO_PEERCRED` to identify caller UID and PID.
   - Derives caller identity via ancestor walk against live sessions. Rejects any caller whose process tree does not trace to a registered/active agent session.
   - Accepts **no** caller-specified `session_ref` or `from` fields.

### 2.2 Strict Directory Permissions & No `/tmp` Fallback

- The `/tmp/xmsg-$UID` fallback is completely removed from all server and client components.
- If `$XDG_RUNTIME_DIR` is unset:
  - The server refuses to start Unix sockets and exits with a clear error.
  - `xmsg register agy` logs a warning to stderr, prints `{"injectSteps":[]}`, and exits 0.
  - `xmsg-pi` extension logs a warning to stderr and disables socket polling.
- Both server and clients verify that the socket directory:
  1. Is owned by `current_uid()`.
  2. Has strict file permissions `mode & 0o777 == 0o700`.
  3. Is a directory and not a symlink.
     If any check fails, connection or binding is refused immediately.

### 2.3 `agent.sock` Protocol & Operations

#### 1. Reply Operation

```json
{"action": "reply", "messageId": "<message_id>", "text": "<reply_text>"}
```

- Server identifies caller session via ancestor walk.
- Server validates that `caller_session.session_id == message.session_id`.
- If matched: inserts reply into SQLite, triggers notifications, returns:
  ```json
  {"status": "ok", "reply": {"id": "...", "seq": 1, "text": "..."}}
  ```
- If mismatched: returns `{"status": "error", "error": "not_recipient", "detail": "caller is not recipient"}`.

#### 2. Send Operation

```json
{"action": "send", "ref": "<target_ref>", "text": "<message_text>"}
```

- Server identifies caller session via ancestor walk.
- Server formats sender as `xmsg@<host> · session:<name>` (where `<name>` is `caller_session.name` or `caller_session.session_id`).
- Message is delivered to the target session (Claude socket, Agy agentapi, or Pi queue).
- Returns:
  ```json
  {"status": "ok", "delivery": {"sessionId": "...", "fromName": "...", "messageId": "...", "bytes": ...}}
  ```

### 2.4 HTTP Surface Changes

- `POST /v1/messages/{id}/replies` is completely removed from HTTP router.
- `send_message_handler` on `POST /v1/sessions/{ref}/messages`:
  - Enforces that `from` MUST NOT start with `session:` or `session/`.
  - If it starts with `session:`, returns HTTP 400 Bad Request.
  - This guarantees that only messages sent over `agent.sock` carry the attested `session:` badge.

### 2.5 MCP Server & Extension Client Migration

- `xmsg mcp`:
  - `send` tool: connects to `agent.sock`, sends `{"action": "send", "ref": ..., "text": ...}`.
  - `reply` tool: connects to `agent.sock`, sends `{"action": "reply", "messageId": ..., "text": ...}`.
  - `list` tool: retains HTTP `GET /v1/sessions`.
- `xmsg-pi` extension:
  - `reply` tool connects to `agent.sock` instead of posting to HTTP.

## 3. Gating Oracles & Red Demonstrations

1. **Red Demo 1 (HTTP Reply Removed)**:
   - At commit `7739858`, an HTTP POST to `/v1/messages/{id}/replies` with a forged `sessionRef` returns 201 Created.
   - After U5, HTTP POST to `/v1/messages/{id}/replies` returns 404 / 405.
2. **Red Demo 2 (`session:` Prefix Protection)**:
   - At commit `7739858`, an HTTP POST with `from: "session:evil"` succeeds and formats `xmsg@host · session:evil`.
   - After U5, HTTP POST with `from: "session:evil"` returns 400 Bad Request.
3. **Red Demo 3 (Socket Directory Insecurity)**:
   - Verification fails when socket directory has mode 0755 or is owned by another UID.
4. **Red Demo 4 (XDG_RUNTIME_DIR Unset)**:
   - Server returns error; `xmsg register agy` exits 0 with `{"injectSteps":[]}`.
5. **Attested Reply on `agent.sock`**:
   - Descendant of recipient session succeeds with 200/ok.
   - Non-descendant process receives `not_recipient`.
