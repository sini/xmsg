## 1. Problem & Context

At Unit U7, all replies were stored in SQLite (`replies` table) and could only be consumed via long-polling (`GET /v1/messages/{id}/replies?after=&wait=`). While polling works for HTTP callers, interactive agent harnesses (Claude Code, Antigravity, Pi) operate via asynchronous inboxes and event loops. An agent sending a request to a peer session has no background thread continually long-polling for replies.

Unit U8 introduces direct **reply push delivery**: when a recipient replies to a message via `agent.sock reply` (or MCP `reply`), `xmsg` automatically pushes the reply directly into the original sender's inbox or queue using the appropriate harness adapter.

### Security Invariant: Derived Return Address
To prevent **confused deputy attacks**, the return address is **strictly derived by the server from attested kernel credentials** on `agent.sock`.
- No API parameter or header allows a caller to specify, override, or redirect a return address.
- If callers could choose the return address, an unauthenticated or malicious caller could inject a message into Session B with return address pointing to Session C, causing Session B's attested reply to be delivered into Session C without C's knowledge or consent.
- Unauthenticated HTTP sends (`POST /v1/sessions/{ref}/messages`) have `return_to = NULL` and remain strictly poll-only.

## 2. Architecture & Mechanisms

### 2.1 Attested Return Address Recording
1. When a message is sent via `agent.sock` `send` (including MCP `send` and Pi extension):
   - The server inspects the kernel-attested caller credentials via `resolve_caller_session`.
   - The message is stored with:
     - `return_harness = caller.harness` (`"claude"`, `"agy"`, or `"pi"`)
     - `return_session_id = caller.session_id`
     - `push_replies = req.push_replies.unwrap_or(true)`
     - `thread_id`: if not inherited from a parent thread, initialized to the message's own `id`
2. When a message is sent via HTTP `POST /v1/sessions/{ref}/messages`:
   - `return_harness = None`
   - `return_session_id = None`
   - `push_replies = false`
   - `thread_id = message_id`

### 2.2 Push Opt-Out (`push_replies: bool`)
- `agent.sock` `send` and MCP `send` accept an optional `push_replies: bool` (default `true`).
- When `push_replies = false`:
  - `push_replies` is stored as `0` in `messages`.
  - When the recipient replies, no push delivery is attempted, and the reply records `push_outcome = "disabled"`.
  - The reply remains accessible via `GET /v1/messages/{id}/replies`.

### 2.3 Reply Action & Push Delivery Flow
When `agent.sock reply` is invoked:
1. Caller authorization is validated (caller must match `recipient_harness` and `session_id` of the original message).
2. The reply text is inserted into `replies`.
3. If `return_harness` and `return_session_id` are present:
   - If `!push_replies`:
     - Set `push_outcome = "disabled"`.
   - Else (`push_replies == true`):
     - Allocate a new ULID `new_message_id`.
     - Construct the reply envelope:
       - Attested badge: `from_name = inbox::sanitize_attested_from(host_label, caller.harness, caller_name)`
       - Header line: `[xmsg] reply to message_id=<orig_id> — message_id=<new_id>; reply with the xmsg reply tool`
     - Attempt push delivery via target adapter:
       - **Claude:**
         - Verify sender session is live in `~/.claude/sessions` and `/proc/<pid>/stat`.
         - If dead or socket missing -> `push_outcome = "sender_gone"`.
         - If alive, encode line (`encode_transport_line`) and write to socket.
         - If write succeeds -> `push_outcome = "pushed"`; if socket error -> `push_outcome = "push_failed"`.
       - **Antigravity (Agy):**
         - Verify session is live via presence lock and registered in `AgyStore`.
         - If unregistered or lock dropped -> `push_outcome = "sender_gone"`.
         - If registered, invoke `deliver_agy` with `new_message_id` and header line.
         - If `deliver_agy` succeeds -> `push_outcome = "pushed"`; else -> `push_outcome = "push_failed"`.
       - **Pi:**
         - Verify Pi process is live via `/proc/<pid>/cmdline` and starttime.
         - If dead -> `push_outcome = "sender_gone"`.
         - If alive, insert `PiPendingMessage` into `pi_pending_messages` with new `message_id`.
         - If queue full -> `push_outcome = "push_failed"`.
         - If inserted -> notify `pi_notify_tx`, `push_outcome = "pushed"`.
     - If `push_outcome == "pushed"`:
       - Insert a new `MessageRecord` into `messages`:
         - `id`: `new_message_id`
         - `session_id`: `return_session_id`
         - `recipient_harness`: `return_harness`
         - `thread_id`: inherited `thread_id`
         - `return_harness`: `Some(caller.harness)`
         - `return_session_id`: `Some(caller.session_id)`
         - `push_replies`: `true`
         - `outcome`: `"delivered"`
4. Store `push_outcome` and `pushed_message_id` on the `replies` row.
5. Notify `notify_tx` for HTTP long-pollers.

### 2.4 Schema Migrations
In `storage::init_db`:
1. Check columns of `messages` via `PRAGMA table_info(messages)`:
   - Add `return_harness TEXT` if missing.
   - Add `return_session_id TEXT` if missing.
   - Add `push_replies INTEGER NOT NULL DEFAULT 1` if missing.
   - Add `thread_id TEXT NOT NULL DEFAULT ''` if missing.
2. Check columns of `replies` via `PRAGMA table_info(replies)`:
   - Add `push_outcome TEXT` if missing.
   - Add `pushed_message_id TEXT` if missing.

## 3. Acceptance Oracles & Test Coverage

### §3a Gating Oracle Tests (`tests/gate_u8_replies.rs`)
1. **Attested Claude Round-Trip Push:**
   - Stand-in session A (Claude) sends to session B (Claude) via `agent.sock`.
   - Session B replies via `agent.sock`.
   - Assert: Reply is pushed into Session A's stand-in socket with Session B's badge and reply header line.
   - Assert: Reply has `push_outcome = "pushed"`.
   - Assert: Pushed reply created a new `message_id` that is repliable by Session A.
2. **Anonymous HTTP No-Push:**
   - Anonymous caller sends via HTTP `POST /v1/sessions/{ref}/messages`.
   - Session B replies via `agent.sock`.
   - Assert: No push is attempted (inbox untouched), `push_outcome` is null/empty.
   - Assert: `GET /v1/messages/{id}` and `GET /v1/messages/{id}/replies` return the reply.
3. **Strict Rejection/Disregard of Return Address Overrides:**
   - Caller on `agent.sock` passes `return_to: "evil"` or `return_address: "evil"`.
   - Assert: Push is delivered strictly to the kernel-attested sender session, never to the injected address.
4. **Push Opt-Out (`push_replies = false`):**
   - Caller on `agent.sock` sends with `push_replies: false`.
   - Recipient replies.
   - Assert: No push is delivered, `push_outcome = "disabled"`.
5. **Sender Gone Handling:**
   - Caller A sends to B.
   - Caller A terminates / socket removed before B replies.
   - B replies.
   - Assert: Reply is recorded in SQLite with `push_outcome = "sender_gone"`.
6. **Cross-Harness Push:**
   - Pi sender registers, sends to Claude recipient. Claude replies -> pushed into Pi pending queue with Pi notification.
   - Claude sender sends to Agy recipient. Agy replies -> pushed into Claude inbox.
