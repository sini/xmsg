## 1. Scope & System Boundaries

### 1.1 In-Scope
1. **Extension Architecture (`extensions/pi/`)**:
   - `xmsg-pi` extension shipped in `extensions/pi/` (not installed globally).
   - Connects to `$XDG_RUNTIME_DIR/xmsg/register.sock` (or `/tmp/xmsg-$UID/register.sock`).
   - Registers session with server using peer credentials.
   - Long-polls socket for incoming messages.
   - Injects delivered messages into Pi session via `pi.sendUserMessage(envelope)`.
   - Registers `reply` tool via `pi.registerTool` allowing model to reply to messages by `message_id`.
2. **Server-Side Queue & SQLite Storage**:
   - SQLite table `pi_pending_messages` (or integrated message queue) holding pending deliveries per Pi session with TTL.
   - HTTP delivery (`POST /v1/sessions/{ref}/messages`) targeting a `pi` session queues the message and notifies active socket connection.
3. **Registration & Process Verification**:
   - Peer connects to `register.sock`.
   - `SO_PEERCRED` provides peer PID.
   - Server checks `/proc/<pid>/cmdline` and `/proc/<pid>/stat` to verify:
     - Peer UID matches server UID.
     - Process is a running `pi` instance.
     - Captures process start time (`proc_start`) for liveness pinning.
   - In-memory active Pi sessions store tracking connection, session ID, session name, and liveness.
4. **Pull-Based Delivery Protocol**:
   - Framed JSON line protocol over the registration stream or long-poll socket connection.
   - Delivery envelope matches §9.4 plain header:
     `[xmsg] from=... message_id=... — reply with the xmsg reply tool\n\n<body>`
5. **Gating Oracles**:
   - Rust tests for registration accept/reject, process validation, SQLite queue, TTL purge, and socket long-polling.
   - Extension tests verifying tool registration, long-poll dispatch, and `sendUserMessage` invocation against mock `ExtensionAPI`.

### 1.2 Out of Scope
- No modification of `nix-config` or global system packages.
- No global installation of `xmsg-pi` extension.
- No supervision or spawning of `pi` sessions by `xmsg`.

## 2. Protocols & Schemas

### 2.1 Wire Schemas (`register.sock`)

#### Registration Request (`pi -> server`)
```json
{
  "harness": "pi",
  "sessionId": "pi-session-abc123",
  "sessionName": "my-pi-worker",
  "cwd": "/workspace/project"
}
```

#### Server Registration Response (`server -> pi`)
```json
{
  "status": "ok",
  "sessionId": "pi-session-abc123"
}
```

#### Pull / Long-Poll Command (`pi -> server`)
```json
{
  "action": "poll",
  "sessionId": "pi-session-abc123",
  "waitSecs": 30
}
```

#### Delivery Payload (`server -> pi`)
```json
{
  "action": "deliver",
  "messageId": "01M49...",
  "fromName": "xmsg@host · claude-orch",
  "text": "Hello pi agent!",
  "envelope": "[xmsg] from=xmsg@host · claude-orch message_id=01M49... — reply with the xmsg reply tool\n\nHello pi agent!"
}
```

#### Ack Payload (`pi -> server`)
```json
{
  "action": "ack",
  "messageId": "01M49..."
}
```

### 2.2 Storage Schema (`src/storage.rs`)

```sql
CREATE TABLE IF NOT EXISTS pi_pending_messages (
    id TEXT PRIMARY KEY,
    session_id TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    from_name TEXT NOT NULL,
    bytes INTEGER NOT NULL,
    text TEXT NOT NULL,
    envelope TEXT NOT NULL,
    delivered_at INTEGER
);

CREATE INDEX IF NOT EXISTS idx_pi_pending_session ON pi_pending_messages(session_id, delivered_at);
```

## 3. Core Mechanisms

### 3.1 Process Validation for Pi
1. `stream.peer_cred()` yields `peer_uid` and `peer_pid`.
2. Check `peer_uid == my_uid`.
3. Inspect `/proc/<peer_pid>/cmdline`:
   - Checks that cmdline contains `pi` or `node` running `pi`.
4. Inspect `/proc/<peer_pid>/stat`:
   - Extracts field 22 (`starttime`).
   - Pins session liveness to `(peer_pid, starttime)`.

### 3.2 Long-Poll Socket Loop
1. The extension opens a persistent connection to `register.sock`.
2. Sends `{ "harness": "pi", "sessionId": ... }`.
3. Server registers the session in `PiStore` (mapping `sessionId -> PiSessionState`).
4. Loop:
   - Extension sends `{ "action": "poll", "sessionId": ..., "waitSecs": 30 }`.
   - Server checks SQLite for undelivered messages for this `sessionId`.
   - If message exists: return immediately and mark delivered.
   - If no message: await `broadcast::Receiver` notification or timeout.
   - On timeout: return `{ "action": "poll_timeout" }`.
   - On message: return `{ "action": "deliver", ... }`.
   - Extension receives delivery, calls `pi.sendUserMessage(msg.envelope)`, and responds with `{ "action": "ack", ... }`.

### 3.3 Extension `reply` Tool
Extension registers `reply` tool with TypeBox schema:
```typescript
pi.registerTool({
  name: "reply",
  description: "Reply to a received cross-session message by message_id",
  parameters: Type.Object({
    message_id: Type.String({ description: "The ID of the message being replied to" }),
    text: Type.String({ description: "Reply content" }),
  }),
  async execute(_id, params, _signal, _onUpdate, _ctx) {
    // Posts to http://127.0.0.1:7787/v1/messages/{message_id}/replies
    // with sessionRef: sessionId
  }
});
```

## 4. Test Oracles & Gating Criteria

1. **Pi Process Verification (`tests/pi_proc.rs`)**:
   - Unit tests against mock `/proc/<pid>/cmdline` and `stat` verifying detection of `pi` and extraction of `starttime`.
   - Rejects non-pi processes or mismatched UIDs.
2. **SQLite Queue & TTL Purge (`tests/pi_queue.rs`)**:
   - Enqueuing pending messages for Pi sessions.
   - Long-poll retrieval returns queued messages in FIFO order.
   - Acknowledged messages marked delivered.
   - Expired messages purged by TTL.
3. **End-to-End Registration & Delivery (`tests/e2e_pi.rs`)**:
   - Simulates extension socket connection.
   - POSTs message to `/v1/sessions/{pi_session}/messages` -> HTTP 202.
   - Asserts socket waiter receives delivery payload with §9.4 envelope.
   - Reply to delivered message succeeds; non-recipient reply rejected with 403.
4. **Extension Unit Test (`extensions/pi/test.ts` or `test.js`)**:
   - Mock `ExtensionAPI` verifying `registerTool("reply")` and `sendUserMessage` calls.
