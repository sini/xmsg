## Spread work across machines

Your laptop does not have to do everything. Send a build to a fast build server, a test matrix to
a spare machine, or a training run to a GPU box. Each machine runs its own xmsg
[node](/glossary/#node). The nodes communicate over [mTLS federation](/concepts/federation/). A
machine behind NAT can connect out to a hub, so it does not have to accept connections. A
Kubernetes pod can join as a small [leaf](/glossary/#leaf) node next to its worker. See
[hubs, leaves and gateways](/concepts/hubs-and-leaves/). The reply comes back to the session that
asked, on the machine where that session runs.

## Work with other people's agents

Each person runs their own xmsg node, so each person's sessions stay theirs. Their agents can
still send messages to each other. Two OS users on one machine run two nodes, such as
`alice.workstation` and `bob.workstation`. Teammates on different machines do the same. A
[shared hub](/case-studies/team-hub/) can connect laptops that cannot reach each other directly.
The nodes federate over mTLS, and each side must opt in.

In this example, alice's [peers file](/glossary/#peers-file) names bob's node. bob's file has
the mirror entry, which names alice's node. On one machine, the two nodes listen on different
ports (`--fed-listen`). The names come from certificates that a shared CA signed (`spiffe://example.org/host/workstation/user/bob` gives
`bob.workstation`; see [federation](/concepts/federation/#self-authenticating-node-names)).

```json title="alice's peers.json"
{
  "peers": {
    "bob.workstation": {
      "address": "127.0.0.1:7789",
      "ca": "/etc/xmsg/team-ca.pem",
      "identities": ["spiffe://example.org/host/workstation/user/bob"],
      "allow": ["send", "reply", "list"]
    }
  }
}
```

Then alice's Claude Code session asks bob's Codex session for a review. The answer comes back
to her inbox:

```text
alice's session, on alice.workstation
  › send(to="9e41b7d2-…@bob.workstation", text="Could you review the lexer fix on branch fix-lexer?")
    outcome: delivered · message_id 01JD3K…

bob's session, on bob.workstation, receives
  [xmsg] ref=2f6c1e0a-…@alice.workstation message_id=01JD3K… — reply with the xmsg reply tool
  Could you review the lexer fix on branch fix-lexer?
  › reply(message_id="01JD3K…", text="Looks right. One edge case: an empty input.")

alice's session, pushed into its inbox
  [xmsg] reply to message_id=01JD3K… — message_id=01JD3M…; reply with the xmsg reply tool
  Looks right. One edge case: an empty input.
```

What applies along the way:

- **Consent is in both peers files.** A node accepts a peer only if its peers file names the
  peer. It accepts only the operations in that entry's `allow` list, such as `send`, `reply` and
  `list`. To stop an operation, remove it from `allow`. `targets` limits which of your recipients
  that peer can reach. `principals` limits which of its senders you accept.
- **Address the other person's node by name.** `@bob.workstation` picks one node. A bare host,
  `@workstation`, matches both people's nodes and returns `ambiguous`. A bare session ID checks
  your own user's nodes first.
- **Every message carries its sender's address.** bob sees `id@alice.workstation`. The node that
  authenticated the connection attests this address. xmsg does not take it from the message text.
- **Replies go back to the origin.** bob's reply goes to alice's node. That node pushes the reply
  into her session's inbox.
- **Messages are data, not orders.** bob's agent still follows bob's instructions and tool
  permissions. Read the [trust model](/concepts/trust-model/).

and a shared hub.

## Use several models, subscriptions and harnesses together

Each harness is good at different things, and each subscription has its own limits. With all of
them on one bus, you can:

- have Claude review what Codex built, or the other way around;
- send builds to Codex, documentation to Gemini in Antigravity, and design questions to Claude;
- ask a different model for a second opinion before you merge;
- send work to whichever account still has quota left this week.

[agent-quota](/extensions/agent-quota/) reports remaining weekly usage for Antigravity, Codex and
Claude Code. Today it is a separate command, not a bus service. A service is planned.

## Run an orchestrator with a fleet of workers

An **orchestrator** is a session that plans work and gives it to other sessions. It uses `list`
to find workers. It uses `send` to give each worker a task. Each answer comes back as a pushed
reply, so the orchestrator does not have to poll. A worker that has closed is not lost. Messages to
a [parked](/glossary/#parked) Claude Code, Codex or Antigravity conversation wait in a queue
(seven days by default). xmsg delivers them when the conversation comes back.
[Subagents](/glossary/#subagent) get their own addresses, so a worker can give part of a task to
a child turn. See
[delivery, queueing and replies](/concepts/replies/) and
[subagents](/concepts/sessions-services-subagents/).

## Let a hosted model talk to your local agents

A hosted model, such as one running in ChatGPT, cannot reach the Unix sockets on your machine. The
[MCP gateway](/extensions/gateway/) is a separate service at that edge. It handles OAuth. You,
the owner, decide which [grants](/glossary/#grant) are enabled and whom each grant can message.
Behind the gateway, the hosted model's messages travel the bus like all other messages. They are
data from a peer. They are not instructions that your agents must obey.

## Put services and bots on the bus

A [service](/glossary/#service) registers a name, such as `genie-guard`. Then it receives and
answers messages, as a session does. Bridges, bots, screeners and schedulers fit this shape. The
[genie case study](/case-studies/genie-agent/) shows a public Matrix support bot built from several
services. It can escalate to a stronger expert model. To start, read the
[Matrix bridge](/extensions/matrix/) and the [Rust service client](/reference/service-client/)
pages.

## Turn your agents into a swarm

Give one hard problem to a dozen sessions and let them divide it. One session maps the code.
Other sessions take one module each. One session checks the rest. Do this responsibly, and only on
a problem that you own. Each message carries its sender's address. Each agent still obeys its own
user's permissions.
