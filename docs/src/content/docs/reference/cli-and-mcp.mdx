### Operator commands

These commands use the daemon's existing HTTP Unix socket, on Linux and macOS.
Pass `--http-sock PATH` to any operator command or set `XMSG_HTTP_SOCK`; otherwise
the CLI uses the daemon's runtime-directory default, including the macOS fallback.

```bash
xmsg list [--node NODE] [--kind service|instance|subagent] [--status live|inactive] [--json]
xmsg send RECIPIENT [TEXT|-] [--from LABEL] [--idempotency-key KEY] [--json]
xmsg replies MESSAGE_ID [--wait SECONDS] [--json]
xmsg show MESSAGE_ID [--json]
```

- `list` prints a recipient table with address, kind, label, status, and node, followed
  by the nodes' status. The default is live recipients; filters narrow the daemon's view.
- `send` prints the message ID, outcome, and resolved recipient address. `-` or omitted
  text reads stdin through EOF, preserving newlines. An idempotency key reuses the same
  send for identical sender, recipient, and text; requests are not automatically retried.
  Outcomes are `delivered`, `queued`, or `pending`;
  `pending` means the daemon has not reported a final delivery outcome.
- `replies` prints stored reply records, optionally waiting `0..60` seconds for the first
  reply. `show` prints message metadata and replies. Both use formatted JSON by default.

`--json` emits the server's response as compact JSON on one line, preserving its field
names and object/array shape. Refusals exit non-zero and retain the server error code;
JSON mode also writes the server's error object to stdout.

`--from` is a plain display label, defaulting to `cli`; values containing `@` or `/` are
rejected. An ordinary shell caller is anonymous and appears as `cli · anon@node`.
The daemon's existing attribution and authorization rules apply to traced callers.
Writing a reply from an anonymous
shell is not an operator CLI command; agents and registered services use their existing
reply interfaces.


### `xmsg service exec`

Runs an optional ordinary service over the daemon's existing registration and agent
sockets. Nothing starts automatically or changes the daemon's normal behavior.

```bash
xmsg service exec --name agent-quota -- agent-quota --json
xmsg service exec --name snapshot --timeout-ms 2000 --max-output-bytes 65536 -- /path/to/producer --json
```

`--register-sock` or `XMSG_REGISTER_SOCK` selects the registration socket, otherwise
the daemon's runtime-directory default is used. `--agent-sock` or `XMSG_AGENT_SOCK`
selects the agent socket, otherwise it is beside the registration socket.
Explicit socket paths must be absolute.
The daemon applies its ordinary service registration, executable and peer-access rules.

Each delivered request runs the fixed program and literal arguments after `--`.
Request text is ignored, the program receives no stdin, and stderr is discarded.
Successful UTF-8 stdout is the reply, unchanged, including whitespace. Configure a
command whose stdout is intended for its requesters; the runner adds no environment
dump or child diagnostics to responses.

The default runtime bound is `75000` milliseconds. The default stdout limit is
`65536` bytes; `--max-output-bytes` accepts `64` through `1048576` and is also capped by the
daemon's reported message limit. Timeout or output overflow kills and waits for the
owned child. Spawn, I/O or nonzero-exit failure, empty stdout, and invalid UTF-8 produce
one static JSON response instead:

```json
{"status":"unknown","error":"timeout"}
```

Other error codes are `output_limit`, `command_failed`, `empty_output`, and
`invalid_utf8`. No quota or other producer value is guessed on failure.

The runner replies with a stable per-message idempotency key, then ACKs the request.
It retains one pending response across transport reconnects and retries an uncertain
reply with the same key and bytes. Commands must tolerate re-execution after a process
crash; pending responses are retained in memory. Interrupt and termination signals
stop the runner and reap an active owned command.
Permanent daemon refusals and configuration/trust failures exit non-zero with a
content-free diagnostic instead of retrying the same rejected response indefinitely.

For quota service use, the producer owns account hashes, measurement age, missing/stale
readings and the JSON schema. The transport relays that output as supplied; per-user
installation and enabling remain deployment configuration.

### `xmsg check-peers`

Validates a `peers.json` file against all naming, trust-model (`pin` vs. `ca` + `identities`), and
non-overlap rules that `xmsg serve` enforces, exiting `0` on success or non-zero naming the failure:

Use it in CI or before a deploy.

```bash
xmsg check-peers /path/to/peers.json --fed-cert /path/to/node.crt
```

## MCP server tools (`xmsg mcp`)

`xmsg mcp` exposes five tools over stdio JSON-RPC (or `[reply, replies]` when started with
`--reply-only` / `XMSG_REPLY_ONLY=1`):

### `list(name?, node?, kind?, status?, within?)`

Lists recipients the caller may see on this node and every reachable peer:

- **`status`:** `"live"` (default, each entry carries `registered_at` in epoch seconds) or
  `"inactive"` (shows `parked` and `closed` instances seen within `within` seconds, default
  `86400` = 24 hours, capped at the reply TTL, each carrying `last_seen`).
- **`kind`:** Filter by `"service"`, `"instance"`, or `"subagent"`.
- **`name`:** Filter by service name or instance label.
- **`node`:** An exact canonical name or local nickname queries one node. A bare-host selector queries all matching nodes in the current view; see [node selectors](/concepts/addressing/#node-selectors).
- **Returns:** `{ recipients: [{ address, kind, harness?, label?, status, node, user, registered_at | last_seen }], nodes: [{ node, status, detail? }] }`.

### `send(to, text, as_agent?)`

Sends a message to `<id or name>[@<node>]` (at most one `@`):

- **`to`:** An instance UUID (optionally `~n`), a delegated sub-address (`<P>/<child>`), a service
  name, or a unique live instance label, optionally followed by `@node`. Passing `ref`, `from`, or a
  label containing `' · '` is refused with a migration hint.
- **`as_agent`:** Set automatically by the harness `PreToolUse` hook when called by a subagent.
- **Returns:** `{ message_id, address, outcome }` where `outcome` is `"delivered"`, `"queued"`, or `"pending"`.
  Use the returned `address` for follow-ups.

### `reply(message_id, text, as_agent?)`

Answers `message_id`'s other party symmetrically (if you received the message, answers the sender;
if you sent it, sends a follow-up to the recipient in the same exchange):

- **Returns:** `{ bytes, messageId, inReplyTo, outcome }`, where `messageId` is the new reply's
  ULID and `inReplyTo` is `message_id`.

### `replies(message_id, wait?)`

Reads stored replies to `message_id`, optionally waiting up to `wait` seconds (clamped to `0..=60`)
for the first reply.

### `inbox(wait?, as_agent?)`

Drains unexpired messages queued for a bound subagent's `<P>/<child>@<node>` turn mailbox while its
turn is active, waiting up to `wait` seconds (clamped to `0..=60`) for the first message, and marks
drained messages `delivered`:

- **Returns:** `{ address, messages: [{ id, from, body, created_at }] }`.
