### Operator commands

These commands use the daemon's HTTP Unix socket, on Linux and macOS. To select the socket, pass
`--http-sock PATH` to the command or set `XMSG_HTTP_SOCK`. Otherwise the CLI uses the daemon's
runtime-directory default, which includes the macOS fallback.

```bash
xmsg list [--node NODE] [--kind service|instance|subagent] [--status live|inactive] [--json]
xmsg send RECIPIENT [TEXT|-] [--from LABEL] [--idempotency-key KEY] [--json]
xmsg replies MESSAGE_ID [--wait SECONDS] [--json]
xmsg show MESSAGE_ID [--json]
```

- `list` prints a recipient table with the address, kind, label, status and node. Then it
  prints the status of the nodes. By default, it shows live recipients. Filters make the
  daemon's view smaller.
- `send` prints the message ID, the outcome and the resolved recipient address. With `-`, or with
  no text, it reads stdin until EOF and keeps the newlines. An idempotency key uses the same send
  again for the same sender, recipient and text. The CLI does not retry requests automatically.
  The outcomes are `delivered`, `queued` and `pending`. `pending` means that the daemon has not
  reported a final delivery outcome.
- `replies` prints the stored reply records. It can wait `0..60` seconds for the first reply.
  `show` prints the message metadata and the replies. By default, both print formatted JSON.

`--json` writes the server's response as compact JSON on one line. It keeps the field names and
the object and array shape. A refusal exits non-zero and keeps the server error code. In JSON
mode, the CLI also writes the server's error object to stdout.

`--from` is a plain display label. The default is `cli`. The CLI refuses a value that contains
`@` or `/`. An ordinary shell caller is [anonymous](/glossary/#anonymous-sender) and shows as
`cli · anon@node`. The daemon's attribution and authorization rules apply to traced callers.
There is no operator CLI command to reply from an anonymous shell. Agents and registered services
use their own reply interfaces.


### `xmsg watch` (planned)

A local recipient roster and metadata exchange timeline:

```sh
xmsg watch
xmsg watch --node YOUR_NODE --interval 5
xmsg watch --once --plain --http-sock /absolute/path/to/http.sock
```

`--http-sock` or `XMSG_HTTP_SOCK` selects the existing HTTP Unix socket. The default refresh
interval is two seconds; `--interval` accepts 1–60 seconds. Ctrl-C exits. `--once` prints one
snapshot; `--plain` disables terminal redraw styling. Non-terminal output is plain.

The roster polls health and live/inactive recipients. It shows reported state, node errors,
partial results, truncation and the age of its last successful refresh. A failed refresh keeps
old rows visibly stale; a successful health check alone does not make the roster fresh. It
retains at most 1,000 rows and rejects response bodies over 4 MiB. Server-supplied names,
labels and other fields have terminal controls escaped before display.

The timeline reads the local [observation journal](/reference/http-and-sockets/#local-observation-journal-planned)
through `GET /v1/observe/events`. It shows source/destination references, message and reply
correlation, times, event kinds and stored outcomes. Each refresh fetches at most two bounded
pages and keeps at most 1,000 timeline rows. It displays gaps, dropped counters, local
truncation and whether it is still catching up. Roster and timeline have separate freshness
ages; a failed timeline refresh keeps its old cursor and visibly stale rows. Older daemons
returning `404` leave the roster usable and mark the timeline unsupported.

The journal is observation, not complete history: a crash or a full queue can lose metadata,
and writer restart is an explicit unknown-loss gap. Stored delivery outcomes do not mean
agent-read or task-complete. Watch reads no bodies or transcripts and does not send,
acknowledge or consume messages or open a listener. Use `xmsg show MESSAGE_ID` for deliberate
known-ID inspection. Existing caller-attribution rules still apply.

### `xmsg service exec`

Runs an optional ordinary service over the daemon's registration and agent sockets. Nothing
starts automatically. The daemon's normal behavior does not change.

```bash
xmsg service exec --name agent-quota -- agent-quota --json
xmsg service exec --name snapshot --timeout-ms 2000 --max-output-bytes 65536 -- /path/to/producer --json
```

`--register-sock` or `XMSG_REGISTER_SOCK` selects the registration socket. Otherwise the runner
uses the daemon's runtime-directory default. `--agent-sock` or `XMSG_AGENT_SOCK` selects the agent
socket. Otherwise the agent socket is next to the registration socket. An explicit socket path
must be absolute. The daemon applies its ordinary rules for service registration, executables and
peer access.

Each delivered request runs the fixed program and the literal arguments after `--`. The runner
ignores the request text. The program gets no stdin. The runner discards stderr. On success, the
UTF-8 stdout is the reply, unchanged, with its whitespace. Configure a command whose stdout is
meant for its requesters. The runner adds no environment dump and no child diagnostics to
responses.

The default time limit is `75000` milliseconds. The default stdout limit is `65536` bytes.
`--max-output-bytes` accepts `64` through `1048576`. The daemon's reported message limit is also a
maximum. On a timeout or an output overflow, the runner kills the owned child and waits for it.
These failures give one static JSON response: a spawn, I/O or nonzero-exit failure, empty stdout,
and UTF-8 that is not valid:

```json
{"status":"unknown","error":"timeout"}
```

The other error codes are `output_limit`, `command_failed`, `empty_output` and `invalid_utf8`.
On a failure, the runner does not guess a quota or another producer value.

The runner replies with a stable idempotency key for each message. Then it ACKs the request.
It keeps one pending response across transport reconnects. It retries an uncertain reply with the
same key and bytes. The runner keeps pending responses in memory. Thus a command must be safe to
run again after a process crash. Interrupt and termination signals stop the runner and reap an
active owned command. A permanent daemon refusal, or a configuration or trust failure, makes the
runner exit non-zero with a diagnostic that has no content. The runner does not retry the same
refused response without end.

For a quota service, the producer owns the account hashes, the measurement age, missing or
stale readings, and the JSON schema. The transport relays that output as it is. Installation and
enablement for each user are deployment configuration.

### `xmsg check-peers`

Validates a `peers.json` file against the rules that `xmsg serve` enforces: naming, the trust
model (`pin` or `ca` + `identities`) and non-overlap. It exits `0` on success. On a failure, it
exits non-zero and names the failure. Use it in CI or before a deploy:

```bash
xmsg check-peers /path/to/peers.json --fed-cert /path/to/node.crt
```

## MCP server tools (`xmsg mcp`)

`xmsg mcp` gives five tools over stdio JSON-RPC. With `--reply-only` / `XMSG_REPLY_ONLY=1`, it
gives only `reply` and `replies`:

### `list(name?, node?, kind?, status?, within?)`

Lists recipients the caller may see on this node and every reachable peer:

- **`status`:** `"live"` or `"inactive"`.
  - `"live"` is the default. Each entry has `registered_at`, in epoch seconds.
  - `"inactive"` shows the `parked` and `closed` instances that xmsg saw within `within` seconds.
    The default is `86400` (24 hours). The maximum is the reply TTL. Each entry has `last_seen`.
    **Planned:** startup Codex roots with queued recovery work appear here as
    `awaiting_reattestation` until verified delivery can resume. They are excluded from the default
    live list; deliberate parking and revoked or closed roots keep their existing states.
- **`kind`:** Filter by `"service"`, `"instance"`, or `"subagent"`.
- **`name`:** Filter by service name or instance label.
- **`node`:** An exact canonical name or local nickname queries one node. A bare-host selector queries all matching nodes in the current view; see [node selectors](/concepts/addressing/#node-selectors).
- **Returns:** `{ recipients: [{ address, kind, harness?, label?, status, node, user, registered_at | last_seen }], nodes: [{ node, status, detail? }] }`.

### `send(to, text, as_agent?)`

Sends a message to `<id or name>[@<node>]` (at most one `@`):

- **`to`:** An instance UUID (with an optional `~n`), a delegated sub-address (`<P>/<child>`), a
  service name, or a unique live instance label. `@node` can follow it. xmsg refuses `ref`, `from`
  and a label that contains `' · '`, with a migration hint.
- **`as_agent`:** When a subagent calls the tool, the harness `PreToolUse` hook sets it
  automatically.
- **Returns:** `{ message_id, address, outcome }` where `outcome` is `"delivered"`, `"queued"`, or `"pending"`.
  Use the returned `address` for follow-ups.

### `reply(message_id, text, as_agent?)`

Answers the other party of `message_id`. If you received the message, the reply goes to the
sender. If you sent it, the reply is a follow-up to the recipient in the same exchange:

- **Returns:** `{ bytes, messageId, inReplyTo, outcome }`, where `messageId` is the new reply's
  ULID and `inReplyTo` is `message_id`.

### `replies(message_id, wait?)`

Reads the stored replies to `message_id`. It can wait up to `wait` seconds (`0..=60`) for the
first reply.

### `inbox(wait?, as_agent?)`

During a bound subagent's active turn, reads the messages in its `<P>/<child>@<node>`
[turn mailbox](/glossary/#turn-mailbox) that have not expired. It can wait up to `wait` seconds
(`0..=60`) for the first message. It marks each message that it reads `delivered`:

- **Returns:** `{ address, messages: [{ id, from, body, created_at }] }`.

### Planned: aggregate admitted-leaf mailbox budgets

`xmsg serve --admitted-mailbox-max-rows 100000 --admitted-mailbox-max-bytes 671088640`
bounds all pattern-admitted leaf mailboxes together. Zero refuses new admitted
rows. The existing per-leaf budgets still apply; concrete leaf entries do not
consume the aggregate admitted budget. Rejection keeps existing messages and
returns `429 peer_mailbox_full`. See
[hub admission](/concepts/hubs-and-leaves/#planned-enrolled-nodes-and-bounded-hub-mailboxes).

## Planned: enrollment commands

[Enrollment](/operations/enrollment-ca/) issues a host certificate after OIDC
sign-in. It does not distribute the machine's private key.

| Command | Purpose |
| --- | --- |
| `xmsg enroll URL` | Browser sign-in and local P-256 key/CSR creation; requires `--fingerprint sha256:<hex>` or `--root-file FILE` |
| `xmsg enroll --renew` | One renewal using saved state; no URL or IdP login required |
| `xmsg enroll-ca --enroll-ca-dir DIR init` | Initialize the independent root and print JSON `root_file`/`fingerprint` |
| `xmsg enroll-ca --enroll-ca-dir DIR --enroll-policy FILE list` | Inspect certificate/SPKI and supersession records |
| `xmsg enroll-ca --enroll-ca-dir DIR --enroll-policy FILE bind USER PROVIDER SUB` | Add an explicit identity alias for a bound user |
| `xmsg enroll-ca --enroll-ca-dir DIR --enroll-policy FILE unbind USER` | Remove a user's binding and aliases; not instant peer revocation |

`enroll` accepts `--flow loopback|paste|device` (default `loopback`), `--provider NAME`,
`--host NAME` and `--state-dir DIR`. The default state directory is
`$XDG_STATE_HOME/xmsg/enroll`, falling back to `~/.local/state/xmsg/enroll`.
`--provider` is optional only with one configured provider. Device enrollment is
planned, disabled by default, and requires independent local CA approval. Fresh enrollment does not overwrite `fed.key`; choose a new state directory
for a new key/login. `enroll-ca` accepts `--db-path FILE` to select the serving
CA's database; `init` needs no policy.

Planned live-daemon device commands:

```sh
xmsg enroll-ca [--http-sock SOCKET] pending
xmsg enroll-ca [--http-sock SOCKET] approve REQUEST_ID --user USER --host HOST --spki-sha256 DIGEST
xmsg enroll-ca [--http-sock SOCKET] deny REQUEST_ID
```

These use mode-0600, UID-checked `http.sock` and need no `--enroll-ca-dir`,
`--enroll-policy` or root key. They are unavailable over TCP, enrollment HTTPS,
MCP and federation. The older commands above retain their requirements.
`pending` exposes only authenticated requests awaiting approval. Approval must
match the verified user, requested host, key and current policy; denial, expiry,
policy drift and replay refuse issuance. Before authentication the client shows
`policy user: pending verification`; afterwards it shows the verified policy
user and `awaiting CA approval`.

Provider policy requires both `device.enabled: true` and a distinct
`clients.device` entry; registration alone does not enable it. Disabled or
unsupported providers refuse and suggest `--flow paste`, without automatic
fallback. Google device support remains unverified pending owner-run real-provider
acceptance. These device command examples are illustrative pending final fixture
verification. See [device setup and bounds](/operations/enrollment-ca/#planned-device-sign-in-from-a-remote-terminal).

| Planned `serve` flag | Meaning |
| --- | --- |
| `--enroll-listen IP:PORT` | Separate enrollment HTTPS listener, not the federation port |
| `--enroll-ca-dir DIR` | Owner-private `root.key` and public `root.crt` directory |
| `--enroll-policy FILE` | Provider, user mapping, deny, lifetime and rate policy |
| `--enroll-state DIR` | Use an enrolled client's saved cert/key and automatic renewal |

Supply the first three flags together with federation credentials, a peers file
and `--fed-listen`. `--enroll-state` conflicts with explicit `--fed-cert` and
`--fed-key`; it still needs the peers file and federation listener. See the
[setup and renewal example](/operations/enrollment-ca/#enroll-the-machine).
