### Operator commands

These commands use the daemon's HTTP Unix socket, on Linux and macOS. To select the socket, pass
`--http-sock PATH` to the command or set `XMSG_HTTP_SOCK`. Otherwise the CLI uses the daemon's
runtime-directory default, which includes the macOS fallback.

```bash
xmsg list [--node NODE] [--kind service|instance|subagent] [--status live|inactive] [--limit 1..500] [--json]
xmsg send RECIPIENT [TEXT|-] [--from LABEL] [--idempotency-key KEY] [--json]
xmsg replies MESSAGE_ID [--wait SECONDS] [--json]
xmsg show MESSAGE_ID [--json]
```

- `list` prints a recipient table with the address, kind, label, status and node. Then it
  prints the status of the nodes. By default, it shows live recipients. Filters make the
  daemon's view smaller. Listing reconciles claims and registrations, and can deliver queued
  messages or fork notices on this node and on peers it asks. Use the planned local snapshot
  mode below when observation must not drive reconciliation.
- `send` prints the message ID, the outcome and the resolved recipient address. With `-`, or with
  no text, it reads stdin until EOF and keeps the newlines. An idempotency key uses the same send
  again for the same sender, recipient and text. The CLI does not retry requests automatically.
  The outcomes are `delivered`, `queued` and `pending`. `pending` means that the daemon has not
  reported a final delivery outcome.
- `replies` prints the stored reply records. It can wait `0..60` seconds for the first reply.
  `show` prints the message metadata and the replies. By default, both print formatted JSON.

`--json` writes the server's response as compact JSON on one line. It keeps the field names and
the object and array shape. A refusal exits non-zero and keeps the server error code. In JSON
mode, the CLI also writes the server's error object to stdout.

`--from` is a plain display label. The default is `cli`. The CLI refuses a value that contains
`@` or `/`. An ordinary shell caller is [anonymous](/glossary/#anonymous-sender) and shows as
`cli · anon@node`. The daemon's attribution and authorization rules apply to traced callers.
There is no operator CLI command to reply from an anonymous shell. Agents and registered services
use their own reply interfaces.


### `xmsg watch`

<Status id="xmsg.watch" />

A read-only local registration snapshot and metadata exchange timeline:

```sh
xmsg watch
xmsg watch --node local --interval 5
xmsg watch --once --plain --http-sock /absolute/path/to/http.sock
```

`--http-sock` or `XMSG_HTTP_SOCK` selects the existing HTTP Unix socket. The default refresh
interval is two seconds; `--interval` accepts 1–60 seconds. Ctrl-C exits. `--once` prints one
snapshot; `--plain` disables terminal redraw styling. Non-terminal output is plain.

The roster polls health and the [read-only local snapshot](/reference/http-and-sockets/#read-only-local-recipient-snapshot).
It shows already-observed registrations and last-seen metadata, marked partial. `registered`
and `seen` are recorded states, not an attestation that a session is currently alive or
reachable. Filesystem-only sessions and newly presented sessions may be absent until normal
activity reconciles them. Watch does not assign claims, prune registrations or drive delivery.

`--node` may select `local` or this daemon's canonical node name. A remote selection fails;
use `xmsg list --node REMOTE` for a live remote listing, with its reconciliation and delivery
side effects. The [fleet observer](/concepts/fleet-observer/) provides the remote view once
its collector is deployed. Watch does not contact federation peers.

The roster shows `scope: local node only`, truncation, and the age of its last successful snapshot.
A first-fetch failure before any snapshot marks the roster `UNAVAILABLE`; once a
snapshot exists, a failed refresh marks it `STALE`, prefixes node lines with
`last known:`, and keeps old rows visibly stale; a successful health check alone
does not make the roster fresh.
An older daemon that rejects the snapshot query leaves the roster unavailable: watch never
retries with the ordinary, mutating listing. It retains at most 1,000 rows and rejects response
bodies over 4 MiB. Server-supplied names, labels and other fields have terminal controls escaped
before display.

The timeline reads the local [observation journal](/reference/http-and-sockets/#local-observation-journal)
through `GET /v1/observe/events`. It shows source/destination references, message and reply
correlation, times, event kinds and stored outcomes. The `arrival` kind means the
daemon committed a queued item's delivery mark for an inbox result. It is not proof of client
receipt, agent-read or task-complete. Each refresh fetches at most two bounded
pages and keeps at most 1,000 timeline rows. It displays gaps, dropped counters
(`Loss counters: unknown` before the first successful timeline page), local
truncation and whether it is still catching up. Roster and timeline have separate freshness
ages; a failed timeline refresh keeps its old cursor and visibly stale rows. Older daemons
returning `404` leave the roster usable and mark the timeline unsupported.

The journal is observation, not complete history: a crash or a full queue can lose metadata,
and writer restart is an explicit unknown-loss gap. Stored delivery outcomes do not mean
agent-read or task-complete. Watch reads no bodies or transcripts and does not send,
acknowledge or consume messages or open a listener. Use `xmsg show MESSAGE_ID` for deliberate
known-ID inspection. Existing caller-attribution rules still apply.

### `xmsg doctor`

<Status id="xmsg.doctor" />

Checks local setup once and prints `info`, `pass`, `warn` or `fail` lines with fix hints, plus informational metadata:

```sh
xmsg doctor
xmsg doctor --json
xmsg doctor --http-sock /absolute/path/to/http.sock --db-path /absolute/path/to/xmsg.db
```

The command exits `1` if any check fails. Warnings alone exit `0`. Informational rows
do not add to the passed, warning or failed totals. `--json` reports
`checks` (each with `id`, `status`, `message` and `hint`), `passed`, `warnings`, `failed`,
`client_version`, `client_build_revision` and `not_checked`.

The always-on `collector.sqlite_engine` line reports `linked SQLite <found>; the fleet collector requires <required>` for this CLI binary. Its status is `info`, even when the versions differ; it does not affect summary counts or the exit code. It performs no file or network I/O and does not validate a collector configuration or a running collector. The collector enforces its engine requirement at startup.

Doctor displays the client and daemon crate versions and build revisions.
The daemon metadata comes from the bounded Unix-socket health response, not a process
or image-name guess. Nix builds embed the source revision; a plain Cargo build without
`XMSG_BUILD_REVISION` reports `unknown`. Missing metadata from an older daemon or an
unknown client or daemon revision produces a warning. Different known client and daemon revisions also
warn, rather than fail: check the intended deployment pin before deciding whether to
restart or upgrade. Matching crate versions such as `0.1.0` do not prove matching builds.

Optional path overrides are `--http-sock`, `--agent-sock`, `--register-sock`, `--db-path`,
`--peers-file`, `--fed-cert`, `--enroll-state` and `--enroll-ca-dir` (<Status id="xmsg.ca-health" />). Doctor checks the selected paths; it
cannot establish that a running daemon loaded those same paths or configuration.
`--fed-cert` requires `--peers-file`; `--enroll-state` names a directory containing
the existing private `enroll.json`.

Planned CA application diagnostics use `GET /v1/diagnostics/enrollment` on the
same-UID Unix socket only. They report parsed enrollment enabled state, the loaded
public root's expiry, policy-reload degradation, signing-key metadata and a count of
pending device approvals. No pending request identities or codes are included. Missing
authority evidence does not establish that enrollment is disabled.

`--enroll-ca-dir DIR` explicitly selects installed CA files when the live view is
unavailable: the bounded public `root.crt` and stat-only `root.key` metadata. The source
is `installed_not_loaded`; enabled state and pending counts stay unknown. No directory
is guessed, and file presence does not imply enabled configuration. This differs from
client `--enroll-state`. The live view takes precedence because loaded and installed
roots can differ. An override appears in `checked_paths` only when the installed
fallback was used. Key metadata must describe a regular file owned by the current UID,
at most 1 MiB, with owner-read permission and no group/other access. This cannot prove
key validity, matching, actual readability or issuance; doctor never opens the key or
issues a test certificate. The CLI's local request has a five-second budget.

Doctor reads local filesystem metadata, probes the database read-only and makes a bounded
`GET /healthz` request on the HTTP Unix socket. It also requests the explicit local
read-only process-liveness snapshot (<Status id="xmsg.recipient-snapshot" />):
`GET /v1/recipients?read_only=true&liveness=true`. Optional peer configuration uses the same
parser as `check-peers`. Optional saved enrollment metadata supplies expiry and renewal
checks; its CA probe makes a TLS handshake only. Doctor does not repair files, initialize
or migrate a database, register a service, renew credentials or send messages. It does not
call the ordinary recipient listing or enrollment-pending endpoints, which can change daemon state.

The planned liveness check aggregates **process** evidence as `live`, `gone` or `unknown`,
with counts by catalogue state and observation reason. A historical `seen` row with
`unknown` / `missing_identity` is informational: it has no stored process identity to probe,
so available `/proc` support does not make it live or gone. Other unknown evidence,
including registered rows, probe errors and unavailable backends, still warns. Gone rows
warn and have at most 20 individual lines; the aggregate reports the full total and
`and N more` when details are capped. Live and unknown rows have no individual lines.

This does not establish harness addressability, a usable Codex writer lease, message
delivery or task completion. The snapshot's `partial` flag describes catalogue scope and
is not itself a warning. Truncation, an older daemon, a cold runtime (`503`) or an unavailable
source still warns; doctor never retries through the ordinary live listing. The roster can
omit registrations, so absence is not evidence that a process is gone. Services use only
their existing stored witness, without registration changes.

Process inspection is optional: missing `/proc`, an unavailable platform API or denied
inspection does not become a hard dependency. Doctor gives one portability warning per run
when process evidence cannot be obtained, rather than repeating it for every row. Existing
witnesses can still establish liveness where supported. Default snapshots and `xmsg watch`
do not opt into these probes.

Doctor also requests planned federation diagnostics from the running daemon over the
Unix socket: `GET /v1/diagnostics/federation`. The CLI never loads a private key or dials
a peer directly. The daemon reuses its loaded identity and existing pin/CA verifiers;
there is no fallback to CLI peer dials if the daemon is down or lacks this endpoint.

Planned: the federation section also reports a Warn for ambiguous dynamic alias classes:
`pattern admits ambiguous aliases; give pods concrete CA leaf entries`. This check uses the
loaded configuration, without another network probe or full URI witnesses in the warning.

The invocation probes at most 32 configured peers in sorted order, with at most four
concurrent attempts, two seconds per peer and an eight-second total deadline. Doctor's
IPC deadline is nine seconds. A configured `leaf` (<Status id="xmsg.doctor-peers" />) with an empty address
or a reserved `.invalid` hostname (for example, `pod.invalid:443`) is reported as
`INFO` with `outbound-only leaf, reached via its hub`. This does not add a pass or
warning, and does not make coverage partial; its TLS, certificate expiry and clock
offset remain unobserved. Addressless non-leaves and other unattempted entries remain
unknown; no address is guessed. Peer failures and uncertain observations warn,
rather than fail. An already-expired leaf certificate actually loaded by this daemon
fails; an approaching expiry warns within the smaller of seven days or one-third of that
certificate's lifetime. Only subject, issuer and `notAfter` certificate metadata is exposed,
not certificates, keys, SANs or pins.

A successful probe establishes mTLS reachability, not application permissions or delivery
readiness. The daemon sends `HEAD /` to the existing federation listener, expecting its
ordinary `404` and standard HTTP `Date`, with `User-Agent: xmsg-doctor/<version>`. The
observed offset is relative to the local clock, with reported uncertainty and a 120-second
tolerance; it does not identify which clock is wrong. Missing or invalid dates, unexpected
status codes or a local wall-clock jump leave the offset unknown. Probes run only for this
invocation, never periodically. Normal connection counters or admission caches can change
as part of a handshake; probes make no persistent or application-state writes and call no
listing, observation or reconciliation route.

The planned primary-database check reports the stored version against this binary's schema
and names structural additions as `ensure table`, `ensure index` or `add column TABLE.COLUMN`.
Missing same-version additions warn. A schema newer than the binary fails because startup
refuses it. An older version fails with `schema 3 message-state rebuild (destructive)` and a
backup hint: that startup path recreates message state. Doctor never performs that work.
These are structural requirements from startup declarations, not a chronological migration
ledger or certification of data backfills. Present optional enrollment tables are
informational, without certifying the rest of the loaded configuration. Missing optional
tables are also informational when the daemon's existing CA diagnostic explicitly reports
enrollment disabled; otherwise their conditional requirements warn. No second configuration
fetch is made. Other databases and integrity are outside this check.

Reader mode depends on the health response. With a live daemon and existing regular WAL and
SHM files, an ordinary read-only connection observes committed WAL metadata. It creates no
new entry and does not change the main database or WAL; SQLite's normal SHM read marks may
change. A live rollback-journal database with no journal, WAL or SHM also permits `mode=ro`;
its main-file fingerprints and absent sidecars are rechecked for concurrent changes. A live
WAL database missing its pair, an observed rollback journal or any inconsistent view stays
unknown. Normal readers can take SQLite read locks but never a writer reservation.
When the daemon is down or its
liveness is unknown and sidecars exist, doctor reports their presence/type/size by stat only,
warns about an unclean/uncertain shutdown and leaves recovery to the next normal SQLite
startup. It does not open or read those sidecars. With no sidecars, the offline probe uses
`mode=ro&immutable=1` and rechecks for changes; uncertainty stays visible.

When client and daemon revisions differ or cannot be compared, the result is labelled
`next start of THIS binary`, not a claim about the running daemon's upgrade behavior.
Use the actual selected `--db-path`; health alone does not prove the daemon uses that path.
Doctor never migrates, checkpoints, vacuums or performs automatic recovery. The observation
sidecar is checked by filesystem metadata only.
See [troubleshooting](/operations/troubleshooting/) for the checks and their limits.

### `xmsg service exec`

Runs an optional ordinary service over the daemon's registration and agent sockets. Nothing
starts automatically. The daemon's normal behavior does not change.

```bash
xmsg service exec --name agent-quota -- agent-quota --json
xmsg service exec --name snapshot --timeout-ms 2000 --max-output-bytes 65536 -- /path/to/producer --json
```

`--register-sock` or `XMSG_REGISTER_SOCK` selects the registration socket. Otherwise the runner
uses the daemon's runtime-directory default. `--agent-sock` or `XMSG_AGENT_SOCK` selects the agent
socket. Otherwise the agent socket is next to the registration socket. An explicit socket path
must be absolute. The daemon applies its ordinary rules for service registration, executables and
peer access.

Each delivered request runs the fixed program and the literal arguments after `--`. The runner
ignores the request text. The program gets no stdin. The runner discards stderr. On success, the
UTF-8 stdout is the reply, unchanged, with its whitespace. Configure a command whose stdout is
meant for its requesters. The runner adds no environment dump and no child diagnostics to
responses.

The default time limit is `75000` milliseconds. The default stdout limit is `65536` bytes.
`--max-output-bytes` accepts `64` through `1048576`. The daemon's reported message limit is also a
maximum. On a timeout or an output overflow, the runner kills the owned child and waits for it.
These failures give one static JSON response: a spawn, I/O or nonzero-exit failure, empty stdout,
and UTF-8 that is not valid:

```json
{"status":"unknown","error":"timeout"}
```

The other error codes are `output_limit`, `command_failed`, `empty_output` and `invalid_utf8`.
On a failure, the runner does not guess a quota or another producer value.

The runner replies with a stable idempotency key for each message. Then it ACKs the request.
It keeps one pending response across transport reconnects. It retries an uncertain reply with the
same key and bytes. The runner keeps pending responses in memory. Thus a command must be safe to
run again after a process crash. Interrupt and termination signals stop the runner and reap an
active owned command. A permanent daemon refusal, or a configuration or trust failure, makes the
runner exit non-zero with a diagnostic that has no content. The runner does not retry the same
refused response without end.

For a quota service, the producer owns the account hashes, the measurement age, missing or
stale readings, and the JSON schema. The transport relays that output as it is. Installation and
enablement for each user are deployment configuration.

### `xmsg harness`

<Status id="xmsg.harness-descriptors" />

Administers declared plugin harness descriptors on the local daemon over `http.sock`:

```bash
xmsg harness reload [--http-sock PATH] [--json]
xmsg harness revoke <NAME> [--http-sock PATH] [--json]
```

- `reload` atomically reloads `--harnesses-file` with fail-closed validation. Removed harnesses
  stop accepting new registrations and drain live connections for `drain_window_secs` (default
  `600` seconds).
- `revoke <NAME>` immediately revokes a declared harness, closes its live plugin connections
  without waiting for the drain window, and refuses new registrations until re-enabled.

Both subcommands require the local same-UID `http.sock` from a non-plugin owner process; they are
denied to plugin connections and absent from TCP and `/fed`.

### `xmsg check-peers`

Validates a `peers.json` file against the rules that `xmsg serve` enforces: naming, the trust
model (`pin` or `ca` + `identities`) and non-overlap. It exits `0` on success. On a failure, it
exits non-zero and names the failure. Use it in CI or before a deploy:

```bash
xmsg check-peers /path/to/peers.json --fed-cert /path/to/node.crt
```

The wrapped peers file also accepts global `deny.uris` and `deny.spkis` lists.
Validation rejects malformed deny fields and fingerprints; it does not prove that
an exact selector matches the intended certificate or that another daemon has
loaded it. See the [deny reference](/concepts/federation/#global-deny-and-current-certificate-authority)
and [offboarding runbook](/operations/enrollment-ca/#offboard-a-teammate-or-a-lost-or-stolen-device).

Planned: an otherwise valid file with ambiguous dynamic aliases still exits `0`, but prints
one warning per alias class to stderr. Such identities will be refused even on their first
connection. Run the new binary's check before upgrading a mixed-pattern hub, including when
enrollment is disabled. Reserve affected pods with concrete CA leaf entries or partition the
patterns; see the [upgrade example](/concepts/hubs-and-leaves/#planned-reserve-pod-names-before-upgrading).

## Hosted gateway protocol bootstrap

The separate HTTP [gateway](/extensions/gateway/#protocol-bootstrap) uses `initialize`
with the supported transport revisions `2025-03-26`, `2025-06-18` and `2025-11-25`,
followed by `tools/list` and `tools/call`. It leaves `server/discover` unanswered and
does not implement `2026-07-28` transport, so hosted clients fall back to `initialize`.

An authenticated discovery probe with `MCP-Protocol-Version: 2026-07-28` receives an
empty HTTP `400`; without that header, or with a supported version, `server/discover`
receives JSON-RPC `-32601` (`Method not found`) after bearer verification and live-grant
authorization. The following section documents the local harness-associated stdio
adapter's tools.

## MCP server tools (`xmsg mcp`)

`xmsg mcp` gives six tools over stdio JSON-RPC (`read_attachment`, `list`, `send`, `reply`,
`replies`, and `inbox`). With `--reply-only` / `XMSG_REPLY_ONLY=1`, it gives only `reply` and
`replies`:

### `read_attachment(message_id, index, offset?, length?, as_agent?)`

Reads a bounded byte range of attachment `index` (`>= 0`) on `message_id`. Attachment contents are
[untrusted peer data](/concepts/attachments/):

- **`offset` / `length`:** `offset` defaults to `0`; `length` (`>= 1`) defaults to, and is capped
  at, the node's `max_body` limit. UTF-8 reads end on a character boundary; an offset inside a
  multi-byte UTF-8 character is refused.
- **`as_agent`:** When a subagent calls the tool, the harness `PreToolUse` hook sets it
  automatically.
- **Returns:** `{ attachment: { name, size, media_type, sha256 }, offset, length, next?, encoding, data }`,
  where `encoding` is `"utf-8"` or `"base64"` and `next` is the next byte offset when more bytes
  remain, or `{ state: "pending" }` while a planned federated fetch is in progress.

### `list(name?, node?, kind?, status?, within?, limit?)`

Lists recipients the caller may see on this node and every reachable peer:

- **`status`:** `"live"` or `"inactive"`.
  - `"live"` is the default. Each entry has `registered_at`, in epoch seconds.
  - `"inactive"` shows the `parked` and `closed` instances that xmsg saw within `within` seconds.
    The default is `86400` (24 hours). The maximum is the reply TTL. Each entry has `last_seen`.
    (<Status id="xmsg.codex-restart-custody" />) Startup Codex roots with queued recovery work appear here as
    `awaiting_reattestation` until verified delivery can resume. They are excluded from the default
    live list; deliberate parking and revoked or closed roots keep their existing states.
- **`kind`:** Filter by `"service"`, `"instance"`, or `"subagent"`.
- **`name`:** Filter by service name or instance label.
- **`node`:** An exact canonical name or local nickname queries one node. A bare-host selector queries all matching nodes in the current view; see [node selectors](/concepts/addressing/#node-selectors).
- **`limit` (<Status id="xmsg.recipient-snapshot" />):** Default `50`, maximum `500`; must be at least `1`. Applies once across all nodes after filters. Live entries sort by newest `registered_at`, inactive entries by newest `last_seen`; equal timestamps sort by address.
- **Returns (<Status id="xmsg.recipient-snapshot" />):** `{ recipients: [{ address, kind, harness?, label?, status, node, user, registered_at | last_seen }], nodes: [{ node, status, detail? }], total, truncated }`. `total` counts matching recipients before the cap. When `truncated` is true, narrow with `name`, `node` or `kind`, or raise `limit`.

Planned CLI example: `xmsg list --node alice.laptop --limit 100 --json`. CLI and MCP default to 50. This response change requires updating daemon and clients together.

### `send(to, text, attachments?, as_agent?)`

Sends a message to `<id or name>[@<node>]` (at most one `@`):

- **`to`:** An instance UUID (with an optional `~n`), a delegated sub-address (`<P>/<child>`), a
  service name, or a unique live instance label. `@node` can follow it. xmsg refuses `ref`, `from`
  and a label that contains `' · '`, with a migration hint.
- **`attachments`:** Optional array of up to `8` [file attachments](/concepts/attachments/). Each
  entry is either `{ path, name?, media_type? }` (an absolute path to a regular file readable by
  `xmsg mcp`, defaulting `media_type` to `application/octet-stream`) or
  `{ name, text, media_type? }` (inline UTF-8 text, defaulting `media_type` to
  `text/plain; charset=utf-8`).
- **`as_agent`:** When a subagent calls the tool, the harness `PreToolUse` hook sets it
  automatically.
- **Returns:** `{ message_id, address, outcome }` where `outcome` is `"delivered"`, `"queued"`, or `"pending"`.
  Use the returned `address` for follow-ups. (<Status id="xmsg.codex-restart-custody" />) A failed immediate Codex push
  returns `queued` when xmsg proves custody for the live root's current generation,
  including an idle subagent's parent fallback.

### `reply(message_id, text, attachments?, as_agent?)`

Answers the other party of `message_id`. If you received the message, the reply goes to the
sender. If you sent it, the reply is a follow-up to the recipient in the same exchange:

- **`attachments`:** Optional array of up to `8` `{ path, name?, media_type? }` or
  `{ name, text, media_type? }` entries, staged the same way as on `send`.
- **`as_agent`:** When a subagent calls the tool, the harness `PreToolUse` hook sets it
  automatically.
- **Returns:** `{ bytes, messageId, inReplyTo, outcome }`, where `messageId` is the new reply's
  ULID (or `null` when `outcome` is `"stored"` for pull-only callers) and `inReplyTo` is `message_id`.
- **Delivery errors:** xmsg stores the reply first, then attempts to push it. If the push fails
  (`pushOutcome` is `"sender_gone"` or `"push_failed"`), the tool returns a classified error:
  - `gone: …` / `not_found: …` (`sender_gone`): the recipient session exited or its inbox socket is
    missing. Do not keep retrying the push; the reply is stored for `replies`, or use `list` and
    `send` to reach a live session.
  - `inbox_unavailable: …` / `inbox_timeout: …` (`push_failed`): the recipient's live inbox
    refused the push or timed out (for example, an `agy` delivery failure or socket error). Check
    the recipient's harness health or daemon logs before retrying.
  - `internal: …` or `reply delivery failed: push_failed`: an internal daemon error occurred while
    formatting or queueing the push (or an older daemon omitted detail). Inspect daemon logs.
- (<Status id="xmsg.codex-restart-custody" />) A Codex reply held for a live root's current generation reports `pushed`
  even if its immediate push fails before handoff. Parked or revoked roots keep
  `sender_gone`; unknown or in-flight handoffs do not imply successful custody.

### `replies(message_id, wait?)`

Reads the stored replies to `message_id`. It can wait up to `wait` seconds (`0..=60`) for the
first reply.

### `inbox(wait?, as_agent?)`

During a bound subagent's active turn, reads the messages in its `<P>/<child>@<node>`
[turn mailbox](/glossary/#turn-mailbox) that have not expired. It can wait up to `wait` seconds
(`0..=60`) for the first message. It marks each message that it reads `delivered`:

- **Returns:** `{ address, messages: [{ id, from, body, created_at }] }`.

### Planned: aggregate admitted-leaf mailbox budgets

`xmsg serve --admitted-mailbox-max-rows 100000 --admitted-mailbox-max-bytes 671088640`
bounds all pattern-admitted leaf mailboxes together. Zero refuses new admitted
rows. The existing per-leaf budgets still apply; concrete leaf entries do not
consume the aggregate admitted budget. Rejection keeps existing messages and
returns `429 peer_mailbox_full`. See
[hub admission](/concepts/hubs-and-leaves/#planned-enrolled-nodes-and-bounded-hub-mailboxes).

## Planned: enrollment commands

[Enrollment](/operations/enrollment-ca/) issues a host certificate after OIDC
sign-in. It does not distribute the machine's private key.

| Command | Purpose |
| --- | --- |
| `xmsg enroll URL` | Browser sign-in and local P-256 key/CSR creation; requires `--fingerprint sha256:<hex>` or `--root-file FILE` |
| `xmsg enroll --renew` | One renewal using saved state; no URL or IdP login required |
| `xmsg enroll-ca --enroll-ca-dir DIR init` | Initialize the independent root and print JSON `root_file`/`fingerprint` |
| `xmsg enroll-ca --enroll-ca-dir DIR --enroll-policy FILE list` | Inspect certificate/SPKI and supersession records |
| `xmsg enroll-ca --enroll-ca-dir DIR --enroll-policy FILE bind USER PROVIDER SUB` | Add an explicit identity alias for a bound user |
| `xmsg enroll-ca --enroll-ca-dir DIR --enroll-policy FILE unbind USER` | Remove a user's binding and aliases; not instant peer revocation |

`enroll` accepts `--flow loopback|paste|device` (default `loopback`), `--provider NAME`,
`--host NAME` and `--state-dir DIR`. The default state directory is
`$XDG_STATE_HOME/xmsg/enroll`, falling back to `~/.local/state/xmsg/enroll`.
`--provider` is optional only with one configured provider. Device enrollment is
planned, disabled by default, and requires independent local CA approval. Fresh enrollment does not overwrite `fed.key`; choose a new state directory
for a new key/login. `enroll-ca` accepts `--db-path FILE` to select the serving
CA's database; `init` needs no policy.

Planned live-daemon device commands:

```sh
xmsg enroll-ca [--http-sock SOCKET] pending
xmsg enroll-ca [--http-sock SOCKET] approve REQUEST_ID --user USER --host HOST --spki-sha256 DIGEST
xmsg enroll-ca [--http-sock SOCKET] deny REQUEST_ID
```

These use mode-0600, UID-checked `http.sock` and need no `--enroll-ca-dir`,
`--enroll-policy` or root key. They are unavailable over TCP, enrollment HTTPS,
MCP and federation. The older commands above retain their requirements.
`pending` exposes only authenticated requests awaiting approval. Approval must
match the verified user, requested host, key and current policy; denial, expiry,
policy drift and replay refuse issuance. Before authentication the client shows
`policy user: pending verification`; afterwards it shows the verified policy
user and `awaiting CA approval`.

Provider policy requires both `device.enabled: true` and a distinct
`clients.device` entry; registration alone does not enable it. Disabled or
unsupported providers refuse and suggest `--flow paste`, without automatic
fallback. Google device support remains unverified pending owner-run real-provider
acceptance. These device command examples are illustrative pending final fixture
verification. See [device setup and bounds](/operations/enrollment-ca/#planned-device-sign-in-from-a-remote-terminal).

| Planned `serve` flag | Meaning |
| --- | --- |
| `--enroll-listen IP:PORT` | Separate enrollment HTTPS listener, not the federation port |
| `--enroll-ca-dir DIR` | Owner-private `root.key` and public `root.crt` directory |
| `--enroll-policy FILE` | Provider, user mapping, deny, lifetime and rate policy |
| `--enroll-state DIR` | Use an enrolled client's saved cert/key and automatic renewal |

Supply the first three flags together with federation credentials, a peers file
and `--fed-listen`. `--enroll-state` conflicts with explicit `--fed-cert` and
`--fed-key`; it still needs the peers file and federation listener. See the
[setup and renewal example](/operations/enrollment-ca/#enroll-the-machine).

## Observation collector

<Status id="fleet-observer.collector" />

```sh
xmsg observe-collector --config collector.json --state-dir ./observer-state --listen 127.0.0.1:9428
```

`--config` and `--state-dir` are
required; `--listen` defaults to `127.0.0.1:9428`. A non-loopback listener requires
`web_tls.cert` and `web_tls.key` in configuration. It dispatches independently of
`serve` and does not initialize the bus, enrollment or harness stores.

The JSON configuration supplies client mTLS files, owner authentication and a static inventory of at most 64 canonical nodes. `sources[].labels`
and `sources[].outbound_only` default false. Outbound-only sources are visibly
unsupported unless an explicit `sources[].relay` selects reverse transport. The
closed relay object supplies `hub`, `leaf`, `address`, and optional `ca`; it
refuses mixed direct trust/address fields. Hub and leaf are canonical full
identities; a URI hub requires its CA. Configuration applies on restart. The private cache and every-request owner checks are described in
[collector setup](/operations/fleet-observer/#configure-the-collector).

`GET /` is the authenticated view, with numeric `node` and `page` filters;
`GET /health` is a fixed metadata-free availability response. The optional
Mission Control issuer adds its own login and device routes.

### Mission Control owner CLI

<Status id="mission-control.session" />

Run `xmsg observe-collector admin` as the collector's OS user with the same
`--state-dir`. Use the owner principal shown by `list` for `--owner`.

```sh
xmsg observe-collector admin --state-dir ./observer-state list
xmsg observe-collector admin --state-dir ./observer-state revoke RECORD_ID
xmsg observe-collector admin --state-dir ./observer-state audit
```

<Status id="mission-control.machine-tokens" />

Specify a name, at least one JSON scope, and the rate for a machine token.
Repeat `--scope` for additional scopes. Available scope objects are
`{"kind":"fleet"}`, `{"kind":"attention"}`, `{"kind":"node","node":"node"}`,
and `{"kind":"session","node":"node","endpoint":"service@node"}`.
`--expires-at` takes a Unix timestamp in seconds and defaults to 90 days
after issue.

```sh
xmsg observe-collector admin --state-dir ./observer-state \
  mint machine --owner OWNER_PRINCIPAL --name attention-poller \
  --scope '{"kind":"attention"}' --rate 12
```

<Status id="mission-control.delegated-grants" />

For a delegated credential, use `mint delegated --owner OWNER_PRINCIPAL
--grant-file ./grant.json`. The JSON object supplies `holder`, `verbs`,
`targets` as explicit `{node, endpoint}` pairs, `expires_at` in Unix
seconds, and `rate`. `read_scope` is optional. Either mint writes the handle
once to stdout. Save it to an owner-only credential file.

`list` reports record IDs, class, principal, minting owner, creation and last
use. Revoke using the record ID. To change an owner's issuer and subject, use
`rebind --owner OWNER_PRINCIPAL --issuer ISSUER --subject SUBJECT`.
Rebinding revokes the old subject's credentials and the grants it minted.

When the collector is serving, the CLI uses its owner-only `admin.sock` and
waits for the authority writer to update the live table. For an offline action,
also pass `--config collector.json` after `admin`. The CLI takes the exclusive
authority lock and reports that changes apply at the next start. A held lock
with the socket unavailable makes the command fail without changing the store.

## Locating a session

<Status id="session-locator.cli" />

```sh
xmsg locate 'SESSION@NODE' [--detail] [--locate-config FILE] [--json]
xmsg locate --label LABEL [--detail] [--locate-config FILE] [--json]
```

The local locator reads registrations without delivering messages or
reconciling claims. It returns every matching label, including matches beyond the normal
`list` display limit, and reports unreachable nodes separately from no match.
Only the CLI and local Unix HTTP API expose this feature; there is no locator
MCP tool or collector action.

Built-in harness resume mappings remain `null` (`reason: live` for live or
stale-unknown registrations, `reason: unproven` otherwise). A declared plugin
harness (<Status id="xmsg.harness-descriptors" />) with a typed `resume_argv`
descriptor renders inert display-only argv tokens when the registration is not
live and carries a validated non-leading-dash native ID; `xmsg` never executes
the rendered command. Instance native IDs are captured at registration, never
reconstructed from a bus address. Older registrations, services and child
bindings without a separately captured native ID return `native_id: null`; a
child never inherits a guessed ID from its root. Invalid IDs are withheld; no
unknown or undeclared harness falls back to Claude or Pi.

An explicitly selected viewer configuration can enable local detail and add
display-only reach hints:

```toml
[locate]
detail = true

[locate.reach]
"alice.laptop" = "ssh alice.laptop"
```

No configuration is selected by default. Both `detail = true` and `--detail`
are required for this CLI to request and display a working directory or terminal
reference. Without both, these fields are redacted. This file is a client
preference, not a same-UID security boundary: a same-UID HTTP caller can make its
own explicit detail request. The file and reach hints are never sent to peers.
Reach hints appear in a separate display block and are never executed. Control
characters are escaped for display; escaping does not turn data into safe shell
commands. Working directories come from the current existing registry, may be
unknown after detach, and are not retained in locator metadata.

Remote results contain only recipient metadata. The locator-only native ID, environment and working-directory fields remain
local to their node. Existing recipient labels remain unchanged and can already
contain harness session names. Remote
lookup uses the existing federation list grant with a read-only request. On a peer older than this release, a remote locate behaves like an ordinary
list (the peer may reconcile its claims as it does for `xmsg list`). Deploy peers
together. New peers honor the read-only flag. Node errors are retained, with no
client-side retry or fallback to a different query.

## Session context tags

<Status id="session-context.tags" />

Authorized `xmsg list --json`, MCP `list`, and `xmsg locate --json` results can
carry optional `context` supplied by the reporting session. With the daemon's
default policy, tags are visible to authorized readers. The daemon uses
self-reported values and does not inspect the session's Git checkout.

| Field | Maximum UTF-8 bytes | Example |
| --- | ---: | --- |
| `repo` | 128 | `github.com/example/widget` |
| `branch` | 128 | `feature/parser` |
| `worktree` | 64 | `widget-parser` |
| `task` | 160 | `issue-418` |
| `pr` | 32 | `#73` |

Use a normalized repository slug or a keyed or salted repository identifier prefixed with `id:`,
a basename for the worktree, and an opaque task identifier if the title is
private. A branch name or task title may itself contain sensitive information.

Pass `--no-context-tags` to `xmsg serve` to disable collection and publication.
Use the repeatable `--context-mask SURFACE:FIELD` option to suppress fields
before publishing. For example, the following daemon options hide branch names
from federated lists and omit all context tags from observation export.

```sh
--context-mask federation:branch --context-mask 'observe:*'
```

To load the policy from TOML, pass `--context-tags-config <path>` to `xmsg serve`.

```toml
[context_tags]
enabled = true

[context_mask]
federation = ["branch"]
observe = ["*"]
```

The mask surfaces are `local`, `federation`, and `observe`. Set
`context_tags.enabled = false` to disable the extension and clear collected tags.
`--no-context-tags` takes precedence over the file and CLI masks add to file masks.
Send `SIGHUP` to reload a changed policy file.

See the [socket contract](/reference/http-and-sockets/#session-context-tags) for writes, freshness, and the wire upgrade.
