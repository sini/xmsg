import Status from '../../../components/Status.astro';

`xmsg serve` binds local Unix domain sockets (`http.sock`, `agent.sock`, `register.sock`; in leaf
mode, `agent.sock` and the leaf registration socket only). Planned (<Status id="xmsg.install-contract" />):
unpinned endpoints live in a state-derived private namespace `xmsg-<uid>-<12hex>/` under canonical
`/tmp` on macOS or `$XDG_RUNTIME_DIR` on Linux (falling back to `/tmp` when a valid `XDG_RUNTIME_DIR`
would exceed `sockaddr_un.sun_path` measured in OS bytes: 103 bytes on macOS, 107 bytes on Linux).
When every enabled endpoint is explicitly pinned, no managed runtime namespace is derived or created.
The managed name stays the default on every platform, and it is specific to the state root. A
stable socket directory is never a default: it is a deployment pin, with all three endpoints in one
owner-private directory and the same paths given to the daemon and to every client (in Home Manager,
[`programs.xmsg.server.sockets.dir`](/operations/nixos-and-home-manager/#a-stable-socket-directory)).
Each socket is published atomically without replacement at mode `0600` in a `0700` directory. With
federation, it also has an mTLS listener for `/fed/v2/*`. Each JSON request body and socket frame
refuses unknown fields. The error is `bad_request`, and it names the unknown fields.

Existing clients that hard-code `<runtime>/xmsg/*.sock` must be updated or use
explicit endpoint pins shared with the daemon. See
[upgrading an existing install](/operations/runtime-and-systemd/#upgrading-an-existing-install)
for legacy-layout pins, stopped-state moves and complete container endpoint sets.

## `http.sock` & HTTP API routes

By default, xmsg serves HTTP only on its resolved `http.sock` (discover the active path read-only
with `xmsg doctor --json`). A caller whose process ancestry traces to a registered session or
service acts as that sender. Other callers are
**[anonymous](/glossary/#anonymous-sender)** (`<from> · anon@<node>`). An anonymous caller can
send, and can read replies by `message_id`. It cannot call `reply` (`403 denied`).

```bash
sock="$(xmsg doctor --json | jq -r '.http_socket')"

# Health check
curl -s --unix-socket "$sock" http://localhost/healthz

# List live recipients (may reconcile claims and deliver queued work)
curl -s --unix-socket "$sock" http://localhost/v1/recipients

# Send a message
curl -s --unix-socket "$sock" http://localhost/v1/messages \
  -H 'content-type: application/json' \
  -d '{"to": "genie-guard", "text": "Please review.", "from": "ci", "idempotency_key": "run-42"}'

# Long-poll replies for up to 30s
curl -s --unix-socket "$sock" "http://localhost/v1/messages/<message_id>/replies?wait=30"
```

| Method & Route | Description |
|---|---|
| `GET /healthz` | Server health check (`200 OK`); the Unix socket also reports daemon build metadata. |
| `GET /v1/recipients?name=&node=&kind=&status=&within=&tag=` | Lists recipients across this node and reachable peers (`{"recipients": [...], "nodes": [...], "total", "truncated", "coverage"?}`). Reconciles claims and registrations and can deliver queued work or fork notices. `tag` is refused (`bad_request`) with `read_only=true` or `status=inactive`. |
| `GET /v1/recipients?read_only=true` | Returns an explicitly partial, read-only local registration snapshot; no reconciliation, pruning, delivery or federation requests. |
| `POST /v1/messages` | Sends `{ "to", "text", "from"?, "idempotency_key"? }`. Returns `202 Accepted` with `{ "message_id", "address", "outcome" }`. |
| `POST /v1/messages/{id}/replies` | Replies to `{id}` with `{ "text", "idempotency_key"? }`. Requires traced session/service caller (or leaf principal). Returns `200 OK` with `{ "seq", "messageId", "createdAt", "replierSessionId", "text", "pushOutcome", "pushedMessageId" }`. |
| `GET /v1/messages/{id}/replies?after={seq}&wait={seconds}` | Reads stored replies to `{id}`, waiting up to `wait` seconds (max `60`, max `128` concurrent waiters). |
| `POST /v1/harnesses/reload` | Local `http.sock` non-plugin owner only (<Status id="xmsg.harness-descriptors" />): atomically reloads `--harnesses-file`. |
| `POST /v1/harnesses/{name}/revoke` | Local `http.sock` non-plugin owner only (<Status id="xmsg.harness-descriptors" />): immediately revokes a declared harness and closes live connections. |
| `GET /v1/messages/{id}` | Returns the stored message record and its replies. |

### Local daemon build metadata

<Status id="xmsg.doctor" />

On `http.sock`, `GET /healthz` includes `version` (the crate version) and
`build_revision` (the compiled source revision), alongside the existing health fields:

```json
{"status":"ok","sessions_dir":"ok","version":"0.1.0","build_revision":"unknown"}
```

Nix builds set `XMSG_BUILD_REVISION` from the flake's `self.rev`, or `self.dirtyRev` for
a dirty tree. A plain Cargo build without that compile-time value reports `unknown`;
the crate version alone does not identify a source revision. Build metadata is read-only.
The optional local TCP health response does not expose the build revision, and the
federation listener does not serve `/healthz`. Use
[`xmsg doctor`](/reference/cli-and-mcp/#xmsg-doctor) on the node to compare the
running daemon with the client.

### LAN discovery health

<Status id="xmsg.discovery" />

On `http.sock`, `GET /healthz` also includes the detector state and announce posture of
[LAN discovery](/concepts/discovery/):

```json
{"discovery":{"mdns":{"state":"unverified","announce_state":"at_rest","announce_mode":"timed","detail":"outbound multicast sent without error; Local Network permission unverified while at rest","since":1763400000,"candidates":2}}}
```

- `state` is one of `off`, `starting`, `active`, `unverified`, `permission_suspected` or `failed`.
- `announce_state` reports the announcement posture separately: `"at_rest"`,
  `{"window_open": <remaining_secs>}` during a `120`-second pairing window (no production
  entry point opens a timed window until the pairing release lands, so `"timed"` nodes stay
  `"at_rest"` until then), or `"always"`.
- `announce_mode` reports the effective configured mode (`"timed"`, `"browse_only"` or
  `"always"`).
- `detail` explains the current state and, for `permission_suspected` and `failed`, names
  the suspected cause and remedy.
- `since` is the Unix timestamp (seconds) of the last `state` change, or `null`.
- `candidates` counts unexpired mDNS candidates currently held in the table.

Like `build_revision`, `discovery` is omitted from the optional TCP health response.

### Pairing authority health

<Status id="xmsg.pairing-authority" />

On `http.sock`, a federating node's `GET /healthz` also reports its
[authority generation](/concepts/trust-model/#authority-generations):

```json
{"pairing":{"committed_revision":4,"installed_revision":4}}
```

`committed_revision` is the pairing store's revision; `installed_revision` is the revision of
the generation federation checks run against. A committed revision ahead of the installed one
means a change is not yet in effect. When the store cannot be read, `committed_revision` is
`null` and `error` names the failure; the installed generation stays in effect. `pairing` is
`null` on a node without federation and is omitted from the optional TCP health response.

### Read-only local recipient snapshot

<Status id="xmsg.recipient-snapshot" />

Use this mode when observing a node must not reconcile its claims or drive queued delivery:

```bash
curl -fsS --unix-socket "$sock" \
  'http://localhost/v1/recipients?read_only=true'
```

The response includes `read_only: true`, `partial: true`, `truncated`, `recipients` and `nodes`.
It reports
already-observed registrations and last-seen metadata. Recipient states `registered` and
`seen` describe stored metadata; they do not certify current liveness or reachability.
A missing last-seen timestamp remains unknown; registration time is not substituted for it.
Unreconciled or filesystem-only sessions may be absent. Reading the snapshot does not assign
or release claims, evict or prune registrations, admit subagents, deliver queued messages or
fork notices, or contact a federation peer. A `503` response means the daemon has not
completed registration-runtime initialization; the snapshot request does not initialize it.

The node selection must be omitted, `local`, or this daemon's canonical node name. Remote
nodes, host selection, `status` (including `live` and `inactive`) and `within` are refused in
snapshot mode. The ordinary listing without `read_only=true` retains its existing live and
inactive queries, peer fan-out and reconciliation side effects. Its behavior is also retained
for MCP and federation listing.

An older daemon rejects the unknown `read_only` query field with `400 bad_request`. A client
requiring a read-only snapshot must report that failure rather than retry the ordinary list.
[`xmsg watch`](/reference/cli-and-mcp/#xmsg-watch) uses this mode exclusively
for its roster. The local observation journal supplies its separate exchange timeline.

### Registered process liveness

<Status id="xmsg.recipient-snapshot" />

The Unix socket accepts an explicit diagnostic variant of the read-only snapshot:

```bash
curl -fsS --unix-socket "$sock" \
  'http://localhost/v1/recipients?read_only=true&liveness=true'
```

It adds `live`, `gone` or `unknown` evidence about the registered owner process where an
existing witness can answer. These are process states, not proof of harness addressability,
a usable writer lease, delivery or task completion. A service probe reads its existing
witness without updating registration state. Some harness rows have no usable evidence
and remain unknown. Missing `/proc`, unavailable native APIs or denied inspection stay
unknown where no existing witness answers; the endpoint does not require `/proc`.

The liveness flag is Unix-only and requires `read_only=true`; local TCP and federation
requests do not offer it. The default snapshot and watch roster remain metadata-only.
The same snapshot bounds and partial-coverage limits apply, and a cold runtime still
returns `503` instead of initializing it. Missing rows or a truncated response do not
establish that a process is gone. A client whose daemon rejects this opt-in must report
unknown rather than fall back to the ordinary listing.

### Invocation-only federation diagnostics

<Status id="xmsg.doctor-peers" />

`GET /v1/diagnostics/federation` is available only over `http.sock`, not the optional
local TCP or federation listener. For example:

```bash
curl -fsS --max-time 9 --unix-socket "$sock" \
  'http://localhost/v1/diagnostics/federation'
```

The daemon uses its existing loaded mTLS identity and pin/CA verifiers to probe at most
32 sorted configured peers, four concurrently, with two seconds per peer and an eight-second
global deadline. It does not invent dial addresses for addressless or outbound-only client
entries. Unattempted entries stay unknown. A down or older daemon leaves the diagnostic
unknown; doctor does not load private keys or directly dial peers as a fallback.

The probe is `HEAD /` on the existing federation listener, with
`User-Agent: xmsg-doctor/<version>`. Its normal `404` response and standard HTTP `Date`
allow an observed offset relative to the local clock to be reported with uncertainty and
a 120-second tolerance. Missing/invalid dates, unexpected status or a local wall-clock
jump make the offset unknown. It is not a diagnosis that the peer clock is wrong.
A successful handshake proves mTLS reachability, not application permissions or delivery
readiness. Certificate metadata is limited to subject, issuer and `notAfter`; no DER,
SANs, pins or keys are returned.

The response is a JSON report with `available`, `ambiguous_aliases`, `own_leaf`, `own_expiry`, `peers`, `partial`, `truncated` and `budget_exhausted`. On a leaf it also carries `stalled_leaf_ack_seconds`, a map from hub name to whole seconds that the hub's current inbox head has waited for a service ACK. The field is omitted when no head is stalled, and lists at most 32 hubs. Doctor turns each entry into a `federation.stalled_leaf_ack.<hub>` warning.

These probes run only when invoked. They add no federation route, protocol or peer right
and do not list recipients, read observation data or reconcile registrations. Normal
connection counters or admission caches may update during a handshake, but diagnostics
make no persistent or application-state writes. See
[`xmsg doctor`](/reference/cli-and-mcp/#xmsg-doctor) for warning and expiry results.

### Local observation journal

<Status id="fleet-observer.collector" />

`GET /v1/observe/events` reads bounded message metadata over `http.sock` from the
same UID. It is absent from the shared TCP router, including a leaf's TCP listener.
It grants no remote peer right and reads no message bodies or harness transcripts.

```bash
curl -s --unix-socket "$sock" \
  'http://localhost/v1/observe/events?after=0&limit=100'
```

The optional query fields are `epoch`, `after` and `limit`. Unknown fields and
invalid bounds return `400 bad_request`. `after` is a nonnegative sequence up to
`9223372036854775807`; `limit` defaults to `100`, with range `1..200`. No long poll
is available. Each page is at most 256 KiB and each event at most 4 KiB.

Without a cursor, the first page is a recent tail in ascending sequence order;
`initial_omitted` distinguishes that intentional omission from loss. Use `after=0`
to begin at the retained floor. To continue, pass the response's `epoch` and `next`
as the next request's `epoch` and `after`. `has_more` reports remaining retained
events at that snapshot. `floor`, `head`, `gaps` and `losses` describe continuity.
An old epoch or a cursor ahead of the journal produces an explicit reset; an
evicted cursor produces a gap. Sequence orders local observations, not globally
synchronized effects or agent progress.

This is **observation, not complete history**. Metadata is queued after a primary
commit; a crash can lose an observation before persistence. Each writer startup
adds a durable `writer_restart` gap with unknown loss, even when the epoch stays
the same. Known queue drops, capacity evictions and TTL expiry have separate
counters. A bounded capture overflow also reports a gap rather than inventing
intermediate transitions. A full or unavailable observer never blocks delivery.

The sidecar is `<configured-db-path>.observe.sqlite`, mode `0600`, beside the
primary database in its private directory. Primary schema version 3 is unchanged;
older binaries ignore the sidecar. Defaults retain seven days, 10,000 events or
16 MiB of stored metadata, whichever limit applies first. The byte budget is
logical metadata; SQLite indexes and journal overhead are additional. Idle
cleanup runs at least every ten minutes. The pending queue separately retains
at most 256 events or 1 MiB and drops oldest observations on overflow.

A corrupt or unsupported sidecar makes observation unavailable; it does not reset
message state or silently delete the journal. Observation errors return
`503 service_unavailable`. Metadata includes endpoint references, message/reply
correlation, source/capture/persistence times and the actual stored outcome.
`delivered`, `queued` and `delivery_unknown` retain their bus meanings; none
asserts that an agent read a message or finished a task.

The `arrival` event records that the daemon committed a queued item's delivery mark
for an inbox result. It does not prove that the client received the response, that an agent
read it, or that a task completed. It carries message/correlation metadata when known, never
the queued body, sender label or envelope; missing correlation remains unknown.

This event is emitted by the inbox-pull path only. Pi/service ACKs, agy receipt and Codex
handoff acceptance do not emit `arrival` in this implementation. Empty or repeated inbox
reads add no arrival event. Like the other journal events, arrival is best-effort post-commit
observation: a full or unavailable sidecar cannot change inbox delivery success.

Endpoint references stay absent when their node cannot be established. The
`body_availability` hint describes capture time: original send bodies are not
retained, and a retained reply at capture time is no promise that it still exists.

## `agent.sock` frames

A line-delimited JSON protocol. `xmsg mcp`, the hook handlers, the Pi extension and the Rust
service client's `AgentClient` use it:

| Request Frame | Response Frame |
|---|---|
| `{"action":"list","name"?,"node"?,"kind"?,"status"?,"within"?,"tag"?,"limit"?}` | `{"status":"ok","recipients":[…],"nodes":[…],"total":N,"truncated":B,"coverage"?:{…}}` |
| `{"action":"tag","add"?,"remove"?,"codex_session"?,"codex_thread"?,"codex_turn"?}` | `{"status":"ok","address","tags":[…]}` (<Status id="xmsg.session-tags" />; `session_id` and `as_agent` are refused `bad_request`) |
| `{"action":"send","to","text","idempotency_key"?,"as_agent"?}` | `{"status":"ok","message_id","address","outcome"}` |
| `{"action":"reply","message_id","text","idempotency_key"?,"as_agent"?}` | `{"status":"ok","reply":{…}}` |
| `{"action":"replies","message_id","wait"?,"after"?}` | `{"status":"ok","replies":[…]}` |
| `{"action":"inbox","wait"?,"as_agent"?}` | `{"status":"ok","address":"<P>/<child>@<node>","messages":[…]}` |
| `{"action":"subagent","event","agent_id",…}` | `{"status":"ok",…}` |
| `{"action":"codex_hook","event","payload",…}` | `{"status":"ok","stdout",…}` followed by client `{"ack":"accepted"\|"abort"}` |
| `{"action":"codex_revoke","session_id","revoked"?}` | `{"status":"ok"}` (`xmsg register codex --revoke`/`--unrevoke` and `xmsg unregister --codex-session`; `revoked` defaults to `true`) |
| `{"action":"mcp_start","schema_version"?,"label"?,…}` | Sent once by `xmsg mcp` at startup to register its session; not for other clients |

## `register.sock` frames

These clients use `register.sock`:

- Antigravity credential registration;
- Pi long-polling;
- headless `svc` daemons (see [Daemon Protocol & Rust Client](/reference/service-client/));
- multiplexed plugin harnesses ([opencode](/harnesses/opencode/) and
  [Hermes](/harnesses/hermes/)).

### Multiplexed plugin protocol (`opencode`, `hermes`, and declared harnesses)

The plugin opens `register.sock` with `{"harness":"opencode"}`, `{"harness":"hermes"}`, or
`{"harness":"<declared-name>"}` (<Status id="xmsg.harness-descriptors" /> when configured via
`--harnesses-file`). The answer is `{"status":"ok","node":"<node>"}`. An undeclared harness name
is rejected with `bad_request`; a revoked declared harness is rejected with `denied`. Each later
frame has a `request_id`, and the response has the same `request_id`. Thus xmsg can answer tool
calls while a `poll` waits on the same connection. Declared v1 harnesses are poll-only: `reclaim`,
`continues`, and `subagent` frames are refused, `env_hint_sources` filters reported terminal hints,
and attachment operations require `"capabilities": {"attachments": true}` (default `false`):

| Frame | Response |
|---|---|
| `{"action":"register","session":S,"reclaim"?:{…}}` | `{"status":"ok","address":"<id>@<node>","reclaim":{…}}` |
| `{"action":"release","session":S}` | `{"status":"ok"}` (`S` answers `gone` thereafter) |
| `{"action":"continues","from":S1,"to":S2}` | `{"status":"ok","address":…}` (moves `S1`'s address to `S2`) |
| `{"action":"subagent","event":"start"\|"stop"\|"end","session"?:S,"agent_id":C,…}` | `{"status":"ok",…}` (binds/updates `<P>/<C>@<node>`) |
| `{"action":"list"\|"send"\|"reply"\|"replies"\|"inbox","session":S,"as_agent"?:C,…}` | Same response shape as `agent.sock`, acting as `S` (or `<P>/<C>@<node>`) |
| `{"action":"poll","wait":N}` | `{"action":"deliver","session":S,"address":…,"message_id":…,"from_name":…,"text":…,"envelope":…}` or `{"action":"timeout"}` |
| `{"action":"ack","session":S,"message_id":M}` | `{"status":"ok"}` |

## Federated `/fed/v2` wire routes

Only the mTLS `--fed-listen` listener serves these routes. They are separate from the local
loopback routes:

| Route | Method | Description |
|---|---|---|
| `/fed/v2/messages` | `POST` | Delivers a federated message (or relays a single-hop forward when the peer has `"forward"`). |
| `/fed/v2/replies` | `POST` | Delivers a reply back to the originating node. |
| `/fed/v2/messages/{id}/replies` | `GET` | Pulls stored replies for a message sent by an outbound-linked or leaf node. |
| `/fed/v2/observe/events`, `/fed/v2/observe/snapshot` | `GET` | Bounded stored metadata for a peer with an explicit `observe` grant. |
| `/fed/v2/sessions` | `GET` | Returns this node's filtered recipient list for mesh `list`. |
| `/fed/v2/inbox`, `/fed/v2/inbox/{id}/ack` | `GET`, `POST` | Long-polls and acknowledges items in a leaf or outbound-linked peer's hub mailbox. |
| `/fed/v2/attachments/{item_id}/{index}?offset=&length=` | `GET` | Planned: reads a bounded raw file range; requires the item's downstream peer and its current hop permission. |
| `/fed/v2/attachment/{query}` | `POST` | Planned: answers a peer-bound mailbox attachment query with raw bytes or a JSON error. |
| `/fed/v2/list/{query}` | `POST` | Posts a leaf or outbound-linked node's answer to a mailbox `list` query. |
| `/fed/v2/handoff`, `/fed/v2/handoff/ack` | `POST` | Transfers and acknowledges a parked Claude conversation queue across a user's machines. |

Mailbox control polling is planned for the next release. `GET /fed/v2/inbox?control=true&wait=30`
long-polls only peer-bound list and attachment controls, never a durable message. It uses a
separate bucket of 120 requests per minute (burst 120, refill two per second), with the same
current-peer and `leaf: true` admission as mailbox reads. `control=false` selects only durable
messages under the ordinary peer/inbox quotas. Omitting `control` retains the legacy combined
response and ordinary quota behavior. ACK uses the existing route and follows service ACK.

For mailbox pulls and ACKs, the authenticated peer must have `leaf: true` on the hub. Each peer
can access only its own mailbox. xmsg accepts the `inbox` string in `allow` and ignores it. Thus
old configurations that list it still load.

A full node with an outbound link needs `relayed` (or `relay`) when a pulled message's origin is
not the hub's canonical node name. A refused item gets a strict
`{"error":"denied","detail":"..."}` reply, and the node ACKs it at the hub. Thus it cannot block
later mailbox items. Mail that starts on the hub itself is delivered without this grant. The
check uses the existing origin fields and does not change the wire shape. It is on the main
branch and is not yet in a release.

### Node observation export

<Status id="fleet-observer.collector" />

These read-only routes require the literal
`observe` peer right over the mTLS federation listener. They are absent from
normal HTTP, leaf TCP and MCP. They do not call discovery, inbox, reply polling,
ACK or body/transcript readers. Outbound-only leaves are unsupported. See
[scope semantics](/concepts/fleet-observer/#an-individual-grant) and the
[configuration and request example](/operations/fleet-observer/).

| Events query field | Default | Bounds |
|---|---|---|
| `v` | `1` | Only version `1`. |
| `epoch` | absent | If present, 1–128 bytes; required with positive `after`. |
| `after` | `0` | Nonnegative signed 64-bit sequence. |
| `limit` | `100` | `1..200`. |
| `scope` | absent | If present, 64 lowercase hex characters; required with positive `after`. |
| `labels` | `false` | Labels require both request opt-in and `observe_labels` on the grant. |

`GET /fed/v2/observe/events?v=1&after=0&limit=100` starts a retained-history
backfill, including when `after` is omitted. Continue with the response's `epoch`,
`scope` and `next` as the next `epoch`, `scope` and `after`. An old epoch or cursor
ahead resets the read; changed scope resets backfill with `scope_changed`.
Reconnect after peer-policy reload. A scope value detects changes; it grants no
rights. `next` advances through scanned records, including filtered records,
but never past a visible event excluded by the response byte limit.

The strict page object contains only `v`, `node`, `epoch`, `scope`, `events`,
`next`, `has_more`, `gaps` and boolean `available`. Node and epoch apply to every
event. The export omits raw journal `head`, `floor` and global loss totals.
A gap has `reason` and `unknown_loss`, with no arbitrary detail or loss count.
`policy_filtered` distinguishes scope filtering from source loss.

Each event has `sequence`, `observed_at`, `persisted_at`, `kind` and `available`;
optional fields are `source_at`, `from`, `to`, `message_id`, `reply_id`, `thread_id`,
`outcome` and `reason`. Timestamps are Unix seconds. Kind, outcome and reason
are closed enums; unknown internal classes become `unknown`, not arbitrary text.
The `arrival` kind preserves the inbox delivery-mark meaning described above in the
node export; it adds no content or acknowledgement to the export.
Endpoint references are canonical `key@node` values. There is no body, text,
excerpt, path, cwd, environment or token field. Event `available` is the enum
`not_recorded` or `retained_at_capture`: capture-time history, not a content-fetch
API or a guarantee that content remains today.

The collector [unknown event kind](/glossary/#unknown-event-kind) fallback
accepts an unrecognized `kind` string only when it matches `[a-z][a-z0-9_]*` and is
at most 64 ASCII bytes. It maps that kind to the unit `Unknown` value for validation
and the fixed caption **“unknown event kind (newer node)”** for display. Known
neighbors, gaps and cursor progress remain intact. `arrival` is a known kind.

The original kind name is retained only in private stable event-envelope JSON for
exact replay comparison and later upgrades, within the existing 4,096-byte event,
256 KiB page and 200-event limits. It is never displayed. No kind-specific payload
is retained: duplicate keys, extra fields, bodies, invalid metadata and unrecognized
other enum values remain refused. The node exporter and public DTO enum remain
closed; this is a collector receive rule, not a payload-schema extension.

Stored newer rows use the same fallback after fresh scope validation, without a
database migration. This compatibility rule requires an updated
collector. An unpatched older binary may reject newer pages or stored rows; a
downgrade to one does not gain the fallback. See the
[mixed-kind example](/operations/fleet-observer/#read-newer-event-kinds).

`GET /fed/v2/observe/snapshot?v=1&labels=false` accepts only `v` and `labels`.
Its object has `v`, `node`, `scope`, `observed_at`, `endpoints`, `truncated` and
`available`. Here `available` is the enum `available`, `partial` or `unavailable`.
Each descriptor has `id`, `node`, `kind`, `harness` and `state`, with optional
`source_at` and `label`. Kinds are `instance`, `subagent`, `service` or `unknown`;
harnesses are built-ins (`claude`, `codex`, `agy`, `pi`, `opencode`, `hermes`),
validated declared harness names (`[a-z][a-z0-9_-]{0,31}`, <Status id="xmsg.harness-descriptors" />),
or `unknown` (adding declared harness names to the observation snapshot wire enum is a breaking
wire change; upgrade daemon, clients, and `observe-collector` together);
states are `registered`, `released`, `seen` or `unknown`. These are cached facts,
not current process liveness. Labels are at most 256 UTF-8 bytes and require
both opt-ins. This implementation always reports a successful cached snapshot as
`partial`, even when `truncated` is false: filesystem-only registrations cannot
be enumerated from the cache.

Both routes reject request bodies, unknown query fields and unsupported versions.
Queries are at most 1 KiB. The export handler has a five-second response-preparation
deadline; timeout returns unavailable. This excludes TLS setup and transmission
time. Blocking work can outlive the timeout while retaining its read slot.
An event page holds at most 200 events, each source event at most 4 KiB, and
at most 256 KiB for the complete encoded page. A snapshot holds at most 200 cached
descriptors and 256 KiB. Busy or unavailable storage returns an unavailable error,
not an empty successful history. Reads share eight node-wide slots without an
unbounded wait queue, and use an `observe:<peer>` rate bucket. Expired source
events are excluded even before journal cleanup.

Sequence order is per node, not a global clock or proof of agent reads. Preserve
gaps, reset and partial states when displaying results. A scoped event with an
unknown or disallowed endpoint is omitted in full. Ordinal spacing may still
reveal omitted activity volume.

## Error vocabulary

Each surface uses the same error codes. HTTP uses `{"error": <code>, "detail": …}`. Sockets use
`{"status":"error","error": <code>,"detail": …}`:

- **Addressing:**
  - `not_found` (`404`): No such recipient, message, or node.
  - `ambiguous` (`409`): Multiple recipients match; `detail` lists every candidate address.
  - `denied` (`403`): Peer rights (`allow`, `principals`, `targets`, `from`) refused the request,
    a caller that is not a party called `reply`, or a hub forward was not authorized.
  - `gone` (`410`): A process-bound session has exited: `pi`, a released `opencode`/`hermes`
    session, or an exited `X~n` fork.
  - `unavailable` (`503`): During bare-reference resolution, xmsg could not reach a node in the
    federated view. `detail` names the node.
  - `not_live` (`409`, node-to-node): A cache-routed send reached a node where the instance is now
    only `parked`.
  - `live_elsewhere` (`409`): A reclaim names an instance ID that is live on another connection.
- **Registration:**
  - `process_already_registered` (`409`): The connecting process already holds a registration for
    another service name.
- **Transport & Validation:**
  - `bad_request` (`400`, including unknown JSON fields or malformed addresses), `bad_sender`
    (`400`), `conflict` (`409`), `payload_too_large` (`413`), `rate_limited` (`429`),
    `service_unavailable` (`503`), `peer_unreachable` (`503`), `credentials_stale` (`503`),
    `inbox_unavailable` (`502`), `inbox_timeout` (`504`), `insecure_socket_dir` (`500`) and
    `internal` (`500`).


Federated file references and fetch routes are planned for the next release. Message and reply
envelopes carry an optional `attachments` array; empty arrays are omitted for compatibility.
A mailbox control item with `kind: "attachment"` carries `query`, `item_id`, `index`, `offset`
and `length`. Only the authenticated queried peer can answer, once. Raw ranges use the
message-body limit and the separate `attach:<peer>` rate bucket. See
[file attachments](/concepts/attachments/) for staging, read permissions, expiry and an example.

## Collector HTTP view

<Status id="fleet-observer.collector" />

The separate `observe-collector` listener never exposes the exporter routes on ordinary bus HTTP or initializes bus state.
This section describes the introspection configuration. The optional [Mission Control issuer](#mission-control-issuer-routes) adds its own routes.

| Method and path | Boundary and result |
| --- | --- |
| `GET /health` without query | Fixed `available` text only; no cached metadata |
| `GET /` | Every-request bearer introspection and exact owner binding before reading the collector cache |

Only numeric `node` (zero-based canonical-name sorted inventory index) and `page`
(0–49) are accepted view queries. A page without a node can only be zero. Unknown,
duplicate, nondecimal and out-of-range fields return 400. Other paths return 404;
non-GET metadata requests return 405 after owner admission. Identity headers do
not authorize any route.

Malformed/invalid bearer claims return 401, an otherwise valid non-owner returns
403, and an unavailable provider returns 503. These responses contain no history
or credential detail. Bearer bytes are at most 8192, headers 16384, introspection
body 65536 and HTML 4 MiB. Introspection has a two-second deadline inside the
five-second request budget. Connections and active requests are capped at 64 and
eight respectively, without an unbounded admission queue.

The view sends CSP with scripts disabled, no-store and nosniff. Its static CSS and
HTML/SVG have no browser bearer store or action routes. A non-loopback listener
requires configured server TLS. See [collector operations](/operations/fleet-observer/)
for configuration, cache retention and restart revalidation states.

## Bounded recipient listings

<Status id="xmsg.recipient-snapshot" />

Ordinary `GET /v1/recipients` and agent/plugin `list` accept `limit` (integer,
1–500, default 50). They return `total` and `truncated` alongside `recipients`
and `nodes`, even when `limit` is omitted. Filtering and federation aggregation
precede the single global cap. Live recipients sort by descending `registered_at`;
inactive recipients sort by descending `last_seen`, with address as the tie breaker.
For example, `/v1/recipients?kind=service&limit=100` returns at most 100 matching services.

Deploy the daemon and CLI/MCP/SDK clients together: strict older clients and servers
are not compatible with this response/query change. The schema version remains 2.
Federation `/fed/v2/sessions` and dial-out list answers retain their existing unbounded
vector wire format. Read-only snapshots, watch and doctor retain their separate behavior.

## Session locator

<Status id="session-locator.cli" />

`GET /v1/locate?address=ADDRESS` or `GET /v1/locate?label=LABEL` is served
only on the local Unix socket, with the same-UID check. Choose exactly one
selector; `detail=true` explicitly requests local working-directory and terminal
reference fields. This endpoint is absent from the TCP and federation listeners.

The strict response has `locators` and `nodes`. Each locator contains its
unchanged `recipient` row, `native_id`, `resume`, `reason`, `env` and `cwd`.
For built-in harnesses, `resume` is `null` (`reason` is `live` for live or
stale-unknown registrations, otherwise `unproven`). For a declared plugin
harness (<Status id="xmsg.harness-descriptors" />) with a typed `resume_argv`
template, non-live registrations with a validated non-leading-dash native ID
return inert argv tokens in `resume` (display-only; never executed). Missing
native IDs or environment hints are `null`; a reported environment is
`{kind, ref?}`, with kind `zellij`, `tmux`, `herdr` or `none`. `none` is
distinct from an unknown environment.

## Declared plugin harness administration

<Status id="xmsg.harness-descriptors" />

`POST /v1/harnesses/reload` and `POST /v1/harnesses/{name}/revoke` are mounted
only on the local `http.sock` Unix router. Both verify that the Unix peer
belongs to the daemon's UID and is not a registered plugin process (`403 denied`
otherwise). Neither route is mounted on the optional local TCP listener or the
mTLS `/fed/v2` listener.

- `POST /v1/harnesses/reload` atomically re-reads and validates
  `--harnesses-file` (failing closed and retaining the previous table on error),
  starts the configured `drain_window_secs` countdown for removed harnesses, and
  immediately terminates live connections for any newly revoked harness.
- `POST /v1/harnesses/{name}/revoke` revokes a declared harness immediately and
  closes its active plugin connections without waiting for the drain window.

Local lookup gathers all matches without the ordinary list display cap,
reconciliation, purge or queued delivery. Remote results expose only recipient
metadata; native IDs, environments and working directories are `null`. Node
errors distinguish an unreachable node from an empty matching set. Remote
lookup uses the existing federation list grant with `read_only=true`, not a
new remote locator route. Old peers may ignore the flag and reconcile exactly
as an ordinary list; new peers honor it. There is no retry through a different
query. The peer update should be deployed together.

The CLI's detail configuration is a viewer preference. A same-UID HTTP caller
can request detail independently. Reach hints belong only to the viewer's
explicitly selected CLI configuration and never appear in this API.

## Session capability tags

<Status id="xmsg.session-tags" />

Registered live sessions can add or remove capability tags (`^[a-z0-9][a-z0-9._-]{0,63}$`, up to 8 per registration) on their own session.

- `agent.sock`: `{"action":"tag","add":"orchestrator.proj"}` or `{"action":"tag","remove":"orchestrator.proj"}` (with `codex_session`/`codex_thread`/`codex_turn` for Codex callers; `session_id` and `as_agent` are refused `bad_request`).
- Pi (`register.sock`): `{"action":"tag","sessionId"?,"add"?,"remove"?}` (foreign `sessionId` is refused `denied`).
- Multiplexed plugin (`register.sock`): `{"action":"tag","request_id":"1","session":"thread-418","add"?,"remove"?}` (unheld `session` is refused `denied`).
- Federation v3: `/fed/v2/sessions?v=3` returns `{"v":3,"entries":[...]}` when `v >= 3` and `!read_only` (otherwise the bare array). A dial-out leaf sets `FedListAnswer::Ok.v = 3` only when the queued `list` item asked for `v >= 3`.

## Session context tags

<Status id="session-context.tags" />

A registered session can publish or clear its own tags through `agent.sock`.
The daemon derives ownership from the authenticated caller and the existing
harness attribution rules. Example request frames, one JSON object per line:

```jsonl
{"action":"update_context","context":{"repo":"github.com/example/widget","branch":"feature/parser","worktree":"widget-parser","task":"issue-418","pr":"#73"}}
{"action":"clear_context"}
```

Pi can send the same actions on its registered `register.sock` connection.
OpenCode and Hermes send them on their existing multiplexed connection and
include `request_id` and the connection-owned `session` key:

```jsonl
{"action":"update_context","request_id":"1","session":"thread-418","context":{"task":"issue-418"}}
{"action":"clear_context","request_id":"2","session":"thread-418"}
```

Codex selects the root or thread with the runtime `codex_session` and
`codex_thread` fields under the attested daemon owner. An optional
`session_id` on either agent action asserts the resolved address's local part.
An ownership mismatch returns `denied`.

The node assigns `updated_at` in Unix seconds and a `generation` on each
update. Tags become `stale: true` after 15 minutes. If they go unrefreshed for
another 15 minutes, the daemon omits them. Clearing tags removes them from
subsequent reads, and daemon restart discards all tags. Oversized and invalid values are refused,
including raw paths and worktree names containing a path separator.
The serialized context is capped at 512 bytes.

An optional `context` object can appear on authorized recipient listings,
locator results, and node observation snapshots. TCP recipient listings omit it. The daemon applies the selected
surface mask before serialization. Upgrade daemons and clients together because
older strict wire readers can reject the new field. Re-pin the gateway after the
daemon and client upgrade.

## Observe export v2 and `activity_changed`

<Status id="fleet-observer.activity-export" />

- **Query version:** `/fed/v2/observe/events` and `/fed/v2/observe/snapshot`
  require explicit `v=2`. Both `v=1` and omitted `v` return `400 Bad Query`.
- **`ExportSnapshot.activity`:** `{ "status": "enabled" | "disabled", "complete": bool }`.
- **`ActivityDescriptor`:** `{ state, block?, reason?, state_epoch, incarnation, revision, changed_at, fresh_at }`
  with closed enums (`idle | working | blocked | unknown`, `input | permission`,
  `background | scheduled_wake | aged | restarted | contradictory | unverified | evidence_lost | registry_unavailable | unreported | incarnation_ended`).
- **Single-endpoint scope rule (`activity_changed` only):** Applied identically
  on node egress and relay validation (including unrestricted targets): `from`
  must be a canonical typed `instance` or `subagent` endpoint on the exporting
  or verified leaf node (`svc:`, malformed, or cross-node `from` refused), `to`
  must be absent, and `from` must be in the peer's targets where set. Ordinary
  message event kinds keep their two-endpoint rules unchanged.



## Mission Control issuer routes

<Status id="mission-control.session" />
<Status id="mission-control.web" />

The optional Mission Control issuer uses the collector's configured HTTPS origin.
A non-loopback collector listener requires configured server TLS.
`GET /` serves the Sign-in shell when unauthenticated, a no-data shell when
`Sec-Fetch-Site` is not `same-origin` or `none`, and the authenticated SSR
roster plus hash-pinned `/assets/mc-roster.<hash>.{js,css}` on same-origin or
`none` navigations under a strict `'self'` CSP with
`require-trusted-types-for 'script'`. `GET /login/callback` returns `200` with
a same-origin refresh to `/`, and `POST /logout` redirects to `/`.

| Route | Credential or flow |
| --- | --- |
| `GET /login` | Begins authorization code login with PKCE S256, state, and nonce |
| `GET /login/callback` | Consumes the matching single-use state and `__Host-mc_flow` cookie |
| `POST /logout` | Revokes the browser session with exact Origin and a synchronizer token |
| `POST /oauth/device_authorization` | Starts a device grant for the configured native client ID |
| `GET /device` and `POST /device` | Browser review and approval or denial, with exact Origin and a synchronizer token for POST |
| `POST /oauth/token` | Polls the device grant with its original client ID |

Both cookies are host-only, Secure and HttpOnly with `Path=/`. The
flow cookie uses SameSite=Lax so the upstream top-level redirect carries it.
The `__Host-mc_session` browser cookie uses SameSite=Strict. Native handles use
`Authorization: Bearer`. A successful device poll consumes the grant and
returns `access_token`, `token_type`, and `expires_in` with
`Cache-Control: no-store`. Early polls get `slow_down`. Each early poll
increases the required interval by five seconds.

| `device_poll_secs` | 5 seconds |
| `device_codes_live`, `device_authorizations_per_min` | 16 live codes, 10 authorizations per minute |
| `device_code_attempts_per_session` | 5 attempts per 10 minutes |
| `session_idle_secs`, `session_absolute_secs` | 7 days and 30 days |

| `revocation_slo_ms`, `authority_watchdog_ms` | 1,000 ms and 250 ms |

### Planned Mission Control read transports

<Status id="mission-control.http" />

The session transport uses `/v1/mission-control/session` with WebSocket
subprotocol `xmsg.mission-control.v1`. The client begins with `hello`
and subscribes to a scoped view. The HTTP snapshot and SSE stream use
`/v1/mission-control/snapshot/{scope}` and
`/v1/mission-control/stream/{scope}`. Both use the same snapshot model,
and the stream carries subsequent events, gaps, and heartbeats.
Snapshot uses a browser cookie or a suitably scoped bearer. Stream uses a
native or machine bearer.

The lease expires at the earliest of the credential's idle expiry, absolute
expiry, and the connection lease cap. WebSocket close codes include 4401
for an expired lease and 4403 for revocation or a policy change. The cutoff
runs from the authority change. The issuer's live registry supplies this
deadline for the planned WebSocket and SSE writers.

#### Mission Control v1 messages and resume

Every message is a versioned JSON object. WebSocket offers
`xmsg.mission-control.v1`, then sends `hello` within five seconds before
`subscribe` or `unsubscribe`. The server accepts text only and ignores
compression offers. Subscriptions use `fleet`, `attention`, `node` or
`session` scope. Both HTTP bindings accept the same scope in the path.
Percent-encode the session endpoint path segment.

A `snapshot` is applied at its `final` part. A later `event` carries a
collector sequence and an opaque cursor. SSE sends a single JSON
message per `data` field and puts the cursor in `id` on events and final
snapshots. Resume using a WebSocket subscription cursor or SSE
`Last-Event-ID`; the scope and credential record must match. An invalid
or expired cursor resets the view through a `gap` and fresh snapshot.
A `tick` proves the connection is alive and leaves event age unchanged.

| WebSocket close | Meaning |
| --- | --- |
| 1002, 1003, 1009 | Invalid framing, binary frame, or size limit |
| 4400 | Invalid message or hello timeout |
| 4401 | Lease expired |
| 4403 | Revoked or policy changed |
| 4408 | Slow consumer |
| 4409 | Version or required capability unavailable |
| 4429 | Client rate exceeded |

The protocol defaults to a 16 KiB client message, 256 KiB server
message, 4 MiB snapshot, and a 15-second heartbeat. The initial upstream
is polled and reports `delivery: delayed`. The shared conformance
vectors are in `tests/vectors/mission-control/v1/` in the source tree.
Command routes and command capability are reserved for a later unit.
