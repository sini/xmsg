`xmsg serve` has three local Unix domain sockets in `$XDG_RUNTIME_DIR/xmsg/`. Each socket has
mode `0600`, in a `0700` directory. With federation, it also has an mTLS listener for
`/fed/v2/*`. Each JSON request body and socket frame refuses unknown fields. The error is
`bad_request`, and it names the unknown fields.

## `http.sock` & HTTP API routes

By default, xmsg serves HTTP only on `$XDG_RUNTIME_DIR/xmsg/http.sock`. A caller whose process
ancestry traces to a registered session or service acts as that sender. Other callers are
**[anonymous](/glossary/#anonymous-sender)** (`<from> · anon@<node>`). An anonymous caller can
send, and can read replies by `message_id`. It cannot call `reply` (`403 denied`).

```bash
sock="${XDG_RUNTIME_DIR:-/run/user/$(id -u)}/xmsg/http.sock"

# Health check
curl -s --unix-socket "$sock" http://localhost/healthz

# List live recipients
curl -s --unix-socket "$sock" http://localhost/v1/recipients

# Send a message
curl -s --unix-socket "$sock" http://localhost/v1/messages \
  -H 'content-type: application/json' \
  -d '{"to": "genie-guard", "text": "Please review.", "from": "ci", "idempotency_key": "run-42"}'

# Long-poll replies for up to 30s
curl -s --unix-socket "$sock" "http://localhost/v1/messages/<message_id>/replies?wait=30"
```

| Method & Route | Description |
|---|---|
| `GET /healthz` | Server health check (`200 OK`). |
| `GET /v1/recipients?name=&node=&kind=&status=&within=` | Lists recipients across this node and reachable peers (`{"recipients": [...], "nodes": [...]}`). |
| `POST /v1/messages` | Sends `{ "to", "text", "from"?, "idempotency_key"? }`. Returns `202 Accepted` with `{ "message_id", "address", "outcome" }`. |
| `POST /v1/messages/{id}/replies` | Replies to `{id}` with `{ "text", "idempotency_key"? }`. Requires traced session/service caller (or leaf principal). Returns `200 OK` with `{ "seq", "messageId", "createdAt", "replierSessionId", "text", "pushOutcome", "pushedMessageId" }`. |
| `GET /v1/messages/{id}/replies?after={seq}&wait={seconds}` | Reads stored replies to `{id}`, waiting up to `wait` seconds (max `60`, max `128` concurrent waiters). |
| `GET /v1/messages/{id}` | Returns the stored message record and its replies. |

### Local observation journal (planned)

`GET /v1/observe/events` reads bounded message metadata over `http.sock` from the
same UID. It is absent from the shared TCP router, including a leaf's TCP listener.
It grants no remote peer right and reads no message bodies or harness transcripts.

```bash
curl -s --unix-socket "$sock" \
  'http://localhost/v1/observe/events?after=0&limit=100'
```

The optional query fields are `epoch`, `after` and `limit`. Unknown fields and
invalid bounds return `400 bad_request`. `after` is a nonnegative sequence up to
`9223372036854775807`; `limit` defaults to `100`, with range `1..200`. No long poll
is available. Each page is at most 256 KiB and each event at most 4 KiB.

Without a cursor, the first page is a recent tail in ascending sequence order;
`initial_omitted` distinguishes that intentional omission from loss. Use `after=0`
to begin at the retained floor. To continue, pass the response's `epoch` and `next`
as the next request's `epoch` and `after`. `has_more` reports remaining retained
events at that snapshot. `floor`, `head`, `gaps` and `losses` describe continuity.
An old epoch or a cursor ahead of the journal produces an explicit reset; an
evicted cursor produces a gap. Sequence orders local observations, not globally
synchronized effects or agent progress.

This is **observation, not complete history**. Metadata is queued after a primary
commit; a crash can lose an observation before persistence. Each writer startup
adds a durable `writer_restart` gap with unknown loss, even when the epoch stays
the same. Known queue drops, capacity evictions and TTL expiry have separate
counters. A bounded capture overflow also reports a gap rather than inventing
intermediate transitions. A full or unavailable observer never blocks delivery.

The sidecar is `<configured-db-path>.observe.sqlite`, mode `0600`, beside the
primary database in its private directory. Primary schema version 3 is unchanged;
older binaries ignore the sidecar. Defaults retain seven days, 10,000 events or
16 MiB of stored metadata, whichever limit applies first. The byte budget is
logical metadata; SQLite indexes and journal overhead are additional. Idle
cleanup runs at least every ten minutes. The pending queue separately retains
at most 256 events or 1 MiB and drops oldest observations on overflow.

A corrupt or unsupported sidecar makes observation unavailable; it does not reset
message state or silently delete the journal. Observation errors return
`503 service_unavailable`. Metadata includes endpoint references, message/reply
correlation, source/capture/persistence times and the actual stored outcome.
`delivered`, `queued` and `delivery_unknown` retain their bus meanings; none
asserts that an agent read a message or finished a task.

Endpoint references stay absent when their node cannot be established. The
`body_availability` hint describes capture time: original send bodies are not
retained, and a retained reply at capture time is no promise that it still exists.

## `agent.sock` frames

A line-delimited JSON protocol. `xmsg mcp`, the hook handlers, the Pi extension and the Rust
service client's `AgentClient` use it:

| Request Frame | Response Frame |
|---|---|
| `{"action":"list","name"?,"node"?,"kind"?,"status"?,"within"?}` | `{"status":"ok","recipients":[…],"nodes":[…]}` |
| `{"action":"send","to","text","idempotency_key"?,"as_agent"?}` | `{"status":"ok","message_id","address","outcome"}` |
| `{"action":"reply","message_id","text","idempotency_key"?,"as_agent"?}` | `{"status":"ok","reply":{…}}` |
| `{"action":"replies","message_id","wait"?,"after"?}` | `{"status":"ok","replies":[…]}` |
| `{"action":"inbox","wait"?,"as_agent"?}` | `{"status":"ok","address":"<P>/<child>@<node>","messages":[…]}` |
| `{"action":"subagent","event","agent_id",…}` | `{"status":"ok",…}` |
| `{"action":"codex_hook","event","payload",…}` | `{"status":"ok","stdout",…}` followed by client `{"ack":"accepted"\|"abort"}` |
| `{"action":"codex_revoke","session_id","revoked"?}` | `{"status":"ok"}` (`xmsg register codex --revoke`/`--unrevoke` and `xmsg unregister --codex-session`; `revoked` defaults to `true`) |
| `{"action":"mcp_start","schema_version"?,"label"?,…}` | Sent once by `xmsg mcp` at startup to register its session; not for other clients |

## `register.sock` frames

These clients use `register.sock`:

- Antigravity credential registration;
- Pi long-polling;
- headless `svc` daemons (see [Daemon Protocol & Rust Client](/reference/service-client/));
- multiplexed plugin harnesses ([opencode](/harnesses/opencode/) and
  [Hermes](/harnesses/hermes/)).

### Multiplexed plugin protocol (`opencode`, `hermes`)

The plugin opens `register.sock` with `{"harness":"opencode"}` or `{"harness":"hermes"}`. The
answer is `{"status":"ok","node":"<node>"}`. Each later frame has a `request_id`, and the response
has the same `request_id`. Thus xmsg can answer tool calls while a `poll` waits on the same
connection:

| Frame | Response |
|---|---|
| `{"action":"register","session":S,"reclaim"?:{…}}` | `{"status":"ok","address":"<id>@<node>","reclaim":{…}}` |
| `{"action":"release","session":S}` | `{"status":"ok"}` (`S` answers `gone` thereafter) |
| `{"action":"continues","from":S1,"to":S2}` | `{"status":"ok","address":…}` (moves `S1`'s address to `S2`) |
| `{"action":"subagent","event":"start"\|"stop"\|"end","session"?:S,"agent_id":C,…}` | `{"status":"ok",…}` (binds/updates `<P>/<C>@<node>`) |
| `{"action":"list"\|"send"\|"reply"\|"replies"\|"inbox","session":S,"as_agent"?:C,…}` | Same response shape as `agent.sock`, acting as `S` (or `<P>/<C>@<node>`) |
| `{"action":"poll","wait":N}` | `{"action":"deliver","session":S,"address":…,"message_id":…,"from_name":…,"text":…,"envelope":…}` or `{"action":"timeout"}` |
| `{"action":"ack","session":S,"message_id":M}` | `{"status":"ok"}` |

## Federated `/fed/v2` wire routes

Only the mTLS `--fed-listen` listener serves these routes. They are separate from the local
loopback routes:

| Route | Method | Description |
|---|---|---|
| `/fed/v2/messages` | `POST` | Delivers a federated message (or relays a single-hop forward when the peer has `"forward"`). |
| `/fed/v2/replies` | `POST` | Delivers a reply back to the originating node. |
| `/fed/v2/messages/{id}/replies` | `GET` | Pulls stored replies for a message sent by an outbound-linked or leaf node. |
| `/fed/v2/sessions` | `GET` | Returns this node's filtered recipient list for mesh `list`. |
| `/fed/v2/inbox`, `/fed/v2/inbox/{id}/ack` | `GET`, `POST` | Long-polls and acknowledges items in a leaf or outbound-linked peer's hub mailbox. |
| `/fed/v2/attachments/{item_id}/{index}?offset=&length=` | `GET` | Planned: reads a bounded raw file range; requires the item's downstream peer and its current hop permission. |
| `/fed/v2/attachment/{query}` | `POST` | Planned: answers a peer-bound mailbox attachment query with raw bytes or a JSON error. |
| `/fed/v2/list/{query}` | `POST` | Posts a leaf or outbound-linked node's answer to a mailbox `list` query. |
| `/fed/v2/handoff`, `/fed/v2/handoff/ack` | `POST` | Transfers and acknowledges a parked Claude conversation queue across a user's machines. |

Mailbox control polling is planned for the next release. `GET /fed/v2/inbox?control=true&wait=30`
long-polls only peer-bound list and attachment controls, never a durable message. It uses a
separate bucket of 120 requests per minute (burst 120, refill two per second), with the same
current-peer and `leaf: true` admission as mailbox reads. `control=false` selects only durable
messages under the ordinary peer/inbox quotas. Omitting `control` retains the legacy combined
response and ordinary quota behavior. ACK uses the existing route and follows service ACK.

For mailbox pulls and ACKs, the authenticated peer must have `leaf: true` on the hub. Each peer
can access only its own mailbox. xmsg accepts the `inbox` string in `allow` and ignores it. Thus
old configurations that list it still load.

A full node with an outbound link needs `relayed` (or `relay`) when a pulled message's origin is
not the hub's canonical node name. A refused item gets a strict
`{"error":"denied","detail":"..."}` reply, and the node ACKs it at the hub. Thus it cannot block
later mailbox items. Mail that starts on the hub itself is delivered without this grant. The
check uses the existing origin fields and does not change the wire shape. It is on the main
branch and is not yet in a release.

## Error vocabulary

Each surface uses the same error codes. HTTP uses `{"error": <code>, "detail": …}`. Sockets use
`{"status":"error","error": <code>,"detail": …}`:

- **Addressing:**
  - `not_found` (`404`): No such recipient, message, or node.
  - `ambiguous` (`409`): Multiple recipients match; `detail` lists every candidate address.
  - `denied` (`403`): Peer rights (`allow`, `principals`, `targets`, `from`) refused the request,
    a caller that is not a party called `reply`, or a hub forward was not authorized.
  - `gone` (`410`): A process-bound session has exited: `pi`, a released `opencode`/`hermes`
    session, or an exited `X~n` fork.
  - `unavailable` (`503`): During bare-reference resolution, xmsg could not reach a node in the
    federated view. `detail` names the node.
  - `not_live` (`409`, node-to-node): A cache-routed send reached a node where the instance is now
    only `parked`.
  - `live_elsewhere` (`409`): A reclaim names an instance ID that is live on another connection.
- **Registration:**
  - `process_already_registered` (`409`): The connecting process already holds a registration for
    another service name.
- **Transport & Validation:**
  - `bad_request` (`400`, including unknown JSON fields or malformed addresses), `bad_sender`
    (`400`), `conflict` (`409`), `payload_too_large` (`413`), `rate_limited` (`429`),
    `service_unavailable` (`503`), `peer_unreachable` (`503`), `credentials_stale` (`503`),
    `inbox_unavailable` (`502`), `inbox_timeout` (`504`), `insecure_socket_dir` (`500`) and
    `internal` (`500`).


Federated file references and fetch routes are planned for the next release. Message and reply
envelopes carry an optional `attachments` array; empty arrays are omitted for compatibility.
A mailbox control item with `kind: "attachment"` carries `query`, `item_id`, `index`, `offset`
and `length`. Only the authenticated queried peer can answer, once. Raw ranges use the
message-body limit and the separate `attach:<peer>` rate bucket. See
[file attachments](/concepts/attachments/) for staging, read permissions, expiry and an example.
