The application chart in `charts/xmsg` runs one full [node](/glossary/#node) or
federation [hub](/glossary/#hub) per release, or, with `mode: leaf`, a
[leaf sidecar](#leaf-sidecar) beside your application. It does not bundle harnesses,
a gateway or a certificate issuer. Install directly from a repository checkout.

<Aside type="note" title="Checkout version">
The chart and examples are planned for the next release. The disposable fixture
has been verified with Helm 4.3.1, kind 0.33 and Kubernetes 1.37: two releases exchanged
a message and reply, and a recreated pod retained its stored reply and exchanged
another message. Uninstalling and reinstalling both releases also retained their
PVCs, identities and stored reply, followed by a new smoke exchange. This establishes
the fixture behavior, not production storage or
network-plugin behavior.
</Aside>

## Prepare a disposable two-node example

The verified disposable kind cluster was named `xmsg-fei9`; use its explicit
kubeconfig at `examples/helm/.local/kubeconfig`. Before these commands, build
and load the checkout's [container image](/operations/docker/) onto its nodes under
`ghcr.io/sini/xmsg:latest`. The `Never` pull policy below assumes that image is
already present; the helper's `--image` must match the loaded repository and tag.

From the repository root, with Python 3, OpenSSL, kubectl and Helm available:

```sh
export KUBECONFIG="examples/helm/.local/kubeconfig"
python3 examples/helm/prepare.py --image ghcr.io/sini/xmsg:latest
kubectl create namespace xmsg-helm-demo --dry-run=client -o yaml | kubectl apply -f -
kubectl -n xmsg-helm-demo create secret tls xmsg-a-tls \
  --cert=examples/helm/.local/a/node.crt --key=examples/helm/.local/a/node.key \
  --dry-run=client -o yaml | kubectl -n xmsg-helm-demo apply -f -
kubectl -n xmsg-helm-demo create secret tls xmsg-b-tls \
  --cert=examples/helm/.local/b/node.crt --key=examples/helm/.local/b/node.key \
  --dry-run=client -o yaml | kubectl -n xmsg-helm-demo apply -f -
helm upgrade --install a charts/xmsg -n xmsg-helm-demo \
  -f examples/helm/.local/a/values.json --set image.pullPolicy=Never --wait --timeout 90s
helm upgrade --install b charts/xmsg -n xmsg-helm-demo \
  -f examples/helm/.local/b/values.json --set image.pullPolicy=Never --wait --timeout 90s
python3 examples/helm/smoke.py --kubeconfig "$KUBECONFIG"
```

`prepare.py` creates disposable 30-day identities and derives their canonical
names and peer pins. It retains existing keys and values rather than replacing
them. `OPENSSL` can select the OpenSSL executable. Keep `.local/` private and out
of version control; review retained values when changing the image or namespace.
The chart itself only references existing TLS Secrets.

The smoke helper requires `--kubeconfig`. It starts a temporary version-reporting
service if needed, lists it through federation, sends `version?`, and checks the
correlated reply. Its success line is
`PASS: two Helm releases, federated send and correlated version reply`.

## Configure a persistent node

| Value | Purpose |
| --- | --- |
| `canonicalNodeName` | Required certificate-derived name for local probes; not a nickname |
| `fullnameOverride` | Optional override for the generated resource name prefix (defaults to `<release>-xmsg`) |
| `serviceAccount.name` | Optional ServiceAccount name override in `leaf` mode (defaults to `xmsg.fullname`) |
| `tls.existingSecret` | Existing `kubernetes.io/tls` Secret with `tls.crt` and `tls.key` |
| `peers` | Peer entries written inside the `{"peers": ...}` JSON configuration |
| `ca.existingConfigMap` | Optional public CA bundle files mounted under `/etc/xmsg/ca` |
| `trustedServices` | Optional service name → executable mapping for `--svc-exe` |
| `image.repository`, `image.tag`, `image.digest` | Image selection; a nonempty digest takes precedence over tag |
| `resources` | Container requests and limits; empty by default |
| `persistence.size`, `persistence.storageClassName` | PVC capacity and optional StorageClass; empty class uses the cluster default |
| `securityContext` | UID, GID and filesystem group, each defaulting to `10001` |

Pinned and CA peer policy still belongs to xmsg; see
[Federation](/concepts/federation/). For CA peers, use the mounted public bundle path
in the peer's `ca` field. The chart provides no issuance or renewal controller.
A pod SPIFFE URI SAN `spiffe://<trust-domain>/ns/<ns>/sa/<sa>` gives the canonical
node name `<sa>.<ns>`.

Replicas are fixed at **one**. The retained PVC holds
`/var/lib/xmsg/state/xmsg.db` and SQLite sidecars. Never attach it to another running
daemon: stop the old writer before replacing or restoring state. A storage access
mode alone is not a one-writer guarantee. Changing the configured UID for existing
state requires an offline ownership migration.

The pod runs without root, privilege escalation or capabilities, with a read-only
root filesystem. The TLS Secret is read-only; its keys map to `node.crt` and
`node.key` with mode `0440` and filesystem group access. `/run` and the empty
harness placeholders are disposable `emptyDir` volumes; no host harness directories
are mounted. Startup uses no shell, init container or `chown` command.

Only federation TCP `7788` has a ClusterIP Service. `XMSG_LISTEN` is unset, so HTTP
remains on `/run/xmsg/http.sock`. Readiness and liveness execute local
`xmsg list --http-sock /run/xmsg/http.sock --node <canonical-name> --json`, with a
ten-second timeout above the command's five-second request budget. Supplying the
correct canonical name keeps these probes local.

Mounted federation certificates, keys and CA bundles are checked for content
changes every 30 seconds by default. TLS Secret rotation does not require an
issuer controller in this chart or a forced pod restart.

## Owned subdirectories for custom pods

For custom pod manifests, place the database inside an owned private child of a
shared volume. `--db-path /var/lib/bus/state/xmsg.db` makes
`/var/lib/bus/state` the state root; pinning all sockets does not bypass its UID
and permission checks. `fsGroup` alone can leave the volume root owned by root
with mode `2777`, which is insufficient.

For example, use an init container running as the **same UID** as xmsg to create
the child directory. This fragment supplements a custom manifest; it does not
change the chart's startup described above. Use an image containing `mkdir`:

```yaml
initContainers:
  - name: prepare-state
    image: busybox:1.37
    securityContext:
      runAsUser: 10001
      runAsGroup: 10001
      allowPrivilegeEscalation: false
    command: ["mkdir", "-m", "0700", "/var/lib/bus/state"]
    volumeMounts:
      - name: state
        mountPath: /var/lib/bus
```

This first-creation example assumes the shared mount permits UID `10001` to
create children and `state` does not already exist. For persistent state,
preprovision an owned private PVC subdirectory, or have initialization validate
an existing child without taking it over. Never chmod/chown the whole shared
mount. Preserve the existing UID and data across restarts. Select the DB inside
that child and prepare private socket parents separately; see
[containers and pods](/operations/runtime-and-systemd/#containers-and-pods).

## Optional federation ingress policy

NetworkPolicy is **off by default**. Enable it with `networkPolicy.enabled` and
set `networkPolicy.allowedPeers`. For example, only selected gateway pods in the
gateway namespace may reach federation:

```yaml
networkPolicy:
  enabled: true
  allowedPeers:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: gateway
      podSelector:
        matchLabels:
          app.kubernetes.io/name: xmsg-mcp-gateway
```

Both selectors in the **same peer entry are ANDed**. Separate entries are
alternatives. An empty allowlist renders `ingress: []`, denying ingress; it does
not render an allow-all rule with `from: []`. The policy permits only TCP `7788`
and leaves DNS and egress unchanged. Other ingress policies selecting the same
pod can also allow traffic. mTLS and xmsg peer policy remain required.

<Aside type="caution" title="Enforcement depends on the network plugin">
Default kind networking does not enforce NetworkPolicy. The fixture's raw TCP
namespace/pod allow, deny and deny-all checks used an enforcing controller in a
disposable cluster. Such a test controller is optional fixture infrastructure;
production needs its own enforcing CNI. Merely creating a NetworkPolicy object
is not evidence of enforcement.
</Aside>

Only in a disposable cluster with an enforcing CNI, run the policy fixture:

```sh
python3 examples/helm/policy-smoke.py --kubeconfig examples/helm/.local/kubeconfig
```

It checks new raw TCP connections with policy off, namespace denial, pod-label
denial/restoration and an enabled empty allowlist. It temporarily changes release
`a`'s ingress policy, restores it to off, and cleans up its random probe resources.
The verified fixture used a separately installed `kube-network-policies` v1.1.3
DaemonSet. The chart does not install that controller.

## Leaf sidecar

A workload that only needs to send and receive messages runs xmsg as an outbound-only
[leaf](/concepts/hubs-and-leaves/#leaf-node-mode---leaf) in its own pod. With
`mode: leaf` the chart renders a one-replica Deployment: a `prepare-state` init
container, the xmsg leaf container and your application containers, all as one UID and
sharing a memory `emptyDir` as `XDG_RUNTIME_DIR`. It also renders a ServiceAccount with
no token and a `peers.json` that dials your hubs. No Service, StatefulSet or
NetworkPolicy is rendered, and the full-node values (`canonicalNodeName`, `peers`,
`persistence`, `networkPolicy`) are unused.

<Status id="xmsg.chart-leaf" />

The render check `ci/tests/check-chart-leaf.py` verifies the invariants below against
`examples/helm/leaf-values.yaml`.

A minimal values file (`examples/helm/leaf-values.yaml`). It's an example, so adapt it:

```yaml
mode: leaf
image:
  repository: ghcr.io/sini/xmsg
  tag: latest
tls:
  # kubernetes.io/tls Secret with tls.crt, tls.key and ca.crt.
  existingSecret: my-app-xmsg-tls
securityContext:
  runAsUser: 65532
  runAsGroup: 65532
  fsGroup: 65532
leaf:
  principal: my-app
  hubs:
    - name: alice.hub
      address: hub.example.com:7788
      identity: spiffe://example.com/host/hub/user/alice
  containers:
    - name: my-app
      image: registry.example.com/my-app:1.0.0
      volumeMounts:
        - name: tmp
          mountPath: /tmp
  volumes:
    - name: tmp
      emptyDir: {}
```

```sh
helm install my-app ./charts/xmsg -n my-app -f leaf-values.yaml
```

For a concrete application overlay, `genie-agent` ships
[`examples/helm/genie-guard-values.yaml`](https://github.com/sini/genie-agent/blob/main/examples/helm/genie-guard-values.yaml)
to pair `genie-guard` with the leaf sidecar (`leaf.containers` and `leaf.volumes`).

Each hub entry becomes `{"address", "ca": "/etc/xmsg/tls/ca.crt", "identities": [identity],
"allow": ["list"]}`. The hub's own `peers.json` needs a matching entry for the leaf, with
`"leaf": true` and the leaf's SPIFFE identity; see
[hub-side durable mailbox](/concepts/hubs-and-leaves/#leaf-node-mode---leaf). Each
`leaf.containers` entry is rendered as given, plus `XDG_RUNTIME_DIR=/run`, the `runtime`
mount and, if it sets no `securityContext`, the hardened one. `leaf.volumes` adds the
pod volumes those containers mount. The app reaches the leaf at
`/run/xmsg/register.sock` and `/run/xmsg/agent.sock`.

What each invariant is for:

| Invariant | Why |
|---|---|
| `prepare-state` runs `mkdir -m 0700 -p /var/lib/xmsg/db` as the pod UID | xmsg refuses a DB directory it does not own at `0700`; an `fsGroup` `emptyDir` root is `root:<gid>` `2777`. |
| One UID for every container | The leaf admits a registration on `register.sock` by `SO_PEERCRED` UID, because it can't attest an executable across containers. |
| A shared memory `emptyDir` at `XDG_RUNTIME_DIR` | The app and the leaf meet on Unix sockets there; the leaf makes its `xmsg/` socket directory `0700` itself. |
| `--agent-sock`, `--leaf-register-sock`, `--db-path` pinned | With every endpoint explicit, xmsg derives no default directory it would refuse as unsafe. |
| `--listen 127.0.0.1:7787` and no `--fed-listen` | `--leaf` requires an HTTP listener; loopback keeps it inside the pod's network namespace, and a leaf accepts no federation connections. |
| Hubs allowed `list` only | The leaf withholds `list` otherwise, and every bare send on the hub reports the leaf `unavailable`. |
| `automountServiceAccountToken: false` | Neither container calls the Kubernetes API. |
| `readOnlyRootFilesystem`, `drop: [ALL]`, `runAsNonRoot` | Neither needs a writable root, a capability or root. |
| `replicas: 1`, `Recreate` | One writer per database. |

The state `emptyDir` is per pod: the leaf's queue starts empty on a new pod, and the
hub's durable mailbox holds anything not yet acknowledged.

### SPIFFE certificate

The TLS Secret comes from your issuer. With cert-manager, a Certificate like this one,
in the release namespace, gives the leaf a URI SAN bound to its namespace and
ServiceAccount (`<release>-xmsg`). It's an example, so adapt it:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: my-app-xmsg
  namespace: my-app
spec:
  secretName: my-app-xmsg-tls
  issuerRef:
    name: my-ca            # your CA issuer
    kind: ClusterIssuer
    group: cert-manager.io
  uris:
    - spiffe://example.com/ns/my-app/sa/my-app-xmsg
  usages: [digital signature, key encipherment, server auth, client auth]
  # Short-lived: expiry stands in for revocation. xmsg reloads rotated files.
  duration: 24h
  renewBefore: 8h
  privateKey:
    algorithm: ECDSA
    size: 256
    encoding: PKCS8
    rotationPolicy: Always
```

### Optional: restrict SPIFFE URIs at admission

A namespace that can create Certificates against a shared CA issuer can name any
identity. A ValidatingAdmissionPolicy can hold each Certificate for that issuer to
exactly one URI SAN, `spiffe://<trust-domain>/ns/<its namespace>/sa/<sa>`, and leave
CertificateRequests to cert-manager's controller. It's an example, so adapt it:
replace `my-ca`, `example[.]com` and the controller's service-account name with your own.

```yaml
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: my-ca-spiffe
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: [cert-manager.io]
        apiVersions: ["*"]
        operations: [CREATE, UPDATE]
        resources: [certificates, certificaterequests]
  matchConditions:
    - name: issued-by-my-ca
      expression: >-
        object.spec.issuerRef.name == 'my-ca' &&
        has(object.spec.issuerRef.kind) && object.spec.issuerRef.kind == 'ClusterIssuer'
  validations:
    - expression: >-
        request.resource.resource != 'certificaterequests' ||
        request.userInfo.username == 'system:serviceaccount:cert-manager:cert-manager'
      message: only cert-manager's controller may request from my-ca; create a Certificate
    - expression: >-
        request.resource.resource != 'certificates' ||
        (has(object.spec.uris) && size(object.spec.uris) == 1 &&
         object.spec.uris[0].matches('^spiffe://example[.]com/ns/' + request.namespace +
           '/sa/[a-z0-9]([-.a-z0-9]*[a-z0-9])?$'))
      message: a my-ca certificate carries exactly one URI SAN, spiffe://example.com/ns/<its namespace>/sa/<sa>
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: my-ca-spiffe
spec:
  policyName: my-ca-spiffe
  validationActions: [Deny]
```

The policy checks the name a namespace asks for. It does not check that the
ServiceAccount exists or that the pod runs as it; mTLS and the hub's peer entry still
decide what the leaf may do.

## Rendering peers with `lib.fleet`

A hub-mode Helm chart can take `values.peers` from
[`lib.fleet.peersRenderedFor`](/operations/fleet-topology/#renderers). A fleet leaf is
rendered outside the chart (in leaf mode the chart takes no fleet peers); the external path
can validate its rendered map with `lib.fleet.checkFinal` (on `main`, unreleased).
