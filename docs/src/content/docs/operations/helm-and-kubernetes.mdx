In a Kubernetes cluster, `xmsg` runs in one of two ways. This includes gVisor-sandboxed pods:

- as a central federated [hub](/glossary/#hub);
- as an in-pod `--leaf` sidecar next to a service worker (`genie-guard`, `matrix-xmsg` or
  `xmsg-mcp-gateway`).

These rules apply:

- **Pod node identity:** A pod certificate with the SPIFFE URI SAN
  `spiffe://<trust-domain>/ns/<ns>/sa/<sa>` gives the canonical node name `<sa>.<ns>` (see
  [Federation](/concepts/federation/#self-authenticating-node-names)).
- **Leaf sidecar mode (`--leaf`):** Mount one `emptyDir` volume at `$XDG_RUNTIME_DIR/xmsg` in
  the service container and in an `xmsg` container. Both run under the same UID (`10001`).
  **Leaf mode needs `--listen`**, also when the service uses the shared Unix sockets:
  `xmsg serve --leaf --leaf-principal svc:<name> --listen 127.0.0.1:7787`
  (or set `XMSG_LISTEN`). Keep the listener inside the pod's isolated loopback namespace. See
  [Hubs, Leaves & Gateways](/concepts/hubs-and-leaves/#leaf-node-mode---leaf).
- **Secret rotation:** Every 30 seconds (`--fed-reload-interval-secs`), `xmsg serve` checks the
  SHA-256 content hash of `--fed-cert`, `--fed-key`, `--peers-file` and the `ca` bundles. Thus it
  picks up Kubernetes `Secret` symlink (`..data`) rotations automatically. The pod does not
  restart.
