## Start with doctor

<Status id="xmsg.doctor" />

Run these as the user who runs the daemon:

```sh
xmsg doctor
xmsg doctor --json
```

Doctor checks setup without changing it. Each result has a status and a fix hint. A
`pass` applies only to the named check; it is not a guarantee that the whole node works.
A `warn` needs interpretation, and a `fail` means a checked requirement failed. Only a
failure makes the command exit `1`; warnings alone exit `0`. JSON includes the checks,
summary counts, the CLI's `client_version`, its `client_build_revision` and a
`not_checked` list.

The `collector.sqlite_engine` metadata line is always informational, including when the linked and required SQLite versions differ. It describes this CLI binary, performs no file or network I/O, and does not validate a collector configuration. `info` rows are excluded from summary counts and do not change the exit code. A collector startup error remains the authoritative engine refusal.

For a custom installation, select the paths you want checked:

```sh
xmsg doctor \
  --http-sock /run/user/1000/xmsg/http.sock \
  --agent-sock /run/user/1000/xmsg/agent.sock \
  --register-sock /run/user/1000/xmsg/register.sock \
  --db-path /home/USER/.local/state/xmsg/xmsg.db \
  --peers-file /home/USER/.config/xmsg/peers.json
```

These are examples, not paths to copy unchanged. Doctor checks explicit paths or its
local defaults; it cannot prove that the running daemon uses the same configuration.
`--fed-cert` can supply the public federation certificate for peer-config consistency.
`--enroll-state` selects saved enrollment state for optional credential checks.

## Interpret a result

| Check or symptom | What it means | What to do next |
| --- | --- | --- |
| Runtime directory or socket fails | A selected path is missing, has the wrong type, owner or permissions. | Check the daemon user, runtime directory and socket flags. Correct the installation deliberately; doctor does not create directories or change modes. |
| Daemon health fails | The bounded request to `GET /healthz` did not give the expected health response. | Check that the daemon is running and that `--http-sock` selects its socket. Read the service logs. |
| Daemon build revision warning | The daemon and client report different known revisions, or revision metadata is unavailable. | Check the intended source pin and the selected Unix socket. Nix builds embed the revision; plain Cargo builds may report `unknown`. The crate version alone is insufficient. A warning does not fail the health check or prove the daemon needs restarting. |
| Registered process liveness warning | A registration has gone/stale process evidence, or bounded read-only diagnostics cannot establish liveness. | Inspect the named local process and registration deliberately. `live` is only process evidence; it does not prove the harness is addressable or a message can be delivered. Missing `/proc` or denied platform inspection may leave evidence unknown and produces one portability warning per run. |
| Harness binary path drift (`harness.codex_exe`, `harness.agy_exe`) | `info`: a live Codex or Antigravity owner is running from a different canonical path than `--codex-exe` / `--agy-exe` (for example after a Nix store upgrade) and was admitted by canonical executable name. `warn`: `--codex-exe-strict` or `--agy-exe-strict` refused admission because the path differed. | On `info`, no action is needed unless you want the harness on the newer build. On `warn`, restart the harness (and any managed Codex app-server) on the configured binary, or omit `--*-exe-strict`. |
| Sessions directory warning | Health reports that the sessions directory is missing. | Check the harness path if this node hosts sessions. A service-only node may not need one. |
| Database schema or additive requirements | Newer schemas fail because startup refuses them; planned (<Status id="xmsg.install-contract" />): populated unversioned (v0) and older (`0 < v < 3`) schemas are refused before any write, preserving existing bytes and rows intact. Missing same-version tables, indexes or additive columns warn by operation name. | Check the selected DB path, preserve a backup and follow a verified migration or export procedure. Version equality is not backfill or integrity certification; optional enrollment schema is conditional. |
| Installation state root, legacy guard, or competing service manager (`install.*`) | Planned (<Status id="xmsg.install-contract" />): `install.state_root` fails when the state root is not owned by the service UID with mode `0700` (setgid `02700` allowed); `install.legacy_guard` fails when an existing legacy DB, enrollment identity, or `peers.json` would be bypassed; `install.service_owner` fails with `ambiguous` when two or more service managers target the same install (setting `endpoints_usable: false`). | Stop and disable competing managers, pin compatible explicit paths (`--db-path`, `--enroll-state`, `--peers-file`, `--*-sock`) for legacy installs, or reconcile unproven runtime directories offline before removing anything. Doctor never locks `serve.lock` or repairs paths implicitly. |
| Journal/WAL/SHM state | Doctor reports stat-only type and size. Live WAL/SHM can be expected; down or unknown daemon state with sidecars warns about an unclean or uncertain shutdown. | Keep the sidecars. The next normal SQLite start handles recovery; doctor does not open sidecars, recover or checkpoint. Presence/size does not prove journal hotness or corruption. |
| Observation sidecar warning | The expected `<database>.observe.sqlite` file is absent or its metadata needs attention. | Check the observer setup and file ownership. Doctor does not open the journal writer or initialize a sidecar. |
| Peer configuration fails | The selected configuration fails the existing `check-peers` parser or certificate consistency check. | Correct the named configuration issue, then run doctor again. Parsing does not prove peer reachability or the daemon's loaded configuration. |
| Enrollment expiry fails | Saved metadata says the enrolled certificate has expired. | Follow the enrollment renewal procedure. Doctor does not renew it. |
| Enrollment renewal warns | The certificate has reached two-thirds of its recorded lifetime. | Schedule renewal. For a 24-hour certificate this is 16 hours after issuance; a fixed seven-day threshold would be misleading. |
| Loaded leaf certificate expired | The running daemon's actually loaded leaf certificate has expired. | Renew and reload that node's identity through the normal procedure. This is a failure; a certificate file selected by the CLI is not substituted for the loaded certificate. |
| Loaded leaf expiry warning | The loaded certificate expires within the smaller of seven days or one-third of its lifetime. | Schedule renewal. This threshold also covers short-lived certificates: a 24-hour leaf warns within its final eight hours. |
| Peer mTLS diagnostic warning | A bounded daemon-side probe could not establish reachability, or an ordinary peer was addressless or unattempted. Configured leaves with empty addresses or reserved `.invalid` hostnames report `INFO: outbound-only leaf, reached via its hub`; they are excluded from partial coverage and make no TLS, expiry or clock claim. Real-address leaves remain unknown and warn. | Inspect the peer's intended configuration and connectivity. Unknown is not evidence of a bad peer, and TLS success does not establish application permissions or delivery readiness. Peer results warn at most. |
| Observed clock offset warning | The peer HTTP date differs from the local clock beyond the 120-second tolerance, accounting for uncertainty. | Compare both clocks with a trusted time source. The diagnostic cannot say which clock is wrong. Missing/bad dates, unexpected status or local clock jumps leave the offset unknown. |
| CA TLS warning | The optional CA TLS handshake did not succeed. | Check connectivity and configured trust. A successful handshake establishes TLS reachability, not enrollment application health or login readiness. |
| MCP `reply` returns `gone:`, `not_found:`, `inbox_unavailable:`, `inbox_timeout:`, or `reply delivery failed: push_failed` | xmsg stored the reply, but pushing it to the other party's live inbox failed (`sender_gone` or `push_failed`). | For `gone:` / `not_found:`, the recipient exited or its socket is missing; check `xmsg list` and start a new exchange with `send` if needed. For `inbox_unavailable:` / `inbox_timeout:`, inspect the target harness and daemon logs before retrying. |
| Raw socket `attach` with `path` fails with `Operation not permitted` or times out on macOS | Direct `agent.sock` or `register.sock` `path` staging opens the file inside `xmsg serve`; a background `launchd` daemon does not inherit terminal TCC access to `Documents`, `Desktop` or `Downloads`, and Nix store-path upgrades invalidate per-binary TCC grants. | Stage bytes from the caller with inline `data` or chunked `upload` frames, or send through `xmsg mcp`, which reads `path` entries in the client process. |

Doctor uses only the explicit Unix read-only liveness snapshot to inspect registrations.
It never falls back to ordinary recipient listing, which can synchronize claims and deliver
queued work. An older daemon, cold runtime, unsupported source or truncated response
leaves uncertain evidence unknown; a gone/stale registration warns rather than fails.
Historical seen rows with missing identity are informational, and catalogue-scope partial
coverage alone does not warn. A missing row does not prove a process is gone. Doctor also
avoids enrollment-pending APIs and commands that initialize
stores. It does not send, acknowledge or consume a message, mint a token or load a private
key for a diagnostic repair. Federation probes run inside the daemon using its loaded
identity, only when doctor requests them over the Unix socket. The CLI never loads a
private key or dials a peer as a fallback. Probes may update normal connection counters
or admission caches during a handshake, but make no persistent or application-state
writes. An older or unavailable daemon leaves the result unknown.
The response deadline is bounded, but the system DNS resolver may finish an in-flight lookup after its request is cancelled.

## CA application health

<Status id="xmsg.ca-health" />

```sh
xmsg doctor --enroll-ca-dir /absolute/path/to/ca --json
```

The running authority reports its loaded public root, policy-reload status and pending
device approval count through a same-UID Unix-only read-only view. Configured disabled
CA enrollment passes its configuration check; missing configuration evidence is unknown.
An expired root fails. A root within the smaller of seven days or one-third of its
lifetime warns. A degraded policy reload warns while the last accepted policy remains
loaded. Pending approvals warn when nonzero; zero passes and unavailable counts warn.
Counting does not prune expired sessions or cancel approvals.

Without that view, `--enroll-ca-dir` checks explicitly selected installed public-root
and signing-key metadata, labeled installed, not loaded. Enabled state and pending
counts stay unknown. A missing or unsuitable signing key warns: the daemon may retain its loaded signer.
Doctor never opens, reads, loads or tests the key and cannot prove it matches the root
or can issue certificates. It neither approves nor denies requests. Use normal CA
operations for any fix. The client enrollment TLS probe remains separate and does not
establish application readiness. See [CA operations](/operations/enrollment-ca/).

## Primary schema views

<Status id="xmsg.schema-status" />

For a live daemon, an existing regular WAL and SHM permit an ordinary read-only metadata
reader; SQLite's reader marks can update the existing SHM. A rollback-journal database also
permits `mode=ro` when no journal, WAL or SHM is present. Doctor rechecks absent sidecars and
main-file fingerprints; detected concurrent changes make the observation uncertain. Normal
SQLite read locks are allowed, but the probe takes no writer reservation and performs no
writes. A WAL database without its existing pair, or any rollback journal, remains unknown.

With the daemon down or unresponsive and sidecars present, doctor uses stat only and leaves
SQLite recovery to startup. With no sidecars, it opens `mode=ro&immutable=1`, then rechecks
metadata for concurrent changes. No mode is an integrity or live-backup guarantee.
Symlinks in the DB path's parent directories are resolved; a DB file that is itself a symlink
is refused as an invalid target.

Results from a different or unknown client/daemon revision are labelled `next start of THIS
binary`. They describe this binary's startup requirements for the selected DB, whose path
may differ from the running daemon's. Named requirements describe structural table/index/
column additions; no migration ledger exists to certify historical backfills. Enrollment
schema is conditional. Present optional tables, or missing tables when the daemon reports
enrollment disabled, are informational; missing tables with enabled/unknown enrollment
still warn. This does not certify the rest of the loaded configuration. No migration,
checkpoint, VACUUM or recovery is run by doctor.

## Intermittent agy delivery timeouts on macOS

<Status id="agy.macos-locks" />

On macOS, an Antigravity delivery could time out or leave its `agy` child running when another
delivery or connection was being set up at the same moment: the child inherited descriptors it
should not have held. The fix marks those descriptors close-on-exec before `agy` starts and kills
the child when a delivery times out. Linux was not affected. Commands run by `xmsg service exec`
get the same close-on-exec treatment.

## agy and Codex lock state on macOS

<Status id="agy.macos-locks" />

macOS has no `/proc/locks`. xmsg reads a process's lock state from the `FWASLOCKED` flag that
`proc_pidfdinfo` reports for each open file. The flag is sticky: `flock(2)` sets it, and it stays
set after `LOCK_UN` until that open file is closed. Only a closed file clears it.

- **Antigravity:** the flag only nominates the holder of a presence lock. Once xmsg has seen a
  holder, it watches the file with `kqueue` `NOTE_FUNLOCK`. The watch fires on an unlock, or when
  a locked file is closed, and from then on xmsg treats that process as released, whatever its
  flag still reads. When xmsg looks for a holder it has not yet watched and finds more than one
  unreleased process with the flag set on that file, for example a child that inherited the
  locked descriptor without close-on-exec, it reports no holder, and the conversation is not
  listed until only one remains. A holder already watched is not affected. A lock taken and
  released before xmsg first sees it reads as held. A holder that is starting a child when xmsg
  first looks briefly shares its descriptors with that child, reads as ambiguous, and is listed
  on the next look.
- **What listing before the first turn relies on:** listing and delivering to an agy conversation
  before its first hook turn relies on two agy behaviours, measured on agy 1.5.3: agy opens its
  presence lock close-on-exec, so its MCP and command children never hold it, and it holds the
  lock for the whole conversation, with no unlock during tool calls; the only release is at
  exit. If another version does not behave this way, xmsg treats the lock as unattested, which
  fails closed, and the conversation is reached through the hook path after its first turn, as
  before.
- **A holderless `.lock` file is normal:** agy leaves the presence `.lock` file behind when it
  exits. A lock file with no holder is a finished conversation; it is not listed.
- **Codex:** admission reads the flag directly. After an explicit unlock that leaves the lock file
  open, admission can still read the owner as holding the writer lock. The lease watch still
  detects the release through `NOTE_FUNLOCK`, so on macOS even a close followed by a reopen of the
  same lock file starts a new lease generation.

## What remains unchecked

Doctor reports the running daemon's version and build revision when its Unix health
response supplies them; missing metadata remains unknown. It does not establish loaded
configuration, historical backfill completion, actual journal hotness, CA application health
or harness addressability. The bounded federation probe reports mTLS reachability,
leaf expiry and observed offset with uncertainty; it is not a complete peer-health or
clock-correctness guarantee.
Registered owner-process liveness does not prove a usable Codex writer lease, message
delivery or task completion. Treat these as separate investigations, not implied successes. Doctor offers no automatic database recovery or
integrity guarantee. See the [CLI reference](/reference/cli-and-mcp/#xmsg-doctor)
for its options and output contract.

### Interpreting the process catalogue

<Status id="xmsg.recipient-snapshot" />

A large historical catalogue does not imply that hundreds of processes are unhealthy.
For example, five live registrations plus 163 `seen` rows lacking a process identity appear
as one aggregate: five live and 163 unknown, with `missing_identity=163`. That history is
informational. A registered process whose observation is unknown, a probe failure, or a
gone process still warns. Only gone rows get individual details, capped at 20; the aggregate
keeps the full total. A truncated response still warns, while the catalogue-scope `partial`
flag alone does not.

## Collector relay failures

<Status id="fleet-observer.reverse-relay" />

The reverse collector reports fixed failure states: unsupported (501),
unavailable (503 or a disconnected leaf), invalid response (400 or malformed
metadata), denied (403), rate limited (429), and timeout. None proves empty or
healthy traffic. Check the configured full hub/leaf identities, the exact enabled
route and independent `observe` grant at both nodes. Do not add a leaf listener
or custody transport as a fallback. Collector changes apply on restart.

Previously validated observations may remain visible as stale, labeled `via hub`
with their original ages. Restart, denied access and changed scope hide history
until validation succeeds. Missing or inconsistent stored relay origin refuses
the history rather than treating it as direct. Downgrading to an older collector
destructively purges relay history; save any required operational evidence before
choosing that downgrade. See [relay configuration](/operations/fleet-observer/#collector-relay-source).

## Discovery source unavailable

<Status id="xmsg.discovery" />

A configured source that is not compiled into the build stays off and cannot permit a source-dependent missing address. Keep a static address or an existing supported hub route until the source integration is available. A failed static address never falls through to a discovered candidate. Unknown-node and ambiguity results describe routing knowledge, not a grant of trust from an announcement. The standalone collector does not use daemon discovery.

## LAN discovery on macOS: Local Network permission

<Status id="xmsg.discovery" />

With [LAN discovery](/concepts/discovery/) enabled, `xmsg doctor` reports a `discovery.mdns`
check from the daemon's local health response (plus a standing `discovery.announce` warning
whenever `discovery.announce` is loosened to `"always"`):

- `active` and `off` pass, as does `starting` within its first `15` seconds (past `15`
  seconds, a stuck `starting` responder warns).
- `unverified` is the normal at-rest state when no announcement window is open (outbound
  random-label IPv4 multicast `sendto` succeeded without error, and positive LAN echo is
  checked only while announcing). Because an allowed browse-only Mac at rest is not a
  fault, `xmsg doctor` reports `unverified` as `info` (excluded from pass and warning totals).
- `permission_suspected` warns after `3` consecutive debounced outbound multicast send
  failures (measured on macOS `26.5.2` under `launchd`: toggling Local Network off makes
  random-label multicast `sendto` return `EHOSTUNREACH` on every round, `4/4`, while
  allowed runs succeed with no reply, `3/3`, after at most one initial post-launch
  `EHOSTUNREACH`; a host firewall rule can also block `sendto`). Because network errors
  cannot prove TCC state by themselves, xmsg labels the condition *permission suspected*,
  never proven.
- `failed` warns and names the responder, UDP `5353` bind, or registration error (which
  retries automatically with bounded backoff).

Serving continues in every state; federation, `agent.sock` and `http.sock` never block on
LAN discovery.

On macOS, open **System Settings › Privacy & Security › Local Network** and enable the entry
for xmsg. When a LaunchAgent-run binary first sends multicast, macOS may prompt for Local
Network access; until you allow it, outbound LAN multicast can be dropped silently. The
detector re-probes on every `30`-second tick and on interface changes, so changing the
setting updates the reported state without restarting the daemon.

After an upgrade macOS may ask again for Local Network access; until you allow it, LAN
discovery is silently off or `permission_suspected`. macOS keys the grant to the binary's
resolved real path rather than a symlink, so retargeting a symlink into a package store
looks like a new binary (and overwriting a running binary in place has been observed to
stall launchd runs for ~`60` seconds). Run xmsg from a stable real path installed cleanly on
upgrade rather than through a store symlink.

On Linux, `permission_suspected` or `failed` usually indicates a host firewall or routing
rule blocking mDNS: allow UDP port `5353` (`224.0.0.251:5353`).


## Executor ownership is unknown

<Status id="teams.supervisor" />

The optional executor supervisor currently has a fake-backend library boundary,
not an installed runtime. In its fixtures, `unknown` means that ownership or an
external effect could not be proved. The slot stays reserved. Reconnect must
reconcile the existing execution; guessing that a saved PID is dead and starting
another child could duplicate work. Workspace cleanup also refuses to discard
modified files. See the [supervisor boundary](/reference/executor-contracts/#supervisor-and-workspace-boundary).


A supervisor socket-path refusal reports the path's byte count and the platform
capacity. macOS permits 104 bytes including the terminating NUL; long temporary
or application-support paths can exceed that. Embedders should use
`OwnerRuntimeConfig::for_user` or pass a shorter explicit `runtime_root` to
`OwnerRuntimeConfig::new`. Invalid or overly permissive runtime directories are
refused without chmod or takeover. See the [runtime socket location](/reference/executor-contracts/#runtime-socket-location).
