## Start with doctor (planned)

Run these as the user who runs the daemon:

```sh
xmsg doctor
xmsg doctor --json
```

Doctor checks setup without changing it. Each result has a status and a fix hint. A
`pass` applies only to the named check; it is not a guarantee that the whole node works.
A `warn` needs interpretation, and a `fail` means a checked requirement failed. Only a
failure makes the command exit `1`; warnings alone exit `0`. JSON includes the checks,
summary counts, the CLI's `client_version`, its `client_build_revision` (planned) and a
`not_checked` list.

For a custom installation, select the paths you want checked:

```sh
xmsg doctor \
  --http-sock /run/user/1000/xmsg/http.sock \
  --agent-sock /run/user/1000/xmsg/agent.sock \
  --register-sock /run/user/1000/xmsg/register.sock \
  --db-path /home/USER/.local/state/xmsg/xmsg.db \
  --peers-file /home/USER/.config/xmsg/peers.json
```

These are examples, not paths to copy unchanged. Doctor checks explicit paths or its
local defaults; it cannot prove that the running daemon uses the same configuration.
`--fed-cert` can supply the public federation certificate for peer-config consistency.
`--enroll-state` selects saved enrollment state for optional credential checks.

## Interpret a result

| Check or symptom | What it means | What to do next |
| --- | --- | --- |
| Runtime directory or socket fails | A selected path is missing, has the wrong type, owner or permissions. | Check the daemon user, runtime directory and socket flags. Correct the installation deliberately; doctor does not create directories or change modes. |
| Daemon health fails | The bounded request to `GET /healthz` did not give the expected health response. | Check that the daemon is running and that `--http-sock` selects its socket. Read the service logs. |
| Daemon build revision warning (planned) | The daemon and client report different known revisions, or revision metadata is unavailable. | Check the intended source pin and the selected Unix socket. Nix builds embed the revision; plain Cargo builds may report `unknown`. The crate version alone is insufficient. A warning does not fail the health check or prove the daemon needs restarting. |
| Registered process liveness warning (planned) | A registration has gone/stale process evidence, or bounded read-only diagnostics cannot establish liveness. | Inspect the named local process and registration deliberately. `live` is only process evidence; it does not prove the harness is addressable or a message can be delivered. Missing `/proc` or denied platform inspection may leave evidence unknown and produces one portability warning per run. |
| Sessions directory warning | Health reports that the sessions directory is missing. | Check the harness path if this node hosts sessions. A service-only node may not need one. |
| Database schema or additive requirements (planned) | Newer schemas fail because startup refuses them; older schemas fail with a destructive schema-3 message-state rebuild warning. Missing same-version tables, indexes or additive columns warn by operation name. | Check the selected DB path, preserve a backup and follow the normal upgrade procedure. Version equality is not backfill or integrity certification; optional enrollment schema is conditional. |
| Journal/WAL/SHM state (planned) | Doctor reports stat-only type and size. Live WAL/SHM can be expected; down or unknown daemon state with sidecars warns about an unclean or uncertain shutdown. | Keep the sidecars. The next normal SQLite start handles recovery; doctor does not open sidecars, recover or checkpoint. Presence/size does not prove journal hotness or corruption. |
| Observation sidecar warning | The expected `<database>.observe.sqlite` file is absent or its metadata needs attention. | Check the observer setup and file ownership. Doctor does not open the journal writer or initialize a sidecar. |
| Peer configuration fails | The selected configuration fails the existing `check-peers` parser or certificate consistency check. | Correct the named configuration issue, then run doctor again. Parsing does not prove peer reachability or the daemon's loaded configuration. |
| Enrollment expiry fails | Saved metadata says the enrolled certificate has expired. | Follow the enrollment renewal procedure. Doctor does not renew it. |
| Enrollment renewal warns | The certificate has reached two-thirds of its recorded lifetime. | Schedule renewal. For a 24-hour certificate this is 16 hours after issuance; a fixed seven-day threshold would be misleading. |
| Loaded leaf certificate expired (planned) | The running daemon's actually loaded leaf certificate has expired. | Renew and reload that node's identity through the normal procedure. This is a failure; a certificate file selected by the CLI is not substituted for the loaded certificate. |
| Loaded leaf expiry warning (planned) | The loaded certificate expires within the smaller of seven days or one-third of its lifetime. | Schedule renewal. This threshold also covers short-lived certificates: a 24-hour leaf warns within its final eight hours. |
| Peer mTLS diagnostic warning (planned) | A bounded daemon-side probe could not establish reachability, or the peer was addressless, unattempted or an outbound-only client. | Inspect the peer's intended configuration and connectivity. Unknown is not evidence of a bad peer, and TLS success does not establish application permissions or delivery readiness. Peer results warn at most. |
| Observed clock offset warning (planned) | The peer HTTP date differs from the local clock beyond the 120-second tolerance, accounting for uncertainty. | Compare both clocks with a trusted time source. The diagnostic cannot say which clock is wrong. Missing/bad dates, unexpected status or local clock jumps leave the offset unknown. |
| CA TLS warning | The optional CA TLS handshake did not succeed. | Check connectivity and configured trust. A successful handshake establishes TLS reachability, not enrollment application health or login readiness. |

Doctor uses only the explicit Unix read-only liveness snapshot to inspect registrations.
It never falls back to ordinary recipient listing, which can synchronize claims and deliver
queued work. An older daemon, cold runtime, unsupported source or bounded/partial response
leaves uncertain evidence unknown; a gone/stale registration warns rather than fails. Some
rows lack process evidence, and a missing row does not prove a process is gone. Doctor also
avoids enrollment-pending APIs and commands that initialize
stores. It does not send, acknowledge or consume a message, mint a token or load a private
key for a diagnostic repair. Federation probes run inside the daemon using its loaded
identity, only when doctor requests them over the Unix socket. The CLI never loads a
private key or dials a peer as a fallback. Probes may update normal connection counters
or admission caches during a handshake, but make no persistent or application-state
writes. An older or unavailable daemon leaves the result unknown.
The response deadline is bounded, but the system DNS resolver may finish an in-flight lookup after its request is cancelled.

## Primary schema views (planned)

A live daemon with an existing regular WAL and SHM permits an ordinary read-only metadata
reader. Main DB and WAL bytes remain unchanged; SQLite's reader marks can update the SHM.
Without that live view, doctor reports unknown instead of creating missing sidecars. With
the daemon down or unresponsive and sidecars present, it uses stat only and leaves SQLite
recovery to startup. With no sidecars, it opens `mode=ro&immutable=1`, then rechecks metadata
for concurrent changes. No mode is an integrity or live-backup guarantee.

Results from a different or unknown client/daemon revision are labelled `next start of THIS
binary`. They describe this binary's startup requirements for the selected DB, whose path
may differ from the running daemon's. Named requirements describe structural table/index/
column additions; no migration ledger exists to certify historical backfills. Enrollment
schema is conditional, and no migration, checkpoint, VACUUM or recovery is run by doctor.

## What remains unchecked

Doctor reports the running daemon's version and build revision when its Unix health
response supplies them; missing metadata remains unknown. It does not establish loaded
configuration, historical backfill completion, actual journal hotness, CA application health
or harness addressability. The bounded federation probe reports mTLS reachability,
leaf expiry and observed offset with uncertainty; it is not a complete peer-health or
clock-correctness guarantee.
Registered owner-process liveness does not prove a usable Codex writer lease, message
delivery or task completion. Treat these as separate investigations, not implied successes. Doctor offers no automatic database recovery or
integrity guarantee. See the [CLI reference](/reference/cli-and-mcp/#xmsg-doctor-planned)
for its options and output contract.

## Collector relay failures (planned)

The planned reverse collector reports fixed failure states: unsupported (501),
unavailable (503 or a disconnected leaf), invalid response (400 or malformed
metadata), denied (403), rate limited (429), and timeout. None proves empty or
healthy traffic. Check the configured full hub/leaf identities, the exact enabled
route and independent `observe` grant at both nodes. Do not add a leaf listener
or custody transport as a fallback. Collector changes apply on restart.

Previously validated observations may remain visible as stale, labeled `via hub`
with their original ages. Restart, denied access and changed scope hide history
until validation succeeds. Missing or inconsistent stored relay origin refuses
the history rather than treating it as direct. Downgrading to an older collector
destructively purges relay history; save any required operational evidence before
choosing that downgrade. See [relay configuration](/operations/fleet-observer/#collector-relay-source-planned).
