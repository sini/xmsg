## Dynamic credential, CA bundle & peers reloading

With federation (`--peers-file`, `--fed-cert`, `--fed-key`), `xmsg serve` loads new
certificates, CA bundles and `peers.json` without dropping active connections:

- **Periodic SHA-256 polling & `SIGHUP`:** `xmsg` checks the SHA-256 content hashes of
  `--fed-cert`, `--fed-key`, `--peers-file` and each peer's `ca` bundle. It does this every
  `--fed-reload-interval-secs` (default `30` seconds, `XMSG_FED_RELOAD_INTERVAL_SECS`), and
  immediately when it gets `SIGHUP`. Content hashes find atomic symlink swaps, such as Kubernetes
  `..data` Secret rotations, also when the symlink `mtime` does not change.
- **Atomic swap & fail-closed validation:** Before the swap, `xmsg` builds and validates the full
  new configuration: the TLS acceptor, the client credentials, the private key match, the peer
  map and the CA trust anchors. If a file is not valid or does not match, xmsg stops the reload
  and logs an error. The previous configuration continues to operate without interruption.
- **Stable node identity:** Planned: reloads must keep the running certificate-derived node
  name. A certificate deriving a different name is rejected before TLS, peers or committed
  file hashes change; the old configuration remains active. The diagnostic class is
  `identity_changed`, without certificate or identity contents. Same-name renewal remains
  supported, including a new key or CA when the derived name stays the same. For a pinned
  certificate without a SPIFFE URI, a new public key changes the derived name and needs a
  planned restart/reconfiguration rather than live renewal.
- **Per-request policy re-evaluation:** On each request, existing HTTP/1.1 keep-alive connections
  on `/fed/v2/*` check peer membership (`current_peers()`) and the source-IP CIDR policy (`from`)
  again. A long-poll that is in progress completes with the configuration it started with. The
  30–60 s wait timeout limits this. The next poll uses the new configuration.

For example, renew `spiffe://example.org/ns/agents/sa/worker` while retaining the
canonical name `worker.agents`, then use the normal reload mechanism. Replacing it
with `spiffe://example.org/ns/agents/sa/other` is refused; restoring the intended
certificate allows the next reload attempt. A deliberate node-identity change
requires stopping the old node and reviewing its peer policy and stored state
before starting the replacement.

## Systemd socket activation & `sd_notify`

Under systemd, `xmsg serve` supports `Type=notify-reload` (`ReloadSignal=SIGHUP`) and socket
activation (`src/systemd.rs`):

- **Socket activation (`LISTEN_FDS`, `LISTEN_PID`, `LISTEN_FDNAMES`):** When `LISTEN_PID` is the
  PID of `xmsg serve` and `LISTEN_FDS >= 1`, `xmsg` takes the inherited descriptors. They start at
  FD `3` (`SD_LISTEN_FDS_START`). xmsg marks each one `FD_CLOEXEC`. It matches the descriptors by
  their canonical `LISTEN_FDNAMES` slot names:
  - `fed` (`--fed-listen`)
  - `listen` (`--listen`)
  - `agent` (`--agent-sock`)
  - `register` (`--register-sock` / `--leaf-register-sock`)
  - `http` (`--http-sock`)
  When `LISTEN_FDS=1` and `LISTEN_FDNAMES` is not set, the single descriptor goes to the only
  configured TCP listener (`--fed-listen` or `--listen`). Startup fails closed on any of these: an
  unknown, duplicate or unconfigured slot; a socket that is not a listening stream socket; a bound
  address or path that does not match.
- **Readiness & reload notifications (`NOTIFY_SOCKET`):**
  - xmsg sends `READY=1` only after all configured listeners are bound (or adopted) and accept
    connections.
  - Each reload after startup starts with `RELOADING=1\nMONOTONIC_USEC=<usec>`. It ends with one of
    these:
    - `READY=1` after a successful reload;
    - `READY=1\nSTATUS=reload failed: <reason>` when the reload fails and xmsg keeps the previous
      configuration;
    - `READY=1\nSTATUS=nothing to reload` when `SIGHUP` arrives and federation is not configured.
  - xmsg sends `STOPPING=1` when `SIGTERM` or `SIGINT` starts a graceful shutdown.

## Persisted state & SQLite schema version

The SQLite database (`--db-path`) records its schema version in `PRAGMA user_version`. The
default path is `$XDG_STATE_HOME/xmsg/xmsg.db` or `~/.local/state/xmsg/xmsg.db`. The current
version is **version 3**:

- **Version 3:** xmsg opens the database in place. Queued messages, stored replies,
  `instance_claims`, idempotency keys, `peer_mailbox` and `forwarded_messages` persist across
  restarts.
- **Below version 3:** In one transaction, xmsg drops the message state tables and creates them
  again at version 3. It keeps `instance_claims`.
- **Above version 3:** xmsg refuses the database at startup and names both versions. Thus a
  downgrade never corrupts newer state. To roll back across a schema change, back up `xmsg.db`
  before you upgrade.

## Building & verification

```bash
# Run Rust test suite
cargo test --all-targets

# Run Clippy lints and rustfmt check
cargo clippy --all-targets -- -D warnings
cargo fmt -- --check

# Run shared service client checks & mutation suite
cargo test --locked --no-default-features --features client --test shared_client
python3 scripts/client-graph.py
python3 scripts/client-mutants.py

# Build Nix default package and OCI image
nix build .#default --no-link
nix build .#image --no-link
nix build -L .#checks.x86_64-linux.image --no-link

# Run full Nix CI suite (module eval, agy/codex hooks, pi/opencode/hermes plugins, shared-client-compat)
nix flake check ./ci
```
