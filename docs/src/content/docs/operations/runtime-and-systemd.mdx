## Dynamic credential, CA bundle & peers reloading

With federation (`--peers-file`, `--fed-cert`, `--fed-key`), `xmsg serve` loads new
certificates, CA bundles and `peers.json` without dropping active connections:

- **Periodic SHA-256 polling & `SIGHUP`:** `xmsg` checks the SHA-256 content hashes of
  `--fed-cert`, `--fed-key`, `--peers-file` and each peer's `ca` bundle. It does this every
  `--fed-reload-interval-secs` (default `30` seconds, `XMSG_FED_RELOAD_INTERVAL_SECS`), and
  immediately when it gets `SIGHUP`. Content hashes find atomic symlink swaps, such as Kubernetes
  `..data` Secret rotations, also when the symlink `mtime` does not change.
- **Atomic swap & fail-closed validation:** Before the swap, `xmsg` builds and validates the full
  new configuration: the TLS acceptor, the client credentials, the private key match, the peer
  map and the CA trust anchors. If a file is not valid or does not match, xmsg stops the reload
  and logs an error. The previous configuration continues to operate without interruption.
- **Stable node identity:** Planned: reloads must keep the running certificate-derived node
  name. A certificate deriving a different name is rejected before TLS, peers or committed
  file hashes change; the old configuration remains active. The diagnostic class is
  `identity_changed`, without certificate or identity contents. Same-name renewal remains
  supported, including a new key or CA when the derived name stays the same. For a pinned
  certificate without a SPIFFE URI, a new public key changes the derived name and needs a
  planned restart/reconfiguration rather than live renewal.
- **Per-request policy re-evaluation:** On each request, existing HTTP/1.1 keep-alive connections
  on `/fed/v2/*` check peer membership (`current_peers()`) and the source-IP CIDR policy (`from`)
  again. A long-poll that is in progress completes with the configuration it started with. The
  30–60 s wait timeout limits this. The next poll uses the new configuration.

For example, renew `spiffe://example.org/ns/agents/sa/worker` while retaining the
canonical name `worker.agents`, then use the normal reload mechanism. Replacing it
with `spiffe://example.org/ns/agents/sa/other` is refused; restoring the intended
certificate allows the next reload attempt. A deliberate node-identity change
requires stopping the old node and reviewing its peer policy and stored state
before starting the replacement.

## Planned: enrollment renewal task

`xmsg serve --enroll-state DIR` reads the saved identity and starts one mutual-TLS
renewal task. It renews at two thirds of the lifetime (normally 16 hours), retries
with exponential backoff capped at 15 minutes, writes `fed.crt` atomically and
calls `CredentialReloader::force_reload`. Key and URI stay the same. The periodic
watcher remains the fallback. See [the renewal example](/operations/enrollment-ca/#renewal-denial-and-another-provider).

`enroll_state_unavailable` and `enroll_renewal_failed` report deferred work without
logging tokens or keys. A different derived name remains an `identity_changed`
refusal and keeps the previous TLS configuration. Re-authentication or an expired
renewal grace needs fresh enrollment into a new private state directory.

CA policy reload uses its content hash. A bad replacement keeps the previous
policy, emits `invalid_enrollment_policy` and reports degraded reload status.
Issuance continues under the last valid policy; startup without one is refused.
Enrollment is not a systemd socket-activation slot: `--enroll-listen` is separate.

## Declared plugin harness descriptors

<Status id="xmsg.harness-descriptors" />

Pass `--harnesses-file <PATH>` (`XMSG_HARNESSES_FILE`) to `xmsg serve` to declare external v1
poll-only plugin harnesses in a strict JSON file. Pure-bus deployments omit this flag.

- **File ownership & permissions:** The descriptor file must be a regular file (at most 1 MiB)
  owned by the daemon's UID or `root` (`uid == 0`), and must not be group- or world-writable
  (`mode & 0o022 == 0`). This accepts immutable Nix store paths (`root`, mode `0444`) as well as
  owner-managed files (`0600`/`0400`).
- **Atomic reload & drain window:** Send `SIGHUP` to `xmsg serve` or run `xmsg harness reload`
  (`POST /v1/harnesses/reload` on local `http.sock`). Validation is fail-closed: invalid JSON,
  unknown fields, built-in shadowing, or unsafe `resume_argv` templates keep the previous table
  unchanged. When a declared harness is removed from the file, new registrations are refused
  immediately while existing live connections drain for `drain_window_secs` (default `600`
  seconds) before closing.
- **Immediate security revocation:** Mark a harness `"revoked": true` (or list it in top-level
  `"revoked_harnesses"`) and reload, or run `xmsg harness revoke <NAME>`
  (`POST /v1/harnesses/{name}/revoke` on local `http.sock`). Revocation closes active connections
  for that harness immediately without waiting for the drain window and rejects new connections
  with `denied`.
- **Coordinated upgrade:** Extending `observe_export::Harness` to accept validated declared harness
  names is a breaking observation-snapshot wire change. Upgrade the daemon, CLI/MCP clients, and
  `observe-collector` together before deploying declared harnesses.

## Systemd socket activation & `sd_notify`

Under systemd, `xmsg serve` supports `Type=notify-reload` (`ReloadSignal=SIGHUP`) and socket
activation (`src/systemd.rs`):

- **Socket activation (`LISTEN_FDS`, `LISTEN_PID`, `LISTEN_FDNAMES`):** When `LISTEN_PID` is the
  PID of `xmsg serve` and `LISTEN_FDS >= 1`, `xmsg` takes the inherited descriptors. They start at
  FD `3` (`SD_LISTEN_FDS_START`). xmsg marks each one `FD_CLOEXEC`. It matches the descriptors by
  their canonical `LISTEN_FDNAMES` slot names:
  - `fed` (`--fed-listen`)
  - `listen` (`--listen`)
  - `agent` (`--agent-sock`)
  - `register` (`--register-sock` / `--leaf-register-sock`)
  - `http` (`--http-sock`)
  When `LISTEN_FDS=1` and `LISTEN_FDNAMES` is not set, the single descriptor goes to the only
  configured TCP listener (`--fed-listen` or `--listen`). Startup fails closed on any of these: an
  unknown, duplicate or unconfigured slot; a socket that is not a listening stream socket; a bound
  address or path that does not match. Planned (<Status id="xmsg.install-contract" />): Unix
  socket activation requires explicit endpoint flags (`--http-sock`, `--agent-sock`,
  `--register-sock` / `--leaf-register-sock`), acquires the per-endpoint lock in the parent
  directory, and excludes validated adopted listeners from the legacy probe, bind, publication and
  cleanup so the service manager keeps owning the socket node. Set `DirectoryMode=0700` explicitly
  in socket units that create the parent directory.
- **Readiness & reload notifications (`NOTIFY_SOCKET`):**
  - xmsg sends `READY=1` only after all configured listeners are bound (or adopted) and accept
    connections.
  - Each reload after startup starts with `RELOADING=1\nMONOTONIC_USEC=<usec>`. It ends with one of
    these:
    - `READY=1` after a successful reload;
    - `READY=1\nSTATUS=reload failed: <reason>` when the reload fails and xmsg keeps the previous
      configuration;
    - `READY=1\nSTATUS=nothing to reload` when `SIGHUP` arrives and federation is not configured.
  - xmsg sends `STOPPING=1` when `SIGTERM` or `SIGINT` starts a graceful shutdown.

## Planned: installation path contract & ownership locks

<Status id="xmsg.install-contract" />

The installation contract unifies default state, config, log and socket paths across `serve`, CLI,
hooks, MCP and `doctor` through one shared resolver (breaking default change; coordinate daemon and
client re-pins together):

| Purpose | macOS default | Linux default |
| --- | --- | --- |
| Config root | `~/Library/Application Support/xmsg/config` | `${XDG_CONFIG_HOME:-$HOME/.config}/xmsg` |
| Durable state root | `~/Library/Application Support/xmsg/state` | `${XDG_STATE_HOME:-$HOME/.local/state}/xmsg` |
| Logs | `~/Library/Logs/xmsg` | `<state>/logs` |
| Managed socket namespace | `/tmp/xmsg-<uid>-<12hex>/` | `$XDG_RUNTIME_DIR/xmsg-<uid>-<12hex>/` (falls back to `/tmp/` if valid parent exceeds `sun_path`) |

- **Precedence & account home:** CLI flags win, then `XMSG_*` environment variables, then absolute
  `XDG_*` roots (a relative `XDG_*` root is refused), then platform defaults. When a component
  needs a home-derived default or expands `~/`, `getpwuid(geteuid())` supplies the authoritative
  account home; a mismatched `HOME` is refused. Components pinned by literal paths never require a
  home, and optional harness discovery (`~/.claude/sessions`, `~/.gemini/antigravity-cli/{presence,brain}`,
  `~/.codex`) is omitted rather than falling back to the working directory.
- **Private permissions & process umask:** Every xmsg writer calls `umask(0077)` at process entry.
  The daemon samples its effective kernel umask before spawning concurrent work and logs it as
  `effective_umask` on `"starting xmsg server"`. State roots and socket parents must be owned by
  the effective UID with `mode & 0o777 == 0o700` (an inherited setgid bit such as `02700` is
  allowed). Missing explicit final directories are created one level deep with exclusive `mkdir` at
  `0700`; existing directories are validated without implicit repair.
- **Pinned socket parents:** A pinned endpoint's parent needs no record in `owner.json`. `serve`
  accepts an existing parent that is a directory (not a symlink) owned by its UID with permission
  bits `0700`, or creates a missing one. A pinned client that starts first, such as `xmsg mcp`,
  creates it the same way, and so may the owner's own setup step; the operator CLI (`xmsg send`,
  `xmsg list`) only connects and creates nothing. The daemon never removes the directory, and on a
  restart it publishes its sockets into the same directory, so a bind mount of it survives the
  restart. A start with every endpoint pinned keeps no `runtime_dir` record.
- **Legacy component guard:** Before creating new state or opening the database (`serve`,
  `enroll-ca`, `enroll`), xmsg checks both `$XDG_STATE_HOME/xmsg` and `~/.local/state/xmsg` for
  legacy `xmsg.db`, enrollment identity files (`enroll.json`, `fed.crt`, `fed.key`) and
  `enroll/peers.json`, and probes legacy runtime endpoints (`$XDG_RUNTIME_DIR/xmsg/`, or
  `DARWIN_USER_TEMP_DIR/xmsg/` on macOS, plus leaf sibling `agent.sock`) read-only before binding.
  Refusals name the blocked component and compatible explicit pin without creating replacement
  state.
- **Ownership locks & atomic socket publication:** `serve` holds an exclusive non-blocking
  `<state>/serve.lock` for its lifetime, persists runtime directory and bound endpoint identities
  in `<state>/owner.json`, and serializes manual endpoint bindings across state roots with
  `<parent>/.<name>.lock` acquired in sorted order. Sockets bind to a byte-bounded temporary sibling
  first and publish atomically without replacement (`renamex_np(RENAME_EXCL)` on macOS,
  `renameat2(RENAME_NOREPLACE)` on Linux, falling back to `link()` + `unlink()` only when
  unsupported). Stale socket cleanup requires matching `(path, dev, ino, uid)` proof in
  `owner.json`; a failed connect alone never unlinks an existing node.
- **Live runtime marker recovery:** If a temporary-directory cleaner deletes only
  `<runtime>/identity.json`, the running daemon verifies its directory identity under the held
  state lock and re-stamps `identity.json` atomically on its periodic maintenance cadence
  (`reply_ttl.clamp(1, 600)` seconds) without restarting.
- **macOS Homebrew staging & verified cache:** Planned (<Status id="xmsg.macos-staging" />) —
  arm64 staging builds embed the source revision in a bounded Mach-O `__DATA,__xmsg_rev` section,
  verify independent upstream GitHub run/artifact provenance before touching Homebrew, and retain
  verified rollback bundles in `<state>/staging-cache`. See
  [macOS Staging](/getting-started/macos-staging/).

## Upgrading an existing install

<Status id="xmsg.install-contract" />

Upgrade the daemon and its CLI, MCP, hooks and service clients together. The
installation layout changes defaults; it does not migrate existing data.
Without an explicit XDG state selection, macOS now uses
`~/Library/Application Support/xmsg/state` instead of `~/.local/state/xmsg`.
Unpinned sockets move from `<runtime>/xmsg/*.sock` into
`<parent>/xmsg-<uid>-<12hex>/`. macOS uses canonical `/tmp`; Linux uses an
owner-private `XDG_RUNTIME_DIR`, or `/tmp` when unset or when a valid parent
exceeds the socket byte budget. An unsafe selected parent is refused.

Two startup refusals are especially relevant:

- `LegacyConflict`: an unpinned component would bypass an existing legacy
  database, enrollment identity or peers file. For example, an old macOS
  `~/.local/state/xmsg/xmsg.db` prevents `serve` from creating a new default DB.
- `UnsafeOwner`: a selected state or socket directory belongs to another UID.
  A shared pod volume such as `root:<group>` mode `2777` is not an owner-private
  runtime directory. A wrong permission mode has its own refusal too.

Choose one of these paths before restarting.

### Keep the legacy layout with explicit pins

Record the paths the existing service actually uses. Pin its database and every
socket enabled in its mode, and give the **same settings to the daemon and all
clients**, including service-manager configuration, MCP and hooks. For example,
for an ordinary node (replace the socket directory with the existing absolute
private directory):

```sh
export XMSG_DB_PATH="$HOME/.local/state/xmsg/xmsg.db"
export XMSG_HTTP_SOCK="/absolute/private/legacy-runtime/http.sock"
export XMSG_AGENT_SOCK="/absolute/private/legacy-runtime/agent.sock"
export XMSG_REGISTER_SOCK="/absolute/private/legacy-runtime/register.sock"
```

Equivalent daemon flags are `--db-path`, `--http-sock`, `--agent-sock` and
`--register-sock`; explicit flags win over environment variables. A leaf needs
its agent and leaf registration endpoints, not HTTP: use `XMSG_AGENT_SOCK` and
`XMSG_LEAF_REGISTER_SOCK` (`--agent-sock` and `--leaf-register-sock`).
`XMSG_REGISTER_SOCK` is a leaf-registration alias when the dedicated leaf
setting is absent; a service client using that generic setting must point it
to the same registration socket. Keep intentional `--enroll-state` and
`--peers-file` settings as well: a database pin alone does not resolve every
legacy-component conflict.

### Remove unproven dead sockets during a pinned upgrade

A daemon from before the ownership-lock contract may leave socket files at the
same explicitly pinned endpoints without the durable ownership proof the new
daemon requires. Startup then refuses `UnprovenExistingSocket`, even when the old
daemon has exited. This is a one-time migration step, not routine socket cleanup.

1. Stop the old daemon **and** its socket-activation units or other supervisors.
   Keep them stopped throughout inspection and cleanup.
2. Inspect only the exact socket paths selected by the daemon's pins. Confirm
   each is a Unix socket owned by the service UID; stop on a symlink, unexpected
   file type or ownership mismatch. Do not scan or delete a runtime directory.
3. Try a Unix-stream connection to each selected socket, for example with
   Python's `socket.socket(socket.AF_UNIX, socket.SOCK_STREAM).connect(path)`.
   A successful connection means something is still listening: stop and find it.
   Only `ECONNREFUSED` establishes a dead listener for this procedure. `ENOENT`
   means there is no file to remove; permission errors, timeouts and every other
   error require investigation, not deletion.
4. Remove only the selected socket files verified dead in step 3, while all
   writers and activation remain stopped. Keep the DB, SQLite sidecars, lock
   files and ownership records intact. Restart the upgraded daemon with the same
   pins, then check `xmsg doctor --json` and reconnect clients.

The daemon deliberately does not treat a failed connection as proof that an
unrecognized socket belongs to it. Do not repeatedly unlink sockets to bypass a
startup refusal.

### Adopt the new defaults

1. Stop the daemon and every other writer to its state, using the existing
   service manager so it cannot restart during the move. Back up the complete
   state directory, including SQLite sidecars; do not copy only a live DB or
   delete `-wal`/`-shm` files.
2. Move the stopped state directory to the new resolved state location. For a
   default macOS install, that is from `~/.local/state/xmsg` to
   `~/Library/Application Support/xmsg/state`. If the resolved state location
   is unchanged (the usual Linux default), leave it in place. Preserve ownership and private
   permissions; the destination must not already contain another install.
   Do not merge two databases. Keep enrollment state, keys and peer policy.
   Keep the standalone Claude adapter's account-wide
   `~/.local/state/xmsg/claude-coordinator` at that fixed location: it does not
   follow the daemon state root. If present inside the old tree, retain that
   directory there while moving the remaining daemon state. See
   [adapter ownership](/reference/claude-install/).
3. Review path references in the moved configuration. Enrollment-generated
   `peers.json` can contain an absolute `hub-ca.pem` path: update it and any
   service `--enroll-state`, `--peers-file` or certificate paths that moved.
   Moving files does not rewrite those references.
4. Remove the legacy DB/socket pins from the daemon **and its clients**, then
   restart using the same selected roots. Keep any intentional XDG settings;
   they still override platform defaults. Use `xmsg doctor --json` to discover
   the resolved endpoints and check the service/client agreement. Reconfigure
   direct socket consumers from that result. Never move old runtime sockets
   into the new namespace; the daemon recreates them with ownership checks.
   For the standalone Claude adapter, stop Claude and other configuration
   writers, then preview `xmsg install claude` with the intended new settings
   and use `--apply` to refresh its owned MCP/hook commands. Unsetting the
   parent environment alone does not edit their already-pinned arguments.

Tools hard-coding `<runtime>/xmsg/http.sock`, `agent.sock` or `register.sock`
must use compatible explicit pins or the resolver/discovered endpoint. Moving
state can change the namespace hash; do not guess or persist its suffix.

### Moving to a pinned socket directory

A deployment that needs the socket paths when a unit is generated (for example a sandboxed service
that bind-mounts them) pins all three endpoints in one directory. With Home Manager that is
[`programs.xmsg.server.sockets.dir`](/operations/nixos-and-home-manager/#a-stable-socket-directory).
Keep the directory apart from the legacy `<runtime>/xmsg/` path.

1. Stop the consumers of the sockets, then stop the old daemon: its `serve.lock` refuses a second
   daemon on the same state root.
2. Switch the configuration, start `xmsg`, then start the consumers.
3. Restart every agent session, so each one runs the new client with the new flags.

**Old shells.** A shell opened before the switch lacks the exported `XMSG_*_SOCK` pins. Its bare CLI
resolves the state root's managed name, where nothing answers, and it does not fall back. `xmsg
doctor` reports this as `install.endpoint_pins`: the check fails when the endpoints the daemon
recorded in `owner.json` differ from the ones the shell resolved and nothing answers at those, and
its message names each recorded endpoint as the variable to export. Export them, or log in again.
Doctor only reports; it never routes.

**Rollback.** Restore the previous configuration, then reset the runtime directory: log out of every
session, or reboot where the user lingers (with linger, `/run/user/<uid>` survives a logout). A
pinned start clears the managed `runtime_dir` record, so until the reset an earlier binary refuses
its leftover managed directory with `no durable runtime_dir proof in owner.json`, changing
nothing. After the reset it creates the directory afresh. A later upgrade needs no reset. Never
edit `owner.json` or remove runtime files by hand.

### Containers and pods

An explicit `--db-path` (or `XMSG_DB_PATH`) selects its parent as the state
root. `serve` requires that directory to belong to the running UID with permission
bits `0700`, **even when every endpoint is pinned and in leaf mode**. A shared
`emptyDir` root owned by `root:<fsGroup>` with mode `2777` fails `UnsafeOwner`;
group write access does not satisfy owner-private state requirements.

Either give xmsg a private runtime directory owned by its service UID with
permission bits `0700`, or pin **every enabled endpoint** under private manual
socket parents. Pinning only some endpoints still derives a managed namespace
and validates the runtime parent. Do not make a shared volume root private by
changing its ownership or permissions out from under other containers.

For an already configured leaf, this environment fragment pins its complete
endpoint set. Assume shared volumes are mounted at `/run/bus` and
`/var/lib/bus`; their private final child directories must be writable/creatable
by the service UID. Retain the leaf's existing peer/TLS configuration and
`--leaf` mode:

```yaml
env:
  - name: XMSG_DB_PATH
    value: /var/lib/bus/state/xmsg.db
  - name: XMSG_AGENT_SOCK
    value: /run/bus/private/agent.sock
  - name: XMSG_LEAF_REGISTER_SOCK
    value: /run/bus/private/register.sock
```

Give the adjacent service client that same agent/registration pair. For a
non-leaf node, pin `XMSG_HTTP_SOCK`, `XMSG_AGENT_SOCK` and
`XMSG_REGISTER_SOCK` instead. With every enabled endpoint pinned, no managed
namespace is created; state and manual socket parents still require the correct
UID and private permissions. Existing unsafe directories are refused rather
than repaired. For a same-UID init-container example, see
[owned pod subdirectories](/operations/helm-and-kubernetes/#owned-subdirectories-for-custom-pods).
See [the socket reference](/reference/http-and-sockets/) and
[upgrade errors](/operations/troubleshooting/#upgrade-path-refusals).

A pod pins its endpoints as above. On a host, a sandboxed system service that bind-mounts a user's
pinned socket directory must not create that directory as root, because the daemon refuses a parent
it does not own. Create it as the user (mode `0700`) before the service starts, start the service
only while the user's runtime directory exists, stop it when that directory goes away, and have the
service wait, bounded, until `agent.sock` accepts. With systemd, tie the service to
`user-runtime-dir@<uid>.service` with `WantedBy=`, `Requisite=`, `After=` and `PartOf=`, rather than
`BindsTo=` or `Requires=`, which would start the runtime directory without the user's daemon.

## NixOS system-service instances

For dedicated system-user daemons on NixOS (such as isolated worker or service tiers),
`nixosModules.xmsg` provides `services.xmsg.instances.<name>`:

```nix
{ inputs, ... }:
{
  imports = [ inputs.xmsg.nixosModules.xmsg ];

  users.groups.xmsg-worker = { };
  users.users.xmsg-worker = {
    isSystemUser = true;
    group = "xmsg-worker";
  };

  services.xmsg.instances.worker = {
    user = "xmsg-worker";
    group = "xmsg-worker";
  };
}
```

Each enabled instance runs `xmsg-<name>.service` (`Type = "notify"`) with:

- **Owner-private runtime & state directories:** `RuntimeDirectory` and `StateDirectory` are
  configured with mode `0700` owned by `user:group`, with `RuntimeDirectoryPreserve = "yes"` and
  `XMSG_DB_PATH` inside `stateDir`.
- **Pinned sockets by default:** `sockets.{http,agent,register}` default to
  `<runtimeDir>/xmsg/{http,agent,register}.sock` (`XMSG_HTTP_SOCK`, `XMSG_AGENT_SOCK`,
  `XMSG_REGISTER_SOCK`). Pinning all three endpoints under the instance's private runtime directory
  keeps clients on deterministic paths and avoids `UnprovenExistingSocket` on fresh installs and
  service restarts.
- **No TCP listener by default:** `allowTcpListen` defaults to `false`, and evaluation asserts
  against `listen`, `--listen` in `extraArgs`, and `XMSG_LISTEN` in `extraEnvironment` unless
  `allowTcpListen = true` is explicitly set.
- **System-unit hardening:** Runs with `ProtectSystem = "strict"`, `ProtectHome = true`,
  `NoNewPrivileges = true`, `ProtectProc = "invisible"`, `ProcSubset = "pid"`, and `UMask = "0077"`
  so callers sharing the instance UID can still be attested via `/proc/<pid>`.

See [NixOS & Home Manager](/operations/nixos-and-home-manager/#nixos-system-services) for the full
option reference.

## Persisted state & SQLite schema version

The SQLite database (`--db-path`) records its schema version in `PRAGMA user_version`. The current
version is **version 3**:

- **Empty version 0 (new database):** xmsg initializes schema version 3.
- **Version 3:** xmsg opens the database in place. Queued messages, stored replies,
  `instance_claims`, idempotency keys, `peer_mailbox` and `forwarded_messages` persist across
  restarts.
- **Populated version 0 or older version (`0 < v < 3`):** Planned (<Status id="xmsg.install-contract" />):
  `storage::init_db` refuses the database before any write (gating both `serve` and `enroll-ca`),
  preserving existing rows and database bytes intact until exported or migrated by a tested
  migration.
- **Above version 3:** xmsg refuses the database at startup and names both versions. Thus a
  downgrade never corrupts newer state. To roll back across a schema change, back up `xmsg.db`
  before you upgrade.
