On Linux and macOS, `xmsg` connects to the OpenAI Codex CLI (`codex`) with four mechanisms:

- writer-lock lease attestation, which proves which session is calling;
- runtime JSON-RPC `_meta` caller attribution;
- a restricted live push relay, for sessions that run on the Codex app-server daemon;
- hook-driven handoff, for embedded (`--no-daemon`) sessions.

## Attestation and admission (`--codex-exe`, `--codex-home`)

To admit Codex root sessions and their direct child subagents, give `xmsg serve` the trusted
Codex executables and home directories:

```bash
xmsg serve \
  --codex-exe /path/to/bin/codex \
  --codex-home "$HOME/.codex"
```

- **Writer-lock & rollout verification:** xmsg admits a Codex root session `P` when two
  conditions are true:
  - An ancestor process that matches `--codex-exe` holds an open file descriptor to
    `<H>/thread-writer-locks/<P>.lock`, under a configured `--codex-home` `<H>`. A continuous
    lease watch monitors it. On Linux, the watch uses `inotify`. On macOS, it uses `kqueue` on an
    `O_EVTONLY` descriptor.
  - The rollout file under `<H>/sessions` passes bounded `O_NOFOLLOW` verification
    (`session_meta.payload.id == P` and `payload.session_id == P`).
- **Runtime MCP `_meta` attribution:** `xmsg mcp` takes three values only from the JSON-RPC
  `params._meta` envelope: `codex_session` (`params._meta.sessionId`), `codex_thread`
  (`params._meta.threadId`) and `codex_turn` (`params._meta["x-codex-turn-metadata"].turn_id`).
  It never takes them from the `arguments` that the model controls. It also removes any
  `as_agent` that the model gives.
- **Direct child subagents (`<P>/<X>@<node>`):** A direct child with a verified rollout under
  `<H>/sessions` (`payload.id == X`, `payload.session_id == P`, `payload.parent_thread_id == P`)
  binds `<P>/<X>@<node>`. The `SubagentStart`, `PreModelRequest` and `SubagentStop` hooks
  (`xmsg register codex --hook --event <event>`) track the turn state. While a child turn is
  active, messages to `<P>/<X>@<node>` wait for `inbox`. Out of turn, messages go to the parent
  `P` with a `to=<P>/<X> agent_id=<X>` header.

## Delivery: live push relay and hook drain

- **Daemon-backed roots (live push relay):** A Codex root can run on the per-home app-server
  daemon (`<H>/app-server-control/app-server-control.sock`). Then `xmsg` does these steps:
  1. It connects to the control socket. It checks for a `0700` directory and a `0600` socket. It
     pins the peer `(pid, starttime)` to the admitted owner.
  2. It checks that `P` is in `thread/loaded/list`.
  3. It sends a restricted, text-only `turn/start` request.
- **Embedded (`--no-daemon`) roots (hook drain):** A session without an app-server socket gets its
  queued messages through the `SessionStart`, `UserPromptSubmit` and `Stop` hooks. The hooks use
  transactional `codex_handoff` state (`pending → inflight → accepted | unknown`). Thus xmsg hands
  off each message at most once.
- **Untrusted-peer-data preamble:** Each Codex delivery carrier adds a fixed untrusted-peer
  preamble outside the escaped message body. The preamble frames peer messages as data from a
  colleague, not as system or developer instructions.

## After a daemon restart

**Planned:** xmsg can wake a known Codex root after its own daemon restarts, without waiting for
that root to make an MCP call. This applies only to roots loaded as recovery candidates at
startup, with queued messages and no operator revocation. Ordinary `SessionEnd` or unsubscribe
parking stays parked.

Before delivery, xmsg rechecks the persisted owner's trusted executable, PID and process start
time, the writer-lock lease and rollout metadata. The live relay still verifies the app-server
socket's peer PID and start time. It does not discover or guess a replacement owner. An owner
change ends automatic recovery; the normal hook or attributed MCP resume path remains available.

A queued message triggers an attempt. If the app-server is temporarily unavailable, a bounded
background retry handles the queued work without another message or MCP call. Retries back off
from one second to at most thirty seconds. Each pass considers at most eight candidates, and
each root uses the bounded eight-envelope relay drain. A drain starts no new attempt after two
seconds; an already-started relay has its own two-second timeout, so the drain can approach
four seconds. Recovery eligibility survives another
xmsg restart, but ends after pending custody is resolved, revocation or an owner change.

Until recovery succeeds, `list --status inactive` reports `awaiting_reattestation`; the default
live list excludes that root. The message keeps its queued custody while checks fail. Unknown
roots still need registration, and an explicit revocation stays in force. See
[Codex restart custody](/concepts/replies/#replies-stored-always-pushed-by-sender-kind) for
stable message IDs, FIFO order, and accepted, pending and unknown handoffs.

## Operator revocation (`--revoke` / `--unrevoke`)

Revocation parks a Codex root session. The session then refuses automatic re-admission until you
clear the revocation:

```bash
# Revoke a Codex root session ID (sets RevokedByOperator)
xmsg register codex --revoke <session-uuid>

# Clear RevokedByOperator so the session can re-attest on resume
xmsg register codex --unrevoke <session-uuid>
```

## Labels with a shared daemon

Use one real, named worktree for each concurrent worker. When no explicit label reaches the
hook, xmsg uses the basename of the session rollout's cwd as its display label. Start each Codex
session in a separate terminal:

```sh
git -C /path/to/project worktree add -b worker-a ../worker-a HEAD
git -C /path/to/project worktree add -b worker-b ../worker-b HEAD
codex -C /path/to/worker-a
codex -C /path/to/worker-b
```

Do not use a per-client `XMSG_CODEX_LABEL` to name sessions that share a per-home daemon that
is already running. The hook sees the startup environment of the server process. It does not
see the environment of each later CLI client. The variable applies to a Codex process's own
embedded execution, or to a daemon that starts new. `xmsg register codex --label <label>` is
still an explicit hook argument. It does not make a launch variable cross that daemon boundary.

A running daemon can keep an older explicit environment label. That label hides the cwd
fallback. The owner can start the daemon again when it is idle. Workers must not restart live
services to change labels. While labels collide, use the full instance address from `list`.
Labels are descriptions. They are not authorization or identity boundaries. This worktree
workflow needs no authentication or profile changes.

This behavior was measured with Codex 0.167.0 and matches its
[server-side hook environment snapshot](https://github.com/openai/codex/blob/086ccc833bc9cf01024ad2dd6af7dbd421b6bf9a/codex-rs/hooks/src/registry.rs#L83).

## Home Manager switch

`programs.xmsg.harnesses.codex.enable = true` does these things:

- It installs `${xdg.dataHome}/xmsg/bin/xmsg`.
- It configures `programs.codex.skills.xmsg` and `programs.codex.settings.mcp_servers.xmsg`.
- It adds `--codex-exe` and `--codex-home` to `xmsg serve`.
- It exposes `programs.xmsg.harnesses.codex.hooks`:

