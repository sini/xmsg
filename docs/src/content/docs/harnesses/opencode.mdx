`opencode` loads `<config>/opencode/plugin/xmsg.ts` (`extensions/opencode/xmsg.ts`) at startup.
The plugin's default export supports `opencode` 1.x (`server` hook) and `opencode` 2.x (`setup`
hook in `opencode service`).

## Multiplexed `register.sock` connection

An `opencode` process (or `opencode service` in 2.x) holds many sessions in one process. Thus
process-ancestry attribution cannot tell one session from another. The plugin works as follows:

- On 1.x, the plugin opens one `register.sock` connection for each `opencode` process.
- On 2.x, `opencode service` sets up the plugin once for each project directory. It holds one
  `register.sock` connection for each served directory.
- `opencode` has no MCP entry. The plugin's native tools (`xmsg_list`, `xmsg_send`, `xmsg_reply`,
  `xmsg_replies`, `xmsg_inbox`) send multiplexed frames on `register.sock`. Each frame names the
  calling `ToolContext.sessionID`. Thus xmsg gives each call that session's address, and no other.

## Finding the daemon

<Status id="harness.plugin-endpoints" />

The plugin looks for the daemon's sockets in this order:

1. **Environment pins:** `XMSG_REGISTER_SOCK` and `XMSG_AGENT_SOCK` name a socket directly.
2. **`xmsg doctor --json`:** without a pin, the plugin runs `xmsg doctor --json` from `PATH`
   once and uses the endpoints it reports (`register_socket`, else `leaf_register_socket`;
   `agent_socket`). These are the daemon's default sockets, in its managed
   `xmsg-<uid>-<12hex>/` directory. The answer is cached; the plugin asks again only after a
   connection to the daemon drops, at its next reconnect.
3. **Legacy directory:** when `xmsg` is not on `PATH`, or is too old to have `doctor`, the plugin
   logs one line and uses `$XDG_RUNTIME_DIR/xmsg/` (on macOS without `XDG_RUNTIME_DIR`, the Darwin
   user temporary directory).

If `doctor` answers but reports the endpoints unusable (`endpoints_usable: false`), prints
malformed output, or takes longer than 3 seconds, the plugin refuses to connect and logs why. It
never falls back to the legacy directory in that case. Run `xmsg doctor` to see the failing check,
or pin the sockets with the environment variables above in the harness's environment.

## Session lifecycle

- **Registration on first prompt:** A session registers at its first user prompt (1.x
  `chat.message`, 2.x session `prompt` hook). This occurs before xmsg answers the turn's first
  tool call. A stored, inactive session on disk does not register until you use it.
- **Push delivery:** xmsg puts an incoming message into its target session as a user prompt (1.x
  `promptAsync`, 2.x `session.prompt`). If the session is idle, this starts a turn. The plugin
  sends `ack` to `xmsg` only after `opencode` accepts the prompt.
- **Child sessions (`<P>/<child_ses>@<node>`):** A `task` or `subagent` child session with a
  `parentID` follows `parentID` to its root conversation `P`. It binds `<P>/<child_ses>@<node>`
  with `subagent` (`start`/`stop`/`end`) on `register.sock`. It passes `as_agent: <child_ses>` on
  `xmsg_send`, `xmsg_reply` and `xmsg_inbox`. While a child turn is active, messages to
  `<P>/<child_ses>` wait for `xmsg_inbox`. Otherwise they go to `P` with a
  `to=<P>/<child_ses> agent_id=<child_ses>` header.
- **Release and reclaim:** When you delete a session, xmsg releases its address (`410 gone`). The
  session stays registered when you switch sessions in the TUI. On 2.x, it also stays registered
  when you quit the TUI while `opencode service` continues to run. If `opencode service` stops or
  loads the plugin again, the connection closes and its addresses detach. Then each session gets
  its address back at its next prompt, within the reply TTL.

## Home Manager switch

In Home Manager, set `programs.xmsg.harnesses.opencode.enable = true`. This installs
`$XDG_CONFIG_HOME/opencode/plugin/xmsg.ts` and `opencode/skills/xmsg/SKILL.md`. See
[NixOS & Home Manager](/operations/nixos-and-home-manager/#per-harness-switches).

## Session locator

The [session locator](/reference/cli-and-mcp/#locating-a-session) captures the
harness-native ID at registration. Resume remains **unproven**: no resume
command is offered. An adapter may report a typed terminal hint from its own
environment; an omitted hint means unknown. Terminal references require local
detail opt-in and are never published to peers.

## Session context tags

<Status id="session-context.tags" />

A context reporter using the session's existing registration can supply optional tags such as a
branch, worktree handle, or task ID. The node publishes submitted tags by default
to authorized readers, subject to its [context controls](/reference/cli-and-mcp/#session-context-tags).

A reporter uses its registered plugin connection and selects a session key held by that connection.
See the [socket frames](/reference/http-and-sockets/#session-context-tags).


## Built-in vs. declared plugin harnesses

<Status id="xmsg.harness-descriptors" />

`opencode` is a compiled-in plugin harness with push delivery, reclaim, and child-session support.
It cannot be shadowed by a descriptor in `--harnesses-file`. To add an external poll-only plugin
harness without changing `xmsg`, declare it via
[`--harnesses-file`](/concepts/sessions-services-subagents/#declared-plugin-harnesses).


## Activity export hook

<Status id="fleet-observer.activity-export" />

Set `XMSG_ACTIVITY=1` to enable the in-process activity handler in
`extensions/opencode/xmsg.ts` (stamping per-session `native_seq`; delivery
handlers remain untouched). Supports `session.status`, `session.idle`,
`session.execution.*`, `permission.asked`/`replied`, and `question.asked`/`replied`.
