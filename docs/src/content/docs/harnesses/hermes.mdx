Hermes loads the `xmsg` plugin (`extensions/hermes/plugin.yaml` and
`extensions/hermes/__init__.py`) from `$HERMES_HOME/plugins/` when `plugins.enabled` includes
`"xmsg"`. As for `opencode`, the Hermes plugin holds one multiplexed `register.sock` connection
for each Hermes process.

## Registration and tools

- **Registration:** A session registers at the first `pre_llm_call` hook or `xmsg` tool call
  that carries its `session_id`.
- **Delegates (`delegate_task`):** The `pre_llm_call` of a `delegate_task` subagent names its
  parent. The subagent acts as its root conversation `P`. It does not bind a separate
  sub-address.
- **Tools (`xmsg` toolset):** The plugin gives `xmsg_list`, `xmsg_send`, `xmsg_reply` and
  `xmsg_replies`. It sends them as frames on `register.sock` under the calling `session_id`. By
  default, Hermes puts plugin tools behind its Tool Search bridge (`tools.tool_search`). Thus
  models find and call them through `tool_search` and `tool_call`.

## Finding the daemon

<Status id="harness.plugin-endpoints" />

The plugin looks for the daemon's sockets in this order:

1. **Environment pins:** `XMSG_REGISTER_SOCK` and `XMSG_AGENT_SOCK` name a socket directly.
2. **`xmsg doctor --json`:** without a pin, the plugin runs `xmsg doctor --json` from `PATH`
   once and uses the endpoints it reports (`register_socket`, else `leaf_register_socket`;
   `agent_socket`). These are the daemon's default sockets, in its managed
   `xmsg-<uid>-<12hex>/` directory. The answer is cached; the plugin asks again only after a
   connection to the daemon drops, at its next reconnect.
3. **Legacy directory:** when `xmsg` is not on `PATH`, or is too old to have `doctor`, the plugin
   logs one line and uses `$XDG_RUNTIME_DIR/xmsg/` (on macOS without `XDG_RUNTIME_DIR`, the Darwin
   user temporary directory).

If `doctor` answers but reports the endpoints unusable (`endpoints_usable: false`), prints
malformed output, or takes longer than 3 seconds, the plugin refuses to connect and logs why. It
never falls back to the legacy directory in that case. Run `xmsg doctor` to see the failing check,
or pin the sockets with the environment variables above in the harness's environment.

A harness started by a service manager (a systemd unit, a launchd agent, a container entrypoint)
sees only that service's environment. If `xmsg` is not on the service's `PATH`, the plugin skips
the doctor step and falls back to the legacy directory, which an unpinned daemon no longer uses.
Put `xmsg` on the service's `PATH`, or set `XMSG_REGISTER_SOCK` and `XMSG_AGENT_SOCK` in
its environment.

## Session lifecycle and compaction

- **Ending a session (`on_session_finalize`):** These actions release the session's address
  (`410 gone`): you close a desktop session, run `/new`, or exit the CLI. A late tool call from an
  ended session's background delegate returns `gone`. It does not register the old session again.
- **Switching sessions in the CLI:** `/new` ends the old session and registers the new one
  (`on_session_reset`). `/resume` and `/branch` start no plugin hook. For them, the plugin sees
  the changed `session_id` on the next hook, tool call or push. It then releases the old address.
  Thus xmsg never puts one session's message into another session.
- **Compression (`continues`):** Hermes's default in-place compaction keeps `session_id` and its
  `xmsg` address. With `compression.in_place: false`, compression makes a new `session_id`. The
  plugin then reads `SessionDB(read_only=True).get_compression_chain`. It sends a `continues`
  frame on `register.sock`, which moves the `xmsg` address to the new session ID.

## Push delivery and busy modes

- **Classic CLI:** While a turn runs, a delivered message goes through the CLI's busy-input
  handler. `display.busy_input_mode` (or `/busy`) sets the mode:
  - `queue` runs the message as the next turn.
  - `interrupt` redirects the running turn.
  - `steer` puts the message in after the current tool call.

  When the session is idle, the message starts a new turn.
- **TUI and desktop host:** Hermes's `inject_message` queues incoming messages on the session in
  all busy modes. Thus a notification never cancels work in progress. This needs
  `plugins.entries.xmsg.allow_gateway_injection: true` in the Hermes settings.
- **Acknowledgments:** The plugin sends `ack` only after Hermes accepts the message.

## Home Manager switch

Set `programs.xmsg.harnesses.hermes.enable = true`. This needs `services.hermes-agent`. The
switch links the plugin into `services.hermes-agent.extraPlugins`, adds `"xmsg"` to
`settings.plugins.enabled`, enables `allow_gateway_injection` and installs the `xmsg` skill. See
[NixOS & Home Manager](/operations/nixos-and-home-manager/#per-harness-switches).

## Session locator

The [session locator](/reference/cli-and-mcp/#locating-a-session) captures the
harness-native ID at registration. Resume remains **unproven**: no resume
command is offered. An adapter may report a typed terminal hint from its own
environment; an omitted hint means unknown. Terminal references require local
detail opt-in and are never published to peers.

## Session context tags

<Status id="session-context.tags" />

A context reporter using the session's existing registration can supply optional tags such as a
branch, worktree handle, or task ID. The node publishes submitted tags by default
to authorized readers, subject to its [context controls](/reference/cli-and-mcp/#session-context-tags).

A reporter uses its registered plugin connection and selects a session key held by that connection.
See the [socket frames](/reference/http-and-sockets/#session-context-tags).


## Built-in vs. declared plugin harnesses

<Status id="xmsg.harness-descriptors" />

`hermes` is a compiled-in plugin harness with push delivery and compression-chain `continues`
support. It cannot be shadowed by a descriptor in `--harnesses-file`. To add an external poll-only
plugin harness without changing `xmsg`, declare it via
[`--harnesses-file`](/concepts/sessions-services-subagents/#declared-plugin-harnesses).


## Activity export hook

<Status id="fleet-observer.activity-export" />

Set `XMSG_ACTIVITY=1` to enable the in-process activity handler in
`extensions/hermes/__init__.py` (stamping per-session `native_seq`; delivery
handlers remain untouched). `post_llm_call` stays `working` unless proven
turn-final; `on_human_input_request` (`clarify` vs `approval`/`sudo`) resolves
via `pre_llm_call` or `post_approval_response`.
