`xmsg` ships a TypeScript extension (`extensions/pi/index.ts`) for the Pi coding agent
(`@earendil-works/pi-coding-agent`).

## How the Pi extension works

- **Registration & long-poll:** At startup, the extension connects to the daemon's
  `register.sock` (see [Finding the daemon](#finding-the-daemon)). `xmsg serve` checks the peer UID (`SO_PEERCRED` /
  `getpeereid`). It records the process start time and makes a new UUID v4 for the session. The
  session's display label is its Pi session name. If it has no name, the label is the basename of
  its working directory.
- **Safe prompt injection:** Incoming messages arrive over the `register.sock` long-poll loop
  (`poll` $\rightarrow$ `ack`). xmsg delivers them into Pi with `expandPromptTemplates: false`.
  This prevents remote command expansion and prompt-template expansion.
- **Tools (`list`, `send`, `reply`, `replies`):**
  - `list`: Asks for active recipients over `http.sock`, or over `XMSG_URL` when you set it.
  - `send`: Sends messages over `agent.sock`, with kernel PID attestation.
  - `reply`: Sends replies over `agent.sock`.
  - `replies`: Reads the stored replies to a sent message over `agent.sock`. It waits up to `wait`
    seconds (at most 60) for the first reply.
- **Lifecycle:** A Pi session's UUID is bound to its process. Thus when Pi exits, xmsg releases
  the session. Later sends to its UUID return `410 gone`. A Pi session is never `parked`. Pi is a
  single-session process. It does not use subagent sub-addresses or `inbox`.

## Finding the daemon

<Status id="harness.plugin-endpoints" />

The extension looks for the daemon's sockets in this order:

1. **Explicit paths:** the `sockPath`, `agentSockPath` and `httpSockPath` options of `XmsgPiBridge`,
   for code that embeds the extension.
2. **Environment pins:** `XMSG_REGISTER_SOCK`, `XMSG_AGENT_SOCK` and `XMSG_HTTP_SOCK` name a
   socket directly.
3. **`xmsg doctor --json`:** without a pin, the extension runs `xmsg doctor --json` from `PATH`
   once and uses the endpoints it reports (`register_socket`, else `leaf_register_socket`;
   `agent_socket`; `http_socket`). These are the daemon's default sockets, in its managed
   `xmsg-<uid>-<12hex>/` directory. The answer is cached; the extension asks again only after a
   connection to the daemon drops, at its next reconnect.
4. **Legacy directory:** when `xmsg` is not on `PATH`, or is too old to have `doctor`, the extension
   logs one line and uses `$XDG_RUNTIME_DIR/xmsg/` (on macOS without `XDG_RUNTIME_DIR`, the Darwin
   user temporary directory).

If `doctor` answers but reports the endpoints unusable (`endpoints_usable: false`), prints
malformed output, or takes longer than 3 seconds, the extension refuses to connect and logs why. It
never falls back to the legacy directory in that case. Run `xmsg doctor` to see the failing check,
or pin the sockets with the environment variables above in the harness's environment.

A harness started by a service manager (a systemd unit, a launchd agent, a container entrypoint)
sees only that service's environment. If `xmsg` is not on the service's `PATH`, the extension skips
the doctor step and falls back to the legacy directory, which an unpinned daemon no longer uses.
Put `xmsg` on the service's `PATH`, or set `XMSG_REGISTER_SOCK`, `XMSG_AGENT_SOCK` and
`XMSG_HTTP_SOCK` in its environment.

## Home Manager switch

In Home Manager, set `programs.xmsg.harnesses.pi.enable = true`. This installs
`~/.pi/agent/extensions/xmsg-pi.ts` and `~/.pi/agent/skills/xmsg/SKILL.md`. Pi automatically
loads all extensions under `~/.pi/agent/extensions/`. See
[NixOS & Home Manager](/operations/nixos-and-home-manager/#per-harness-switches).

With [`programs.xmsg.server.sockets.dir`](/operations/nixos-and-home-manager/#a-stable-socket-directory)
set, the installed extension begins by setting `XMSG_REGISTER_SOCK`, `XMSG_AGENT_SOCK` and
`XMSG_HTTP_SOCK` to the directory's sockets, unless pi's environment already sets them. So pi finds
the daemon however it was started, not only from a login shell.

## Session locator

The [session locator](/reference/cli-and-mcp/#locating-a-session) captures the
harness-native ID at registration. Resume remains **unproven**: no resume
command is offered. An adapter may report a typed terminal hint from its own
environment; an omitted hint means unknown. Terminal references require local
detail opt-in and are never published to peers.

## Session context tags

<Status id="session-context.tags" />

A context reporter using the session's existing registration can supply optional tags such as a
branch, worktree handle, or task ID. The node publishes submitted tags by default
to authorized readers, subject to its [context controls](/reference/cli-and-mcp/#session-context-tags).

A reporter sends the context actions on its registered `register.sock` connection.
See the [socket frames](/reference/http-and-sockets/#session-context-tags).

## Activity export hook

<Status id="fleet-observer.activity-export" />

Set `XMSG_ACTIVITY=1` to enable the in-process activity handler in
`extensions/pi/index.ts` (stamping per-session `native_seq`; delivery handlers
remain untouched). Maps `agent_start`/`turn_start` -> `working`,
`ui_prompt_start`/`end` -> `blocked(input)`/`working`, `agent_settled` ->
`idle` (`agent_end` is not treated as idle).
