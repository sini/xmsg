`xmsg` sends messages to three kinds of recipient:

- **Instances** are interactive AI agent sessions. See [instance](/glossary/#instance).
- **Services** are headless daemons and bridges. See [service](/glossary/#service).
- **Subagents** are child turns that a parent conversation starts. See
  [subagent](/glossary/#subagent).

## Instances and fork claims (`X~n`)

An instance is a live or [parked](/glossary/#parked) conversation in an agent
[harness](/glossary/#harness):

- **Persistent conversation IDs (`claude`, `agy`, `codex`):** The instance ID is the harness's own
  conversation UUID. A conversation can close, or pause between turns. Then its ID stays `parked`
  in SQLite for the [reply TTL](/glossary/#reply-ttl) (`--reply-ttl`, 7 days by default).
  Incoming messages wait for its next turn.
- **Process-bound session IDs (`pi`, `opencode`, `hermes`):** `xmsg` makes a new UUID v4 at
  registration. When a Pi process exits, its address becomes [`gone`](/glossary/#gone) (`410`).
  The same occurs when an `opencode` or `hermes` session is deleted or finalized.

### Concurrent processes and fork suffixes (`instance_claims`)

Two or more live processes can show the same Claude conversation ID `X`. They can be in the
same `~/.claude/sessions` directory, or in different `--sessions-dir` tenant directories. `xmsg`
records them in the persistent SQLite `instance_claims` table:

- The first live process that xmsg sees with `X` claims plain `X` (suffix 1).
- Each later live process with `X` gets the next [fork suffix](/glossary/#fork-suffix): `X~2`,
  `X~3`, …, in the order xmsg sees them. Within one scan, `(procStart, pid)` breaks a tie.
- Suffixes persist across `xmsg serve` restarts. xmsg never promotes a suffix while it is live.
- When a node sees a second live process for an ID that is already live, it sends one fork notice
  to each process. The notice gives both addresses (`X@node` and `X~2@node`).
- When an `X~n` fork process exits, xmsg releases its claim. Then sends to `X~n` return
  `410 gone`. When xmsg releases plain `X`, the next process with `X` claims plain `X`. xmsg never
  uses a numeric suffix `~2`, `~3`, … again while its records exist.

## Services (`<name>@<node>`)

Headless daemons, bots, guards and bridges register bare service names over `register.sock`.
Examples are `genie-guard`, `matrix-xmsg` and `xmsg-gateway`:

```rust file=<rootDir>/src/client/mod.rs#L63-L105
```

- **Executable attestation (`--svc-exe`):** On normal host nodes, `xmsg serve` needs
  `--svc-exe <NAME>=<PATH>` (or `XMSG_SVC_EXE`). A process connects to `register.sock` and sends
  `{"harness":"svc","name":"<NAME>"}`. Then `xmsg` makes two checks:
  - The peer UID is the server UID (`peer_uid == server_uid`).
  - The canonical executable path is `<PATH>`. On Linux, xmsg reads `/proc/<pid>/exe`. On macOS,
    it uses `proc_pidpath`.

  Only one live process can hold a service name at a time.
- **At-least-once long-poll and `ack`:** A service pulls messages with
  `{"action":"poll","waitSecs":30}` on `register.sock`. It stores each delivery in its own durable
  store. Then it acknowledges the delivery with `{"action":"ack","messageId":"..."}`
  ([ack](/glossary/#ack)). An unacknowledged message stays `queued`, in the connection's
  `in_flight` set. If the service disconnects before the `ack`, xmsg delivers the message again,
  in FIFO order.
- **Structured `origin` attestation:** Each delivered frame includes an attested
  [`origin`](/glossary/#origin) struct (`id`, `service`, `node`, `label`). Thus a service makes
  authorization decisions from structured fields. It does not parse display headers:

```rust file=<rootDir>/src/client/origin.rs#L3-L16
```

See [Daemon Protocol & Rust Client](/reference/service-client/) for the wire frames and the
`xmsg::client` library.

## Delegated subagents (`<P>/<child>@<node>`)

A parent conversation `P` can start child subagents. Each bound child gets a delegated
sub-address `<P>/<child>@<node>`. `<child>` is the subagent's bound name, or its harness
`agent_id` or child session ID. Both `<P>/<name>` and `<P>/<agent_id>` resolve to the same bound
subagent. `list` shows live bound subagents with `kind: "subagent"`.

### Turn mailbox (`inbox`) and parent fallback

- **Active turn (`inbox`):** A subagent's turn is active while `turn_pid` is live with the
  matching start time. During the turn, messages and replies to `<P>/<child>@<node>` wait in its
  [turn mailbox](/glossary/#turn-mailbox) (`outcome: "queued"`). The subagent reads them during
  its turn with **`inbox(wait?)`**. The call returns
  `{address, messages: [{id, from, body, created_at}]}` and marks each message `delivered`.
- **Parent fallback (`to=<P>/<child> agent_id=<id>`):** The subagent's turn is not active between
  turns, or after `SubagentStop` or `Stop`. Then messages and replies to `<P>/<child>@<node>` go
  to the parent session `P`. xmsg adds a `to=<P>/<child> agent_id=<agent_id>` header before the
  message body. If `P` is parked now, the message stays queued on `<P>/<agent_id>`. Then one of two
  things occurs first:
  - the subagent reads it with its next `inbox` call;
  - xmsg delivers it to `P`, with the fallback header, when `P` returns.

### Per-harness subagent support

| Harness | Sub-address Form | Attribution & Lifecycle |
|---|---|---|
| [Claude Code](/harnesses/claude-code/) | `<P>/<name>@<node>` and `<P>/<agent_id>@<node>` | `xmsg register claude --hook` on `SubagentStart`, `PostToolUse` (`Agent`/`SendMessage`), `SubagentStop`, and `PreToolUse` (stamping `as_agent`). |
| [Codex](/harnesses/codex/) | `<P>/<X>@<node>` (direct children where `parent_thread_id == P`) | Attributed from runtime `params._meta` (`sessionId`, `threadId`); turn state tracked by `SubagentStart`, `PreModelRequest`, and `SubagentStop` hooks. |
| [Antigravity](/harnesses/antigravity/) | `<P>/<child_uuid>@<node>` | Admitted from `P`'s `transcript.jsonl` (`invoke_subagent`) and tracked by `xmsg register agy --hook` (`pre-invocation`, `pre-tool-use`, `stop`). |
| [opencode](/harnesses/opencode/) (1.x & 2.x) | `<P>/<child_ses>@<node>` | Child sessions walk `parentID` to root `P`, bind via `subagent` (`start`/`stop`/`end`) on `register.sock`, and pass `as_agent` on `xmsg_send`, `xmsg_reply`, and `xmsg_inbox`. |
| [Hermes](/harnesses/hermes/) | Root `<P>@<node>` | `delegate_task` subagents act as their root conversation `P` and do not bind separate sub-addresses. |
| [Pi](/harnesses/pi/) | None | Single-session process; no subagent sub-addresses. |

## Watch the recipient roster (planned)

Run `xmsg watch` from your local owner terminal to follow live and inactive recipients and
node reachability. The view groups identities by node, kind and harness, using the website
demo's participant vocabulary without inventing its message-flow animation. Refresh age and
partial/stale states distinguish an old snapshot from a currently reachable session.

Watch uses existing read endpoints over `http.sock`; it records no bodies and reads no harness
transcripts. `xmsg watch --once --plain` gives one bounded snapshot for a pipe. See the
[CLI reference](/reference/cli-and-mcp/#xmsg-watch-planned) for refresh, socket and limit details.
