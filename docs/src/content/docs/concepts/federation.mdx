[Federation](/glossary/#federation) connects xmsg nodes on different hosts, virtual machines
and Kubernetes pods. The nodes use mutual TLS ([mTLS](/glossary/#mtls)) on the `/fed/v2` wire
protocol. Each node lists the nodes it trusts, its [peers](/glossary/#peer), in a
[peers file](/glossary/#peers-file).

## Self-authenticating node names

xmsg makes a node's name from its cryptographic identity or its OS identity. You cannot set the
name with a free-form flag. xmsg refuses `--host-label` and `XMSG_HOST_LABEL` at startup:

1. **CA-signed identity (`--fed-cert` with URI SAN):** The name comes from the single
   [SPIFFE](/glossary/#spiffe-id) URI Subject Alternative Name (SAN) on the node's leaf
   certificate:
   - `spiffe://<trust-domain>/host/<host>/user/<user>` $\rightarrow$ `<user>.<host>` (for example,
     `alice.workstation`).
   - `spiffe://<trust-domain>/ns/<ns>/sa/<sa>` $\rightarrow$ `<sa>.<ns>` (for example,
     `genie-guard.genie`).
   - xmsg refuses a dot (`.`) in `<user>`, `<host>`, `<ns>` or `<sa>`.
2. **Pinned key (`--fed-cert` without URI SAN):** The name comes from the public key. xmsg takes
   the SHA-256 digest of the key's `SubjectPublicKeyInfo` DER. It encodes the digest in lowercase
   RFC 4648 base32. The name is the first 16 characters (for example, `k5x3q7mzv2ndp4ha`).
3. **No federation identity (local-only):** When `--fed-cert` is not set, the node name is
   `<user>.<host>`. `<user>` is the OS username of the effective UID. `<host>` is the short
   hostname, cut at the first `.`. This name never goes on the wire.

### Canonical names and local nicknames

Envelopes on `/fed/v2` carry canonical node names. The receiving node gives each incoming
message the canonical name of the peer entry that authenticated the TLS connection. The exception
is a message that an
[authorized forwarding hub relays](/concepts/hubs-and-leaves/#forwarding-through-a-hub).

When you type `@node` locally, you can use the peer's canonical name. For a pinned peer, you can
also use your local nickname, which is the key in your `peers.json`. An exact canonical name or
nickname has priority over a bare-host selector such as `workstation`:

- `list(node="workstation")` asks all matching nodes in the current view.
- `send(to="guard@workstation", text="...")` selects one match. Two or more matches return
  `ambiguous`. With no match, the explicit destination goes to the default route, if there is
  one. Otherwise it is unknown.

To select one user on a shared host, use a canonical name. See
[node selectors](/concepts/addressing/#node-selectors).

## Trust models: pinned vs. CA-signed

Each entry in `peers.json` uses **exactly one** trust mechanism:

- **Pinned certificates (`pin`):** xmsg authenticates the peer when its SHA-256 SPKI certificate
  fingerprint (`sha256:...`) is the [pin](/glossary/#pin). Use it for direct 1:1 peerings,
  laptops and edge nodes without a PKI.
- **CA-signed certificates (`ca` + `identities`):** xmsg checks the peer's X.509 certificate
  chain against a PEM trust anchor bundle (`ca`). The leaf certificate's **single URI SAN** must
  be the entry's single concrete URI (`identities`). xmsg never uses the Common Name (CN) or DNS
  SANs for identity. Use it for SPIFFE/SPIRE, `cert-manager`, `step-ca` or a fleet CA, where
  certificates rotate automatically. See [CA entry](/glossary/#ca-entry).

```json
{
  "peers": {
    "laptop": {
      "address": "192.168.1.50:7788",
      "pin": "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
      "allow": ["send", "reply", "list"],
      "from": ["192.168.1.0/24", "fd00::/8"]
    },
    "worker.prod": {
      "address": "10.0.0.12:7788",
      "ca": "/etc/xmsg/spire-bundle.pem",
      "identities": [
        "spiffe://example.org/ns/prod/sa/worker"
      ],
      "allow": ["send", "reply"]
    }
  }
}
```

### Naming and non-overlap invariants (`xmsg check-peers`)

`xmsg serve` and the standalone validator
`xmsg check-peers <peers.json> [--fed-cert <cert.pem>]` both apply these rules:

- A CA peer entry's key must be the node name that its `identities` URI gives (`worker.prod`
  above).
- A pinned peer entry's key is its 16-character key-derived name or a local nickname. A nickname
  must not contain `.`. It must not be 16 characters of `[a-z2-7]`.
- All entry keys, derived names and this node's own name share one namespace. There must be no
  collisions and no duplicate JSON keys.
- At handshake time, a certificate must match **exactly one** peer entry. Overlapping CA entries
  fail closed. A certificate that matches both a pinned entry and a CA entry also fails closed.

## Peer configuration reference (`--peers-file`)

### File format

The peers file is a JSON object. This site uses the wrapped form in its examples:

```json
{
  "peers": { "<entry key>": { ... } },
  "hub": { "patterns": [ ... ], "rules": [ ... ] }
}
```

- `peers` holds one entry for each peer. The entry key is the peer's node name or a local nickname.
- `hub` is optional. It is permitted only in the wrapped form. See [hub admission](#hub-admission-hub).
- Any other top-level field is refused.

xmsg also accepts two other forms. A bare map has the entries at the top level, with no `peers`
wrapper. The Home Manager module writes this form. A JSON array of entries is also accepted; each
entry then needs a `name` field. Neither form can hold a `hub` block.

### A leaf entry

A hub does not dial a leaf. The leaf connects to the hub and collects its messages. Thus a
`leaf: true` entry does not need an `address`:

```json
{
  "peers": {
    "guard.genie": {
      "ca": "/etc/xmsg/ca.pem",
      "identities": ["spiffe://example.org/ns/genie/sa/guard"],
      "leaf": true,
      "allow": ["send", "reply"]
    }
  }
}
```

A sender on the hub can send to `<target>@guard.genie`. A peer can also ask the hub to forward a
message there. In both cases the hub stores the message in its `peer_mailbox`, and the send
returns `outcome: "queued"`, not `"delivered"`. The message stays queued until the leaf collects
it and acknowledges it.

### Entry fields

| Field | Type | Description |
|---|---|---|
| `address` | `string` | The peer's `host:port` endpoint. Required, except on a `leaf: true` entry (the hub never dials it) or when another entry sets `default_route`. |
| `pin` | `string` (optional) | Expected SHA-256 certificate fingerprint (`sha256:...`). Mutually exclusive with `ca`. |
| `ca` | `string` (optional) | Path to PEM trust anchor bundle. Mutually exclusive with `pin`; requires `identities`. |
| `identities` | `list[string]` (optional) | Single concrete SPIFFE URI SAN (`["spiffe://..."]`). Required with `ca`. |
| `allow` | `list[string]` | Permitted capabilities (`"send"`, `"reply"`, `"list"`, `"inbox"`, `"forward"`, `"relayed"`). |
| `from` | `list[string]` (optional) | Permitted source IP addresses or CIDR blocks for inbound connections. Empty `[]` is refused. |
| `leaf` | `bool` (optional) | When `true`, this node does not dial the peer. Messages and `list` queries for the peer wait in this node's durable `peer_mailbox` until the peer collects them by long-polling. A send to the peer returns `outcome: "queued"`. Default `false`. |
| `dial` | `"outbound"` (optional) | Starts a background pull loop on this node. The loop connects to `address`. It pulls messages, answers `list` queries and polls replies. Not permitted with `leaf: true`. |
| `principals` | `list[string]` (optional) | Inbound sender filter: service name, instance ID or `anon:<from>`. **Absent or `[]` permits every principal.** A list with entries permits only those senders. |
| `targets` | `list[string]` (optional) | Local recipient filter for messages and `list`: service name or instance ID, never an instance label. **Absent permits all; `[]` permits none.** |
| `default_route` | `bool` (optional) | Use this peer for an explicit `ref@node` destination that is not a direct peer. At most one entry may set it to `true`; direct routes take precedence. See [hub forwarding](/concepts/hubs-and-leaves/#forwarding-through-a-hub). |

### Mailbox retention

A message in the `peer_mailbox` stays until the leaf acknowledges it, or until it is older than
the reply TTL. The reply TTL is `--reply-ttl` (environment `XMSG_REPLY_TTL`). Its default is
604800 seconds (7 days). xmsg deletes expired rows when it completes a local delivery. Thus an idle
hub can keep expired rows for longer. There is no limit on the number of messages or bytes for
each peer.

### Hub admission (`hub`)

A hub can admit clients that have no entry of their own. The `hub` block matches the client's
certificate identity against patterns:

```json
{
  "peers": {
    "xmsg.ca-host": {
      "address": "ca-host.example.org:7788",
      "ca": "/etc/xmsg/fleet-ca.pem",
      "identities": ["spiffe://example.org/host/ca-host/user/xmsg"],
      "allow": ["send", "reply"]
    }
  },
  "hub": {
    "patterns": ["spiffe://example.org/host/*/user/*"],
    "rules": [
      { "pattern": "spiffe://example.org/host/*/user/alice", "allow": ["send", "reply", "list"] }
    ]
  }
}
```

- **`patterns`** (required, not empty): SPIFFE URI patterns. A `*` matches exactly one whole path
  segment. xmsg admits a client when its certificate has exactly one URI SAN, the URI matches a
  pattern, and the chain verifies against the CA bundles of this file's `ca` entries.
- **A CA entry is required.** xmsg refuses a `hub` block when `peers` has no `ca` entry.
- **`rules`** (optional): each rule has a `pattern` and an `allow` list. The first rule whose
  pattern matches the client's URI gives the client its operations. `allow` takes `send`, `reply`,
  `list` and `forward`. It must not be empty.
- **Closed by default.** An admitted client that matches no rule gets no operations.
- **Load checks.** xmsg refuses a duplicate rule pattern. It also refuses a rule that no admission
  pattern can match.
- **Names.** The client's node name comes from its URI, as for a CA entry. At load, xmsg refuses a
  pattern without `*` that gives this node's own name or a concrete entry's name. At connect, it
  refuses a client whose name is a concrete entry's name. When two different URIs give the same
  name, it refuses the second client.
- After an admitted client connects, its name is in this node's view of known nodes.

## Mesh `list` across peers

Two things authorize mailbox access: the authenticated peer identity, and `leaf: true` on the
hub's peer entry. xmsg accepts `inbox` in `allow` and ignores it. Thus old configurations that
list it still load. It does not give more mailbox access.

When a caller runs `list` without a `node` filter, `xmsg` asks this node and each peer in
`peers.json` at the same time. The timeout is 5 seconds for each peer:

- xmsg asks **direct peers** over `GET /fed/v2/sessions`.
- **Dial-out clients (`"leaf": true`)** get a `{"kind":"list","query":"..."}` item in their hub
  mailbox. The item wakes their long-poll. They send their filtered recipient list back to
  `POST /fed/v2/list/{query}`.
- A peer's `allow` list for the asker can omit `"list"`. Then the peer refuses with
  `403 Forbidden`. The asker shows that node in `nodes` as
  `status: "unreachable", detail: "withholds list"`.
- Host-internal details (`pid`, `cwd`, harness, local paths) never cross `/fed/v2`. The asker
  drops each entry whose reported `user` is not the peer certificate's user.

### Policy defaults matter

`principals: []` removes the sender filter. It does not refuse all senders. To stop an
operation, remove it from `allow`. To show no local recipients, use `targets: []`.

A network connection must still pass the peer's TLS identity, its operation rights and the `from`
filter, if there is one. `allow`, `principals` and `from` control the traffic that this node
accepts from that peer.

A hub also applies a destination peer's `targets` filter before it forwards or queues. Dialable
forwarding sends that limit to the recipient in `forwarded.targets`, for semantic target checks.
Mailbox pull items do not have that marker. The hub-side pre-filter applies to them, but the
recipient does not enforce the forwarded target limit. This is a known limitation. See
[hub forwarding](/concepts/hubs-and-leaves/#forwarding-through-a-hub).

The empty-list rules are in
[`PeerConfig` parsing and inbound checks](https://github.com/sini/xmsg/blob/76f8f1e8249777cfb63c4d0287431cbbf6b2ce76/src/fed.rs).
