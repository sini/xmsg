[Federation](/glossary/#federation) connects xmsg nodes on different hosts, virtual machines
and Kubernetes pods. The nodes use mutual TLS ([mTLS](/glossary/#mtls)) on the `/fed/v2` wire
protocol. Each node lists the nodes it trusts, its [peers](/glossary/#peer), in a
[peers file](/glossary/#peers-file).

## Self-authenticating node names

xmsg makes a node's name from its cryptographic identity or its OS identity. You cannot set the
name with a free-form flag. xmsg refuses `--host-label` and `XMSG_HOST_LABEL` at startup:

1. **CA-signed identity (`--fed-cert` with URI SAN):** The name comes from the single
   [SPIFFE](/glossary/#spiffe-id) URI Subject Alternative Name (SAN) on the node's leaf
   certificate:
   - `spiffe://<trust-domain>/host/<host>/user/<user>` $\rightarrow$ `<user>.<host>` (for example,
     `alice.workstation`).
   - `spiffe://<trust-domain>/ns/<ns>/sa/<sa>` $\rightarrow$ `<sa>.<ns>` (for example,
     `genie-guard.genie`).
   - xmsg refuses a dot (`.`) in `<user>`, `<host>`, `<ns>` or `<sa>`.
2. **Pinned key (`--fed-cert` without URI SAN):** The name comes from the public key. xmsg takes
   the SHA-256 digest of the key's `SubjectPublicKeyInfo` DER. It encodes the digest in lowercase
   RFC 4648 base32. The name is the first 16 characters (for example, `k5x3q7mzv2ndp4ha`).
3. **No federation identity (local-only):** When `--fed-cert` is not set, the node name is
   `<user>.<host>`. `<user>` is the OS username of the effective UID. `<host>` is the short
   hostname, cut at the first `.`. This name never goes on the wire.

### Planned: enrolled identity through OIDC

An [enrollment CA](/operations/enrollment-ca/) inside an xmsg hub can sign a host
identity after browser sign-in. This is the CA trust form above, not a third TLS
trust mode: `spiffe://example.org/host/laptop/user/alice` still derives
`alice.laptop`. The user comes from a verified claim and explicit CA policy; the
host is the machine's unverified label. Never grant authority on that host label.
Peers trust the enrollment root only in their intended `ca` entries or
[pattern-bound bundles](#hub-admission-hub). Fleet and pod issuers remain separate.

### Canonical names and local nicknames

Envelopes on `/fed/v2` carry canonical node names. The receiving node gives each incoming
message the canonical name of the peer entry that authenticated the TLS connection. The exception
is a message that an
[authorized forwarding hub relays](/concepts/hubs-and-leaves/#forwarding-through-a-hub).

When you type `@node` locally, you can use the peer's canonical name. For a pinned peer, you can
also use your local nickname, which is the key in your `peers.json`. An exact canonical name or
nickname has priority over a bare-host selector such as `workstation`:

- `list(node="workstation")` asks all matching nodes in the current view.
- `send(to="guard@workstation", text="...")` selects one match. Two or more matches return
  `ambiguous`. With no match, the explicit destination goes to the default route, if there is
  one. Otherwise it is unknown.

To select one user on a shared host, use a canonical name. See
[node selectors](/concepts/addressing/#node-selectors).

## Trust models: pinned vs. CA-signed

Each entry in `peers.json` uses **exactly one** trust mechanism:

- **Pinned certificates (`pin`):** xmsg authenticates the peer when its SHA-256 SPKI certificate
  fingerprint (`sha256:...`) is the [pin](/glossary/#pin). Use it for direct 1:1 peerings,
  laptops and edge nodes without a PKI.
- **CA-signed certificates (`ca` + `identities`):** xmsg checks the peer's X.509 certificate
  chain against a PEM trust anchor bundle (`ca`). The leaf certificate's **single URI SAN** must
  be the entry's single concrete URI (`identities`). xmsg never uses the Common Name (CN) or DNS
  SANs for identity. Use it for SPIFFE/SPIRE, `cert-manager`, `step-ca` or a fleet CA, where
  certificates rotate automatically. See [CA entry](/glossary/#ca-entry).

```json
{
  "peers": {
    "laptop": {
      "address": "192.168.1.50:7788",
      "pin": "sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
      "allow": ["send", "reply", "list"],
      "from": ["192.168.1.0/24", "fd00::/8"]
    },
    "worker.prod": {
      "address": "10.0.0.12:7788",
      "ca": "/etc/xmsg/spire-bundle.pem",
      "identities": [
        "spiffe://example.org/ns/prod/sa/worker"
      ],
      "allow": ["send", "reply"]
    }
  }
}
```

### Naming and non-overlap invariants (`xmsg check-peers`)

`xmsg serve` and the standalone validator
`xmsg check-peers <peers.json> [--fed-cert <cert.pem>]` both apply these rules:

- A CA peer entry's key must be the node name that its `identities` URI gives (`worker.prod`
  above).
- A pinned peer entry's key is its 16-character key-derived name or a local nickname. A nickname
  must not contain `.`. It must not be 16 characters of `[a-z2-7]`.
- All entry keys, derived names and this node's own name share one namespace. There must be no
  collisions and no duplicate JSON keys.
- At handshake time, a certificate must match **exactly one** peer entry. Overlapping CA entries
  fail closed. A certificate that matches both a pinned entry and a CA entry also fails closed.

## Peer configuration reference (`--peers-file`)

### File format

The peers file is a JSON object. This site uses the wrapped form in its examples:

```json
{
  "peers": { "<entry key>": { ... } },
  "hub": { "patterns": [ ... ], "rules": [ ... ] }
}
```

- `peers` holds one entry for each peer. The entry key is the peer's node name or a local nickname.
- `hub` is optional. It is permitted only in the wrapped form. See [hub admission](#hub-admission-hub).
- Any other top-level field is refused.

xmsg also accepts two other forms. A bare map has the entries at the top level, with no `peers`
wrapper. The Home Manager module writes this form. A JSON array of entries is also accepted; each
entry then needs a `name` field. Neither form can hold a `hub` block.

### A leaf entry

A hub does not dial a leaf. The leaf connects to the hub and collects its messages. Thus a
`leaf: true` entry does not need an `address`:

```json
{
  "peers": {
    "guard.genie": {
      "ca": "/etc/xmsg/ca.pem",
      "identities": ["spiffe://example.org/ns/genie/sa/guard"],
      "leaf": true,
      "allow": ["send", "reply"]
    }
  }
}
```

A sender on the hub can send to `<target>@guard.genie`. A peer can also ask the hub to forward a
message there. In both cases the hub stores the message in its `peer_mailbox`, and the send
returns `outcome: "queued"`, not `"delivered"`. The message stays queued until the leaf collects
it and acknowledges it.

### Global deny and current certificate authority

The wrapped file form accepts `deny` beside `peers` and `hub`:

```json
{
  "peers": {},
  "deny": {
    "uris": ["spiffe://example.org/host/lost-laptop/user/alice"],
    "spkis": []
  }
}
```

`deny.uris` contains nonempty exact URI SAN strings. Every actual URI SAN is
checked; there is no pattern, alias or normalization match. `deny.spkis` contains
64 lowercase hexadecimal SHA-256 DER-SPKI fingerprints without `sha256:`. Missing
or empty lists add no denial. Unknown fields, wrong types and malformed
fingerprints reject the complete reload and retain the previous policy.

A matching deny wins over explicit pins, concrete CA entries and hub patterns,
for inbound and outbound federation. A loaded deny is checked again at request
entry and response publication, including parked polls and internal answer
publication. Reverse answer uploads check each awaited frame before append.
Outbound response frames are checked before parsing or accepting their bytes.

CA-mode connections also retain their actual leaf's `not_after` and refuse after
that deadline at those same boundaries. A renewed leaf or learned cached pin
cannot extend the old connection's expiry. Explicit pin-mode connections continue
to ignore certificate expiry, but still obey deny. An operation already beyond
its applicable check can finish its bounded effect; parallel operations may each
have passed a check, and committed effects are not rolled back. This does not
close idle sockets. CA issuance/renewal policy and the standalone fleet-collector
HTTPS client are separate. See the [offboarding runbook](/operations/enrollment-ca/#offboard-a-teammate-or-a-lost-or-stolen-device).

### Entry fields

| Field | Type | Description |
|---|---|---|
| `address` | `string` | The peer's `host:port` endpoint. Required, except on a `leaf: true` entry (the hub never dials it), when another entry sets `default_route`, or on an exact-identity entry (a `pin`, or a `ca` entry with one identity) that an enabled [discovery](/concepts/discovery/#the-discovery-key-and-source-availability) source can find. |
| `pin` | `string` (optional) | Expected SHA-256 certificate fingerprint (`sha256:...`). Mutually exclusive with `ca`. |
| `ca` | `string` (optional) | Path to PEM trust anchor bundle. Mutually exclusive with `pin`; requires `identities`. |
| `identities` | `list[string]` (optional) | Single concrete SPIFFE URI SAN (`["spiffe://..."]`). Required with `ca`. |
| `allow` | `list[string]` | Permitted capabilities (`"send"`, `"reply"`, `"list"`, `"inbox"`, `"forward"`, `"relayed"`; planned `"observe"`). |
| `observe_labels` | `bool` (optional, planned) | Default `false`; even an explicit `false` requires `"observe"` in `allow`. Labels also require request opt-in. |
| `from` | `list[string]` (optional) | Permitted source IP addresses or CIDR blocks for inbound connections. Empty `[]` is refused. |
| `leaf` | `bool` (optional) | When `true`, this node does not dial the peer. Messages and `list` queries for the peer wait in this node's durable `peer_mailbox` until the peer collects them by long-polling. A send to the peer returns `outcome: "queued"`. Default `false`. |
| `dial` | `"outbound"` (optional) | Starts a background pull loop on this node. The loop connects to `address`. It pulls messages, answers `list` queries and polls replies. Not permitted with `leaf: true`. |
| `principals` | `list[string]` (optional) | Inbound sender filter: service name, instance ID or `anon:<from>`. **Absent or `[]` permits every principal.** A list with entries permits only those senders. |
| `targets` | `list[string]` (optional) | Local recipient filter for messages and `list`: service name or instance ID, never an instance label. **Absent permits all; `[]` permits none.** |
| `default_route` | `bool` (optional) | Use this peer for an explicit `ref@node` destination that is not a direct peer. At most one entry may set it to `true`; direct routes take precedence. See [hub forwarding](/concepts/hubs-and-leaves/#forwarding-through-a-hub). |

### Mailbox retention

<Status id="xmsg.peer-mailbox" />

A stored message or reply stays in the `peer_mailbox` until its
leaf acknowledges it or it passes the reply TTL. `--reply-ttl` (`XMSG_REPLY_TTL`) defaults to
604800 seconds (7 days). Expiry cleanup also runs while the hub is idle: every 10 minutes by
default, or once per reply-TTL period when that is shorter, with a minimum interval of 1 second.
The existing cleanup after a local delivery remains. Expired rows can remain until the next
cleanup tick; an ACK removes its row immediately.

Each leaf has a separate budget. The defaults allow 10,000 rows and 67,108,864 bytes (64 MiB),
intended as an offline-week budget that operators can resize for their traffic. These are two
independent limits, not a promise that every workload fits a week. Configure the per-leaf budget
for this daemon with:

| Option | Environment | Default |
|---|---|---|
| `--peer-mailbox-max-rows` | `XMSG_PEER_MAILBOX_MAX_ROWS` | `10000` |
| `--peer-mailbox-max-bytes` | `XMSG_PEER_MAILBOX_MAX_BYTES` | `67108864` |

Zero refuses new stored rows. Limits count all stored messages and replies for that peer;
transient `list` queries are not persistent rows. Bytes count every UTF-8 string column, including
body, envelope JSON and origin/metadata, plus 16 bytes for the two integer fields. A body stored
both directly and in the envelope counts twice. SQLite page/index overhead is outside this byte
budget; the row limit also bounds per-row overhead.

An insert that would cross either limit is refused with HTTP `429` and error code
`peer_mailbox_full`. That refusal reaches the sender, including through a forwarding hub and
on reply paths. Existing rows are kept; no oldest-message eviction or silent drop occurs. An
already-stored duplicate succeeds without consuming more budget, even at capacity. ACKs and
expiry cleanup free capacity. Existing over-limit mailboxes are not trimmed on upgrade: they
refuse new rows until enough old rows leave. Retry a refused send/reply after capacity is freed,
using the same idempotency key when the sending interface supports it.
The command-backed service retains its pending response and stable reply key while it retries
this temporary refusal. Internal delivery-rejection notices remain best-effort: a failed notice
is logged by error code, and the rejected item is still ACKed so it cannot block the queue.


### Hub admission (`hub`)

A hub can admit clients that have no entry of their own. The `hub` block matches the client's
certificate identity against patterns. Each pattern (<Status id="xmsg.enroll-ca" />) binds its own CA bundle,
and a rule may grant a durable leaf mailbox:

```json
{
  "peers": {
    "xmsg.ca-host": {
      "address": "ca-host.example.org:7788",
      "ca": "/etc/xmsg/fleet-ca.pem",
      "identities": ["spiffe://example.org/host/ca-host/user/xmsg"],
      "allow": ["send", "reply"]
    }
  },
  "hub": {
    "patterns": [{"pattern": "spiffe://example.org/host/*/user/*", "ca": "/etc/xmsg/fleet-ca.pem"}],
    "rules": [
      { "pattern": "spiffe://example.org/host/*/user/alice", "allow": ["send", "reply", "list"] }
    ]
  }
}
```

- **`patterns`** (required, not empty): a SPIFFE pattern may be an object
  `{ "pattern": "spiffe://example.org/host/*/user/alice", "ca": "/etc/xmsg/enrollment.pem" }`.
  A `*` matches one whole path segment, including a keyword position. The TLS verifier and
  request admission both use the matched pattern's bundle; anchors are not pooled across
  unrelated patterns.
- **Every pattern needs one bundle.** An object names its bundle directly and does not need a
  concrete CA peer entry. A bare string remains compatible when the file's CA entries resolve
  to one bundle; with several distinct bundles, it is refused until its `ca` is explicit.
- **`rules`** (optional): the first matching rule grants `allow` operations and optional
  `leaf: true`. Allowed operations are `send`, `reply`, `list`, `forward` and `relayed`.
  `leaf` defaults to false. A rule compatible with patterns of different bundles is refused;
  split it rather than sharing a fleet rule with enrollment identities.
  Planned observation rules also accept `observe`, optional `targets` and
  `observe_labels`; an observe rule must name one literal SPIFFE identity.
- **Closed by default.** An admitted client that matches no rule gets no operations.
- **Load checks.** xmsg refuses a duplicate rule pattern. It also refuses a rule that no admission
  pattern can match.
- **Names.** The client's node name comes from its URI, as for a CA entry. At load, xmsg refuses a
  pattern without `*` that gives this node's own name or a concrete entry's name. At connect, it
  refuses a client whose name is a concrete entry's name.
- **Planned: prospective name ownership.** A dynamic client is refused if another full URI
  allowed by the configured patterns could derive its name, even before either client connects.
  The check retains the trust domain and the `host/user` or `ns/sa` form. Several patterns that
  describe the same exact URI are not a collision. The configuration may still load, but an
  ambiguous dynamic alias cannot be claimed by arriving first or reconnecting after a restart.
- After an admitted client connects, its name is in this node's view of known nodes.
- **Cross-bundle name checks:** patterns under distinct bundles must not derive a common
  canonical name. The check ignores trust domains and covers both `host/…/user/…` and
  `ns/…/sa/…`, including wildcards in keyword positions. Refusal prevents another bundle from
  reclaiming a queued mailbox name after restart. See
  [enrolled hub mailboxes](/concepts/hubs-and-leaves/#planned-enrolled-nodes-and-bounded-hub-mailboxes).

### Planned: check ambiguous aliases before an upgrade

Before upgrading a hub that mixes host/user and namespace/service-account patterns, check
for names that those patterns could share. **Enrollment being disabled is no exemption.**
Use the new binary's `xmsg check-peers PEERS_FILE [--fed-cert CERT]` before replacing the
running hub. It warns on stderr about ambiguous alias classes while keeping exit `0` for an
otherwise valid configuration. Existing load errors still fail validation.

Startup and successful reload also emit one warning per ambiguous alias class, naming the
alias pattern and colliding forms without full URI witnesses. Doctor's federation section warns:
`pattern admits ambiguous aliases; give pods concrete CA leaf entries`.

Reserve affected pods with concrete CA leaf entries, or partition the patterns, before upgrading.
A concrete entry reserves its exact name and identity while the pod is offline and keeps the
existing node spelling. See the [pod reservation example](/concepts/hubs-and-leaves/#planned-reserve-pod-names-before-upgrading).

## Mesh `list` across peers

Two things authorize mailbox access: the authenticated peer identity, and `leaf: true` on the
hub's peer entry. xmsg accepts `inbox` in `allow` and ignores it. Thus old configurations that
list it still load. It does not give more mailbox access.

When a caller runs `list` without a `node` filter, `xmsg` asks this node and each peer in
`peers.json` at the same time. The timeout is 5 seconds for each peer:

- xmsg asks **direct peers** over `GET /fed/v2/sessions`.
- **Dial-out clients (`"leaf": true`)** get a `{"kind":"list","query":"..."}` item in their hub
  mailbox. The item wakes their long-poll. They send their filtered recipient list back to
  `POST /fed/v2/list/{query}`.
- A peer's `allow` list for the asker can omit `"list"`. Then the peer refuses with
  `403 Forbidden`. The asker shows that node in `nodes` as
  `status: "unreachable", detail: "withholds list"`.
- Host-internal details (`pid`, `cwd`, harness, local paths) never cross `/fed/v2`. The asker
  drops each entry whose reported `user` is not the peer certificate's user.

### Policy defaults matter

`principals: []` removes the sender filter. It does not refuse all senders. To stop an
operation, remove it from `allow`. To show no local recipients, use `targets: []`.

A network connection must still pass the peer's TLS identity, its operation rights and the `from`
filter, if there is one. `allow`, `principals` and `from` control the traffic that this node
accepts from that peer.

A hub also applies a destination peer's `targets` filter before it forwards or queues. Dialable
forwarding sends that limit to the recipient in `forwarded.targets`, for semantic target checks.
Mailbox pull items do not have that marker. The hub-side pre-filter applies to them, but the
recipient does not enforce the forwarded target limit. This is a known limitation. See
[hub forwarding](/concepts/hubs-and-leaves/#forwarding-through-a-hub).

The empty-list rules are in
[`PeerConfig` parsing and inbound checks](https://github.com/sini/xmsg/blob/76f8f1e8249777cfb63c4d0287431cbbf6b2ce76/src/fed.rs).

## Diagnose peer connectivity

<Status id="xmsg.doctor-peers" />

Run `xmsg doctor --json` on the node to inspect bounded federation diagnostics. Doctor
asks the daemon through its Unix socket; it does not load private keys or dial peers.
The daemon reuses its loaded identity and existing pin/CA verifiers. No periodic probe,
new federation route or new peer right is introduced.

Each invocation considers at most 32 sorted configured peers, with four concurrent probes,
a two-second peer deadline and an eight-second total deadline. Addressless, unattempted
and outbound-only client entries remain unknown rather than acquiring guessed addresses.
Peer failures warn at most. An expired leaf actually loaded by the local daemon fails;
an approaching expiry warns within the smaller of seven days or one-third of its lifetime.
Certificate output contains only subject, issuer and `notAfter`, not DER, SANs, pins or keys.

The daemon requests `HEAD /` on the existing federation listener and observes the normal
`404` response's HTTP `Date`. The reported offset is relative to the local clock, with
uncertainty and a 120-second tolerance. Neither side is declared wrong; missing/invalid
dates, unexpected status or a local wall-clock jump leave it unknown. mTLS reachability
does not prove application permissions or delivery readiness. Normal connection counters
or admission caches may update during the handshake, but this diagnostic makes no
persistent or application-state writes, listing requests or reconciliation calls. See
[troubleshooting](/operations/troubleshooting/) and the
[Unix endpoint reference](/reference/http-and-sockets/#invocation-only-federation-diagnostics).

## Identity during credential renewal

Planned: live credential reload preserves the running node's derived name. Renewing
a certificate for the same derived name can change its key or issuing CA; replacing
it with a certificate deriving another name is rejected while the old TLS and peer
configuration keep working. A pinned certificate's public key determines its name,
so rotating that key changes the node identity. See
[credential reloading](/operations/runtime-and-systemd/#dynamic-credential-ca-bundle--peers-reloading)
for the renewal example and intentional identity-change procedure.

## Planned: pattern-specific admission roots

Hub patterns may use the object form `{"pattern": "spiffe://example.org/host/*/user/alice", "ca": "/etc/xmsg/enrollment.pem"}`.
The TLS verifier and request admission both verify against that pattern's bundle,
rather than pooling every peer root. Bundle files participate in credential reload;
an unreadable or invalid bundle retains the previous working configuration.
Patterns bound to distinct bundles cannot derive a common node name, even with
wildcards in keyword segments or different trust domains. A rule compatible with
patterns of multiple bundles is refused. See
[enrolled hub mailboxes](/concepts/hubs-and-leaves/#planned-enrolled-nodes-and-bounded-hub-mailboxes)
for the rule's `leaf` field and a configuration example.

## Observation grants

The literal `observe` capability permits bounded stored metadata reads on the
federation listener. It is never implied by other rights, `"*"`, `leaf: true` or
a wildcard admission pattern. Concrete CA identities remain literal-only; hub
rules granting observe must also be literal. First-match rules never union grants.
For observation, omitted `targets` is node-wide after the explicit grant, `[]`
permits no endpoint/event data, unqualified keys mean local endpoints and qualified
keys match exactly. Every endpoint must pass the scope check. Labels require
both grant and request opt-in. Reconnect after peer-policy reload.

See [fleet observer concepts](/concepts/fleet-observer/) and the
[grant and request example](/operations/fleet-observer/). The collector, owner
authentication and web view (<Status id="fleet-observer.collector" />) are tracked in the feature manifest.


## Reverse observation controls

<Status id="fleet-observer.reverse-relay" />

Reverse metadata export reuses the leaf's
outbound control-only HTTP polls. A capable leaf advertises `observe_relay=1`
on each poll; the hub can send an Observe control only to that currently waiting
poll. A concurrent legacy poll can receive only its existing List/Attachment
controls. The capability disappears when its poll completes or disconnects.
The leaf answers with a fresh outbound mTLS POST; no leaf listener, consuming
message poll, custody row, ACK, or message wake is introduced.

The top-level `reverse_observe` peers block has independent `hub_enabled` and
`leaf_enabled` booleans, both defaulting to `false`, and an empty-by-default
`routes` list. Each route has exactly `hub`, `leaf`, and `collector`, containing
literal full SPIFFE identities or lowercase `sha256:` pins. Unknown, duplicate,
and wildcard route configuration is refused. A route does not grant `observe`:
the end collector needs that right independently at both hub and leaf.

The hub attests the actual authenticated collector, and the leaf checks that
assertion against its enabled exact route and its own current collector policy.
The hub is an owner-administered trusted origin attestor, not independent leaf
proof. See [the trust and IP limits](/concepts/fleet-observer/) and
[the hub/leaf configuration example](/operations/fleet-observer/#reverse-observation-through-a-trusted-hub).

The collector selects direct or relay transport per source, using full
hub/leaf identities and a separate trust binding for each configured hub. Relay
history displays the configured leaf via its trusted hub. Changing routes takes
effect on collector restart and purges the previous route's cache; no browser
header can select or stamp an origin. See [collector relay setup](/operations/fleet-observer/#collector-relay-source).

## Exact-identity discovery

<Status id="xmsg.discovery" />

The [discovery core](/concepts/discovery/) keeps configured addresses authoritative, then verifies candidate addresses against an exact configured identity: one CA URI, or an SPKI pin. Announcements do not grant admission. Core-only builds keep the unimplemented source off; address-less onboarding requires the later source integration. Existing leaf mailboxes and applicable hub forwarding retain their semantics.

## Remote session locators

`xmsg locate ADDRESS@NODE` uses the existing federated list authorization and
transport with a read-only query. New peers do not reconcile claims, prune history,
or deliver queued messages for it. On a peer older than this release, a remote
locate behaves like an ordinary list: the peer may reconcile its claims as it
does for `xmsg list`. Deploy the peer update together. A node that cannot answer
is reported as unreachable or refused, with its node error; the locator never
retries a different, mutating query.

Remote results contain only the existing recipient fields. The locator-only `native_id`, terminal environment and working-directory
fields never leave the source node. Existing recipient labels remain unchanged
and can already contain harness session names. Run `xmsg locate` on that node for local details. A reach hint
can come only from the viewer's explicitly selected local configuration; peer
recipes or hints are not accepted. Reach strings are displayed, never executed.

## Mission Control delegated grants

<Status id="mission-control.delegated-grants" />

The owner can define an expiring grant for a separate holder with an explicit
set of verbs and canonical endpoint targets. The mint path requires a
`{node, endpoint}` pair for each target, including its exact endpoint
address. An optional read scope narrows what the holder can observe.
Rebinding or removing the minting owner ends its grants.

The planned command stage uses the current grant directly, without an owner
round trip for each request. Audit records distinguish the holder, an
independently authenticated presenting service when present, and the
minting owner. The planned confirmation option applies only to selected verbs
after the owner opts in through the management panel.

See the [owner CLI](/reference/cli-and-mcp/#mission-control-owner-cli).

### Planned Mission Control delegation

The planned delegated grant records a holder, explicit verbs and targets,
and possibly a narrow read scope. The grant supplies the holder's
authority within those bounds. Its audit chain distinguishes the holder,
an authenticated presenter when applicable, and the minting owner.
The separated management panel gates production use. The commands unit
will separately gate the optional per-verb `confirm_verbs` setting.
