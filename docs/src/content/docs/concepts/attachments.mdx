## Local protocol

A message can carry up to eight content-addressed references:

```json
{"name":"report.md","size":18,"media_type":"text/markdown","sha256":"<64 lowercase hex>"}
```

The bytes stay in SQLite, not in the message text. `--max-attachment-bytes`
(`XMSG_MAX_ATTACHMENT_BYTES`, default 8 MiB) sets the maximum size of each file. xmsg sanitises
names. The maximum name length is 128 bytes. The default media type is
`application/octet-stream`. Attachment rows have the same reply TTL as their message. Staged
bytes that are not sent, and incomplete uploads, expire after the idempotency TTL. Garbage
collection removes orphaned blobs. A hash alone does not give permission to attach or read a
file.

On `agent.sock`, stage inline bytes with
`{"action":"attach","name":"report.md","data":"<base64>"}`. Inline `data` is the portable form.
It also works across container filesystems. On the same host, you can also use
`{"action":"attach","name":"report.md","path":"/absolute/file"}`. The daemon resolves this path
on its own host, which can be different from the caller's container. The answer contains
`attachment`. Put that reference in the `attachments` array of a send or reply. Plugin harnesses
use these operations on `register.sock`, with the held `session` and `request_id`, as for send.

For larger socket uploads, send `attach` for each chunk. Give an opaque `upload` ID, the byte
`offset` and base64 `data`. Start at offset zero. A retry of the same bytes at the same offset
does nothing. xmsg refuses a conflicting offset. To finish, send
`{"action":"attach","upload":"<id>","name":"report.md","sha256":"<optional expected hash>"}`.
If you give an expected hash, the server checks it before it stages the completed file.

MCP `send` and `reply` accept `attachments` entries. Each entry is
`{"path":"/absolute/file","name":"optional-name"}` or
`{"name":"report.md","text":"file contents"}`, with an optional `media_type`. MCP stages the files
before it sends. It divides large inline text into chunks automatically.

Read with `{"action":"read_attachment","message_id":"<id>","index":0,"offset":0,"length":4096}`.
The default length, and the maximum, is the node's message-body limit. Offsets count bytes. A
UTF-8 read ends at a character boundary. xmsg refuses an offset inside a character. Other data is
base64 encoded. Follow `next` until there is no `next`. A message's sender and recipient can read
its files. Anyone with a reply's pushed message ID can read the reply's files. This is the same
access as for stored replies.

An HTTP upload uses `POST /v1/attachments?name=report.md&media_type=text/markdown` with raw
bytes. An anonymous sender also gives its usual `from` query value. Sends and replies take the
returned reference in `attachments`.
`GET /v1/messages/{id}/attachments/{index}?offset=0&length=4096` returns raw bytes,
`Content-Type`, `X-Xmsg-Sha256`, and `Content-Range`.

## Files between nodes

Federated attachment fetching is planned and is not in a tagged release yet. Send and reply
use the same references across [federation](/concepts/federation/). Both nodes must support
attachments. The receiving node fetches a file when someone first reads it, checks the whole
file's size and SHA-256, then serves the requested range. A failed integrity check stores no
verified copy; a later read tries again. A read that takes more than ten seconds returns
`pending` while fetching continues. Retry the read to collect its result. A fetch waits and
retries a rate-limited chunk within a three-minute total deadline. Expiry of that deadline
returns a retryable error, discards partial chunks, and publishes no verified blob.

Files travel along the message's authenticated peer route. A hub fetches from the peer that
supplied that particular item before it serves the next hop. Having the same hash cached for
a different message does not bypass this check. A peer can fetch only an item whose recorded
downstream is that peer, while its current `reply` permission (for a message) or `send`
permission (for a reply) remains enabled. Reloading peers therefore applies to later fetches.
Files are never fetched from an unrelated node by hash.

An outbound-only leaf answers file queries through its hub mailbox; it needs no inbound
listener. Each chunk takes a mailbox round trip, so large files on a high-latency link can
be slow. Queue handoff preserves the file's original expiry. If the origin's file expires
before the first fetch, the read reports `gone`; a missing or unavailable upstream cannot
be replaced by an unrelated cached copy. A recipient can forward a readable file without
uploading it again: xmsg fetches and verifies it first.

Federation uses authenticated `GET /fed/v2/attachments/{item_id}/{index}?offset=0&length=4096`
for raw byte ranges, bounded by the message-body limit and charged to a separate attachment
rate bucket. Socket and local HTTP readers keep their existing item permissions and range
formats.

File contents remain [untrusted peer data](/concepts/trust-model/#provenance-is-not-instruction-authority).
